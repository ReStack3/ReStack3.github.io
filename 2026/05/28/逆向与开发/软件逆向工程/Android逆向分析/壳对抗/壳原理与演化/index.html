Java的反射机制

Java反射机制是指在程序运行时动态加载类并获取类的详细信息，从而可以操作类或对象的属性和方法。反射机制的核心是通过 Class 对象来实现的。当Java虚拟机（JVM）获得类的 Class 对象后，可以通过这个对象获取类的构造函数、方法、字段等信息，并且可以在运行时创建对象、调用方法或访问属性。这使得Java程序在运行时具有更高的灵活性和动态性。

可以把class文件想象成类的结构化目录，该类的成员变量和函数等都被分门别类的存在class的不同局域位置。而多个不同的class又组成了一个class目录。并于通过查询该目录找到对应的类的所有信息

常规实例化

想象你是一个图书馆管理员，编译时你知道所有书籍的名称和作者（例如，”Java 编程”）。当有人请求这本书时，你直接去书架上拿书。

Java是一种先编译后运行的语言，这意味着在编译时，程序中所有对象的类型和结构都是固定的。然而，在某些情况下，程序可能需要在运行时动态地加载某些类。比如，在插件化架构中，应用程序可以根据用户的选择或需求动态加载不同的模块，而这些模块在编译时并不存在。

反射机制允许开发者在运行时获取类的 Class 对象后【在 Java 中，类的 Class 对象是反映 Java 类的内部结构和行为的特殊对象。每个 Java 类、接口和枚举类型在运行时都会由 JVM 创建一个对应的 Class 对象，这个 Class 对象包含了关于该类的所有信息，例如类的名称、父类、实现的接口、方法、字段、构造函数等。】，可以利用这个对象来获取该类的构造函数、方法和字段等信息。基于这些信息，可以创建该类的实例、调用其方法或访问其属性，而不需要在编译时硬编码类的名称。

反射实例化

现在，假设你有一个应用程序，它可以根据用户的请求动态获取书籍。用户可能输入书名，而你不知道这个书名是否在书架上。你通过输入的书名查找图书馆数据库（使用反射），并在运行时决定是否能够找到这本书。如果书存在，你可以将它拿出来；如果书不存在，你将会处理一个错误。

反射的优缺点

1、优点：

（1）在运行时获得类的各种内容，进行反编译，对于Java这种先编译再运行的语言，能够让我们很方便的创建灵活的代码，这些代码可以在运行时装配，无需在组件之间进行源代码的链接，更加容易实现面向对象。

2、缺点：

（1）反射会消耗一定的系统资源，因此，如果不需要动态地创建一个对象，那么就不需要用反射；

（2）反射调用方法时可以忽略权限检查，因此可能会破坏封装性而导致安全问题。

双亲委派模型

在初识JVM - The Peak Tower中有对java的双亲委派模型做了一定的了解。

本质上 Android 和传统的 JVM 是一样的，也需要 ClassLoader 将目标类加载到内存，类加载器之间也复合双亲委派模型。但是在 Android 中，ClassLoader的加载细节有略微的差别。在 Android 虚拟机里是无法直接运行 .class 文件，Android 中会将所有的 .class 文件转化为一个 .dex 文件。Android 将加载 .dex 文件的实现封装在 BaseDexClassLoader 中，一般我们使用它的两个子类：PathClassLoader 和 DexClassLoader。

dex加载运行整体步骤

加载 classes.dex 文件

当应用程序启动时，系统会通过 ClassLoader 读取 APK 中的 classes.dex 文件。这个文件包含了应用的字节码。

初始化 DexClassLoader 或 PathClassLoader

Android 提供了不同类型的 ClassLoader（如 DexClassLoader 和 PathClassLoader）用于加载 .dex 文件。这些加载器在初始化时会指向要加载的 classes.dex 文件的路径。

解析 .dex 文件格式

.dex 文件的格式与 Java 的 .class 文件不同。它的结构包括：

  • 魔数（Magic Number）：用于标识文件格式。
  • 版本号：表示 .dex 文件的版本。
  • 字符串表：存储字符串常量的索引。
  • 类型表：存储类和接口的描述信息。
  • 方法表：描述所有方法的信息。
  • 字段表：描述所有字段的信息。

读取数据

ClassLoader 使用特定的解析器（如 Dex 类）读取 .dex 文件中的数据结构。通过索引和表的结构，ClassLoader 能够快速定位到每个类、字段和方法的描述。

查找和加载类

当需要加载一个类时，ClassLoader 会：

  • 查找字符串表，根据给定的类名找到类的索引。
  • 解析类型表，获取类的具体描述，包括父类、实现的接口等信息。
  • 解析方法表和字段表，获取类的方法和字段的详细信息。

检查已加载类

在加载之前，ClassLoader 会先检查其缓存，以查看类是否已经加载（通过 findLoadedClass() 方法）。如果已加载，则直接返回该类；如果未加载，继续执行后续加载操作。

生成类对象

一旦找到类的信息，ClassLoader 会调用 defineClass() 方法将字节码转换为 Java 对象。此时，JVM 会为该类分配内存，并初始化它的静态变量。

字节码验证

在加载过程中，系统会进行字节码验证，以确保类的安全性和有效性，防止恶意代码的执行。

JIT/AOT 编译

在 Dalvik 中，首次调用方法时会进行即时编译（JIT），将字节码编译为机器码。在 ART 中，应用安装时会将 .dex 文件的字节码编译为机器码（AOT），提高运行效率。

修正加载器

简单分析

如何加载dex文件？

Android里边的BaseDexClassLoader可以实现在运行的时候加载在编译时未知的dex文件，经过此加载器的加载，ART虚拟机内存中会形成相应的数据结构，对应的dex文件也会由mmap映射到虚拟内存当中，通过此加载器的loadClass(String className, boolean resolve)方法就可以得到类的Class对象，从而可以使用该类。

查看源码可以看到PathClassLoader是继承自BaseDexClassLoader的，而PathClassLoader还有另外两个兄弟: InMemoryDexClassLoader以及DexClassLoader，而壳程序很多都使用了这两个类加载器来加载解密后的dex文件。其中InMemoryDexClassLoader是Android8.0以后新增的类，可以实现所谓的”不落地加载”。

如何让修改加载之后的Application进入后续的加载流程？

后续的加载流程指的就是app组件（比如Activity）的加载，而加载组件时，使用的是加载应用程序的ClassLoader。

如若不做任何处理，仅仅在attachBaseContext方法中使用上面讲的某个类加载器对dex加载，后续加载源程序的组件时会出现ClassNotFoundException的错误，为什么会这样？

这是因为如果仅仅在attachBaseContext方法中使用类加载器加载dex，之后加载组件时使用的ClassLoader和我们使用的加载器不同，并且，加载组件的ClassLoader通过双亲委派模型发现没有人能加载组件类（因为组件类在我们的dex中），导致ClassNotFoundException。

还记得BaseDexClassLoader吗，其有一个DexPathList，记录了已加载的dex文件路径。

加载组件时对应的BaseDexClassLoader的DexPathList是没有源程序的dex路径的，如果尝试让BaseDexClassLoader加载不在这个列表中的类，就会报ClassNotFoundException。

因此有两种方法可以解决这个问题。

  1. 既然使用的加载器不同，那么改成相同的不就行了。

    通过反射获取到LoadedApk，修改其mClassLoader为我们加载dex文件的ClassLoader实例，这样后续试图加载组件类的时候，就能找到相应的类。

  2. 通过打破原有双亲委派关系，添加我们的ClassLoader进入关系网。

    原先的mClassLoader是PathClassLoader，其在双亲委派关系中的父亲是BootClassLoader，所以只要将我们的ClassLoader添加进他们两个之间即可。也就是将PathClassLoader的父亲设置为我们自己的ClassLoader，再将我们自己的ClassLoader的父亲设置为BootClassLoader

修正并加载源Application

简单分析

为什么要替换Application？

因为Application做为整个应用的上下文，它的生命周期就是整个应用程序的生命周期，它还会与Activity、Service等组件有交互关系。对于壳程序和源程序，它们对应的Application实例不一定相同，为了维护应用的正常生命周期，所以需要进行替换。可以认为Application就代表着整个APP，Application都不同，那运行的App能是一样的吗？

为什么选择Application类作为脱壳代码执行的地方？

因为Application是整个应用程序的入口点，它的创建早于任何一个Activity、Service的创建（ContentProvider例外），因此壳程序必须在Android系统启动组件之前运行，完成源程序的解密和动态加载，否则会使程序出现加载类失败的异常，所以选择这里作为脱壳代码执行的地方。

其次，Application类的attachBaseContext()方法比onCreate()方法先执行。

全在attachBaseContext()方法或者全在onCreate()方法中执行都行的！但在attachBaseContext()方法执行会有缺陷，就是ActivityThread实例中的mInitialApplication又会被壳程序的Application替换掉。

怎么替换Application？

需要将壳程序的Application（也就是mApplication）从ActivityThread实例中的mAllApplications中删除。之后设置LoadedApk实例中的mApplication字段为null，这样才能调用LoadedApk类的makeApplication()方法创建源程序的Application实例（也是反射，需要获取到源Application类名，可以通过在壳程序的ActivityManifest.xml中使用<meta-data>标签填写并在代码中获取）。当然ContentProvider也会有Application实例，也是需要替换的。最后运行源程序的Application实例的onCreate()方法，这样源程序才开始它的运行生命周期。

如果源程序也有自定义的Application，我们就需要重新makeApplication，进入到源程序的Application，保证程序的完整生命周期。

不落地加载壳实现

在第一代壳实现【DEX整体加固壳-落地加载】 - The Peak Tower和壳实现的前置知识 - The Peak Tower中实现的整体加固壳的基本工作原理可以简单总结为：

  1. 将加密的 DEX 文件解密后，写入设备的存储（如 /data/data/<package>/ 或 /sdcard/ 等目录）。
  2. 使用 DexClassLoader 或 PathClassLoader 从磁盘加载解密后的 DEX 文件。

我们注意到：解密后的 DEX 文件会被写入磁盘，生成一个临时文件。暂且不论文件 I/O 操作（如读写磁盘）会带来额外的性能开销。

但从安全性和隐私上：攻击者可以通过文件系统提取并分析这些文件。临时文件可能被恶意软件或调试工具捕获。解密后的 DEX 文件可能包含敏感信息（如密钥、算法等），写入磁盘后容易被泄露。

所以有没有一种机制能够之间直接在内存中解密和加载 DEX 文件，避免将解密后的 DEX 文件写入磁盘，从而减少被攻击的风险。不落地加载的方式也就应运而生了。

Android的抽取壳是一种常见的App保护技术，属于DEX加固的一种形式，主要用于防止反编译和代码分析。它的核心原理是将原始DEX文件中的关键代码（通常是业务逻辑或敏感算法）动态隐藏，在运行时再解密并加载执行，从而增加逆向分析的难度。其抽取壳的核心原理是：

  • 代码抽取：在编译阶段，将原始DEX中的关键方法（如onCreate()、支付逻辑等）的字节码替换为空实现或无效指令（如全NOP指令）。被抽离的原始字节码会被加密后存储在DEX的其他位置（如资源文件、自定义段）或服务器上。
  • 动态恢复：App运行时，壳代码（加固后的入口）会先执行，在内存中解密被抽取的原始字节码。通过Hook Android的类加载机制（如ClassLoader）或动态修改内存中的DEX结构，将解密后的指令回填到对应的方法体中。

PLT Hook（以 bhook 为例）
基本原理

目标对象：拦截 PLT（Procedure Linkage Table） 中的函数调用，主要用于动态链接库（.so）中的 外部函数调用（如 libc 的 open、read 等）。

实现步骤：

  1. 定位 PLT 表：PLT 表用于在动态链接时跳转到 GOT（Global Offset Table）中的真实函数地址。
  2. 修改 GOT 条目：将 GOT 中的函数地址替换为自定义的 Hook 函数地址。
  3. 执行流重定向：当原函数被调用时，实际跳转到 Hook 函数。

特点

  • 稳定性高：不修改函数体代码，只修改 GOT 表中的指针。
  • 局限性：仅适用于动态链接的符号（通过 PLT/GOT 调用的函数），无法 Hook 静态函数或模块内调用。
  • 性能影响小：无指令替换开销。

适用场景：Hook 系统库（如 libc、libart）的导出函数。适合需要高稳定性的轻量级 Hook。

Inline Hook（以 Dobby 为例）
原理

目标对象：直接修改目标函数的 机器指令，劫持执行流。

实现步骤：

  1. 定位函数入口：找到目标函数的起始地址。
  2. 插入跳转指令：在函数开头写入 ARM/Thumb 或 x86 的跳转指令（如 B <hook> 或 JMP）。
  3. 备份原指令：保存被覆盖的原始指令，在 Hook 函数中执行后再恢复。
  4. 跳转回原函数：通过 trampoline 机制执行原始指令并返回。

特点

  • 通用性强：可 Hook 任意函数（包括静态函数、模块内调用）。
  • 侵入性高：直接修改函数代码，可能触发代码签名校验或反调试。
  • 兼容性挑战：需处理指令对齐、多线程竞争等问题。

适用场景：Hook 任意地址的函数（如游戏逻辑、JNI 函数）。需要深度定制的复杂 Hook。

特性 PLT Hook (bhook) Inline Hook (Dobby)
Hook 对象 动态链接的符号（PLT/GOT） 任意函数地址（包括静态函数）
实现复杂度 低（修改指针） 高（指令替换、trampoline）
稳定性 高（不破坏原函数） 中（可能破坏指令或寄存器状态）
性能开销 几乎无 轻微（跳转指令 + trampoline）
兼容性 仅限动态链接库 全平台（需处理指令集差异）
对抗反 Hook 容易被检测（GOT 表修改） 更隐蔽（但可能触发代码校验）

值得注意的是：

**PLT Hook **无法 Hook 以下情况：

1.静态链接的函数。2.通过 dlopen 动态加载的库（需先确保符号已绑定）。

Inline Hook 需要注意：

  • 指令修复：ARM 架构需处理 Thumb/ARM 模式切换（如 PC+4 规则）。
  • 原子操作：多线程环境下需确保指令替换的原子性（如 ARM 的 IT 块）。
  • 反调试对抗：某些应用会校验关键函数的内存完整性。

  • 解释器维护虚拟机状态(寄存器、栈等)
  • 通过解释器代码而非原生机器码来管理这些状态

DexVmp原理：对原 dex 处理，找到要保护的方法，将原指令翻译成等价指令，加密存储，并将原指令替换为 VMP 入口指令 - 实现 VM，解释执行存储的等价指令。那么这样这样实现的VM可以在java层也可以在so层，一般来说是放在so层。

  1. 解析dex： 定位保护的方法，可以手动解析dex文件或者使用开源库dexlib2

  2. 将原指令翻译成等价指令 ： 这里就需要通过jni接口实现，这也是为什么DexVmp加壳后有native标签，我们知道一条java指令对应可以用jni指令进行实现，那么我们需要的就是将对应的方法通过jni接口调用so层中c/c++实现方法进行翻译。因为dex-vmp需要调用jni接口，所以一定会调用CallVoidMethod方法等，所以这也是为什么很多快速追踪vmp调用栈选择InvokeWithVarArgs的原因

  3. 实现VM: vm基于寄存器结构，我们需要初始化寄存器，然后对对应的Opcode进行翻译，这里调用一些jni接口

arm-vmp原理：将so文件中的arm汇编的指令码转换为自定义的虚拟指令。核心是虚拟指令集和虚拟指令解释器

  1. 将Native化的java代码和原C++代码使用Capstone进行反编译，生成原生汇编码

  2. 使用随机生成的矩阵将原生指令码转换为虚拟指令码

  3. 通过虚拟指令解释器对虚拟指令码进行解释

ART下的Vmp

我们知道在ART下使用AOT机制，其中会使用到dex2oat对app代码进行编译，这就违背了Vmp所需要的解释运行要求。所以在ART环境下，VMP（虚拟化保护）壳的运行流程需要绕过AOT编译的机器码执行，强制让被保护的代码回归到解释执行或动态解释的模式。防止被保护方法的代码被编译为机器码（.oat），确保始终由VMP解释器接管。

  • ART保留了Dex字节码解释器（尽管不常用），VMP利用这一点强制回归解释模式。
  • 动态代码支持：
    ART允许运行时加载/执行未编译的字节码（如动态代理），VMP通过加密指令流伪装成“动态代码”。
  • JNI桥接：
    所有系统调用最终通过JNI实现，与虚拟机版本无关。

同时需要模拟Dalvik行为，即在ART环境下，通过自定义解释器执行加密指令流（类似Dalvik时代的VMP）。

绕过AOT编译可以使用方法替换：
VMP编译器会将原始方法（如onCreate）的Dex字节码替换为一个壳入口桩代码（例如直接返回或抛出异常），确保该方法不会被dex2oat编译为机器码。 实际代码被加密后隐藏到资源文件或.so中。

或者强制解释执行： 当ART尝试调用该方法时，壳代码会拦截调用，跳转到VMP解释器（即使系统已生成AOT机器码）。

值得注意的是：VMP由于运行开销较大一般只保护关键算法

VMP解释器执行完所有指令后，通过VMP_RETURN将控制权交还ART，继续执行未保护的其他代码。

ART与Dalvik下VMP的差异

维度 Dalvik下的VMP ART下的VMP
对抗AOT 无需处理（Dalvik无AOT） 需主动破坏AOT编译或强制解释执行
性能损耗 高（解释+JNI） 极高（解密+解释+JNI+AOT失效）
实现复杂度 较低（直接修改解释器） 高（需绕过AOT优化和ART安全检查）
典型Hook点 dvmInterpret函数替换 art::interpreter::Execute劫持

总结一下

Android DexVMP的实现原理就是对ART解释器进行自定义,壳代码运行在传统ART解释器下,被加固应用运行在自定义解释器下。

补充

ART（Android Runtime）虽然在应用安装时通过 dex2oat 将 Dex 字节码预编译为 OAT 文件（ELF 格式的本地机器码），但 仍然需要保留解释器 的原因涉及兼容性、动态行为和运行时灵活性等多方面因素。

处理动态代码和反射

动态代码加载 ：某些场景下，应用会在运行时动态生成或加载 Dex 字节码（如插件化框架、热修复技术）。这些代码无法预先编译为 AOT 机器码，必须依赖解释器即时执行。

反射调用 ：反射（如 Class.forName()、Method.invoke()）的目标方法可能在运行时才确定，无法在 AOT 阶段静态编译。解释器可以动态处理这类调用。

兼容性与回退机制

AOT 编译失败 ：部分 Dex 字节码可能因复杂性或兼容性问题无法编译为机器码（如使用了某些指令或未优化的第三方库）。此时解释器作为备用执行路径。

低性能设备优化 ：在内存或存储空间不足的设备上，系统可能选择 部分 AOT 编译（仅编译高频代码），剩余代码由解释器执行以节省空间。

计算机执行原理与虚拟化基础

1. 物理计算机的核心运行逻辑

  • 硬件层：CPU 直接执行二进制机器码（如 x86 的 0x55 对应 push ebp），依赖物理寄存器和内存。
  • 软件层：操作系统将程序代码从磁盘加载到内存，CPU 按指令顺序执行。

2. 虚拟化的本质

  • 硬件虚拟化（如VMware）：
    通过 Intel VT/AMD-V 技术，让虚拟机直接访问物理CPU，性能高但无法隐藏原始指令。
  • 软件虚拟化（如VMP）：
    完全通过软件模拟 CPU 行为，自定义指令集和虚拟环境，实现代码混淆与保护。

下面先简单了解一下PC端VMP壳的的相关知识：

为什么要谈PC端，因为VMP加固技术方案大规模应用到软件保护领域最早在PC时代源于俄罗斯的著名保护软件”VmProtect”，该方案引起了软件保护壳领域的革命。各大软件保护壳开发团队都将虚拟机保护这一新颖的技术加入到自己的产品中。但是到目前为止该软件还未对ARM平台支持。随着移动端安全开发的升级，移动应用的安全越来越被重视，在PC时代用到的VMP方案也被成功应用到移动端的加固产品中来。

VMP的核心设计

虚拟执行环境的构建
物理硬件组件 VMP虚拟化实现 技术细节
CPU寄存器 VM_CONTEXT 结构体 内存中开辟区域模拟寄存器（如 EDI 指向虚拟寄存器数组 vReg[8]）。
内存访问 虚拟栈（vStack） 用 EBP 指向栈顶，操作与物理栈一致，但数据加密存储。
指令集 自定义字节码（VM_DATA） 指令码与物理CPU无关（如 0x1=压栈，0x2=加法），每个版本指令集不同。
指令指针 vEIP（如 ESI 寄存器存储） 指向当前执行的虚拟指令地址，通过 jmp esi 或 push esi, ret 实现分支跳转。

为了在软件层面模拟CPU执行二进制的代码指令，需要有以下关键点：

  • 虚拟机的寄存器，用来存放各种临时数据
  • 虚拟机的堆栈，用来做各种数据交换
  • 虚拟机的指令。x86架构下，CPU一旦读取到0x55指令，就知道执行push ebp；一旦读取到0x8BEC，就知道执行mov ebp,esp； 同理，虚拟机也需要有自己的指令集，虚拟CPU才知道自己要干啥。一般虚拟机的指令要么是操作寄存器，要么是操作堆栈，要么做各种算数运算，虚拟机指令的handler都要模拟这些功能。那么问题来了，虚拟机的指令集能不能和物理CPU一样了？ 显然是不行的！ 两个原因：（1）如果一样，还要纯软件虚拟机干啥？ （2）如果一样，达不到混淆指令的目的
  • 虚拟机的EIP，用来指明虚拟CPU当前执行的代码

为了满足以上关键点，VMP采取的方案：

  • 虚拟机的寄存器：在内存开辟一段连续的区域当成虚拟机的寄存器，业界称之为VM_CONTEXT，某些版本的VMP用EDI指向这个区域

  • 虚拟机的堆栈: 这个和物理机是一样的，直接在内存开辟就好。VMP还是用EBP指向栈顶
  • 虚拟机的指令：不同版本VMP的指令是不一样的，这样可以在一定程度上防止VMP本身被破解，业界俗称VM_DATA

一条指令由两部分组成，一个加密的handle偏移量和它加密后的参数（操作码和操作数）

  • 虚拟机的EIP：业界俗称vEIP，某些版本的VMP用ESI替代，指向VM_DATA，用以读取虚拟CPU需要执行的指令；

VMP虚拟机的执行流程

指令执行周期

  1. 上下文保存:保存物理寄存器状态（类似硬件虚拟化的 VMExit）。

  2. 指令分发

    Dispatcher 通过 vEIP 从 VM_DATA 读取指令码，跳转到对应 Handler：

    VStartVM部分初始化虚拟机，VMDispatcher负责调度这些Handler，Handler可以理解为一个个的子函数(功能代码)，它是每一个伪指令对应的执行功能代码，为什么要出现一条伪指令对应着一个Handler执行模块呢？这和虚拟机加壳的指令膨胀有关，被虚拟机加壳后，同样一条指令被翻译成了虚拟伪指令，
    一条虚拟伪指令往往对应着好几倍的等效代码，当中可能还加入了花指令，整个Handler加起来可能就等效为原本的一条x86汇编指令。Bytecode就是虚拟伪指令，在程序中，VMDispatcher往往是一个类while结构，不断的循环读取伪指令，然后执行。

  3. Handler模拟执行:每个 Handler 模拟物理指令行为（如 Handler_ADD 实现虚拟寄存器加法）。

  4. 循环执行:更新 vEIP，重复上述流程直至退出。

代码混淆与保护
  • 指令随机化：同一功能（如加法）在不同版本中使用不同指令码（0x2 或 0x5A）。
  • 动态解密：VM_DATA 在内存中加密，仅执行时逐条解密。
  • 反调试：检测调试器后触发 Handler 分支执行垃圾代码。
