浏览器渲染与前端框架

浏览器渲染原理

浏览器的渲染原理是指浏览器将 HTML、CSS 和 JavaScript 转换成用户可视界面的过程，这一过程涉及多个关键步骤，通常称为 “关键渲染路径”。渲染进程的主要任务就是将静态资源转化为可视化界面

一个渲染引擎主要包括：HTML 解析器，CSS 解析器，javascript 引擎，布局 layout 模块，绘图模块；

  • HTML 解析器：解释 HTML 文档的解析器，主要作用是将 HTML 文本解释成 DOM 树；
  • CSS 解析器：它的作用是为 DOM 中的各个元素对象计算出样式信息，为布局提供基础设施；
  • Javascript 引擎：使用 Javascript 代码可以修改网页的内容，也能修改 css 的信息，javascript 引擎能够解释 javascript 代码，并通过 DOM 接口和 CSS 树接口来修改网页内容和样式信息，从而改变渲染的结果
  • 布局 (layout)：在 DOM 创建之后，Webkit 需要将其中的元素对象同样式信息结合起来，计算他们的大小位置等布局信息，形成一个能表达这所有信息的内部表示模型
  • 绘图模块 (paint)：使用图形库将布局计算后的各个网页的节点绘制成图像结果

DOM树构建

HTML文档本质上是线性文本流：

浏览器需要将其转换为有层级的树形结构才能：

  • 理解标签之间的父子、兄弟关系
  • 正确应用CSS的层叠和继承规则
  • 计算元素的布局位置
  • 从页面的视角来看，DOM 是生成页面的基础数据结构；
  • 从 JavaScript 脚本视角来看，DOM 提供给 JavaScript 脚本操作的接口，通过这套接口，JavaScript 可以对 DOM 结构进行访问，从而改变文档的结构、样式和内容；
  • 从安全视角来看，DOM 是一道安全防护线，一些不安全的内容在 DOM 解析阶段会被拒之门外。

所以需要将HTML转化为浏览器能够理解的结构——DOM树。

对比维度 没有DOM树 有DOM树
结构理解 只能看到字符序列 理解嵌套层级关系
元素定位 基于字符串搜索（易错） 基于层级关系精确定位
样式应用 无法计算继承和层叠 支持完整的CSS规则
动态更新 重新解析整个文档 局部更新，高效增量渲染
事件系统 只能页面级事件 支持精确的事件委托和传播

在页面中，每个HTML标签都会被浏览器解析成文档对象。HTML本质上就是一个嵌套结构，在解析时会把每个文档对象用一个树形结构组织起来，所有的文档对象都会挂在document上，这种组织方式就是HTML最基础的结构——文档对象模型（DOM），这棵树的每个文档对象就叫做DOM节点。

所以输入HTML 文档（字节流）。过程：

  • 字节 → 字符：浏览器将原始字节解码为可读字符。
  • 词法分析（Tokenizing）：将字符转换为标记（Tokens，如 <html>、<div>）。
  • 语法分析（DOM Tree Construction）：根据标记的嵌套关系构建 DOM 树（Document Object Model）。

注意：遇到 <script> 会阻塞 DOM 解析（除非标记 async 或 defer）。遇到 <link rel="stylesheet"> 会并行下载 CSS，但会阻塞渲染（避免 FOUC）。

上面已经基本了解了DOM的构建过程，但是这个DOM结构只包含节点，并不包含任何的样式信息。下面就来看看，浏览器是如何把CSS样式应用到DOM节点上的。

JavaScript对DOM的影响：

JavaScript对DOM的影响主要体现在解析和渲染过程中的阻塞行为上。当HTML解析器遇到script标签时，无论是内联脚本还是外部脚本，都会暂停DOM的解析。这是因为JavaScript代码可能会修改已经生成的DOM结构，所以解析器需要等待脚本执行完成后再继续解析后续内容，以确保DOM的正确性。

  • 对于内联脚本，解析器会直接执行脚本内容；
  • 对于外部脚本，则需要先下载文件。脚本的下载过程同样会阻塞DOM解析，这可能会显著延长页面加载时间，尤其是当网络环境较差或脚本文件较大时。为了优化性能，可以通过CDN加速、压缩脚本文件等方式来减少下载时间。

如果脚本中没有操作DOM的代码，可以通过为script标签添加async或defer属性来实现异步加载，从而避免阻塞。

  • async属性允许脚本在下载完成后立即执行，但多个async脚本无法保证执行顺序；
  • defer属性则确保脚本在文档解析完成后按顺序执行，同时脚本的下载过程与文档解析并行进行，这样不会阻塞DOM的构建。

除了对DOM的直接影响，JavaScript的执行还可能受到CSS样式文件的阻塞。如果页面中存在外部CSS文件，渲染引擎在执行JavaScript之前需要等待CSS文件下载并解析完成，生成CSSOM对象。这是因为JavaScript代码可能会操作CSSOM，而引擎无法预先判断，因此会保守地等待所有样式就绪。这种依赖关系可能导致更长的延迟，特别是在样式文件较大或网络较慢的情况下。

总的来说，JavaScript会阻塞DOM的解析，而CSS样式文件又会阻塞JavaScript的执行，这种连锁反应可能显著影响页面的加载速度。在开发中，合理使用异步加载、可以优化资源顺序和减少不必要的阻塞

CSSOM树构建

同样，浏览器也是无法直接理解CSS代码的，需要将其浏览器可以理解的CSSOM树。实际上。浏览器在构建 DOM 树的同时，如果样式也加载完成了，那么 CSSOM 树也会同步构建。CSSOM 树和 DOM 树类似，它主要有两个作用：

  • 提供给 JavaScript 操作样式的能力；
  • 为渲染树的合成提供基础的样式信息。

**CSSOM树是样式系统的”大脑”**，它：

  1. 将声明式CSS转换为可计算模型 → 支持复杂的样式计算
  2. 建立样式层叠和继承规则 → 实现CSS的核心特性
  3. 提供样式查询和操作接口 → 支持动态样式和主题切换
  4. 与DOM树协同构建渲染树 → 决定最终视觉效果
  5. 实现响应式和条件样式 → 支持现代网页设计需求

不过，CSSOM 树和 DOM 树是独立的两个数据结构，它们并没有一一对应关系。DOM 树描述的是 HTML 标签的层级关系，CSSOM 树描述的是选择器之间的层级关系。可以在浏览器的控制台，通过document.styleSheets命令来查看CSSOM树。

输入的是CSS 文件或 <style> 内容。过程：

  • 类似 HTML 解析，生成 CSSOM 树（CSS Object Model）。
  • CSS 规则是层叠的，浏览器需计算最终的样式（如 font-size 的继承与覆盖）。

*特点：CSSOM 的构建是渲染阻塞**的（浏览器会等待所有 CSS 解析完成才渲染页面）。

特性 DOM树 CSSOM树
数据源 HTML文档 CSS样式表
结构 元素节点树 规则集合树
更新频率 相对较低 可能频繁（hover、动画）
继承机制 元素嵌套继承 属性值继承

在 DOM 树和 CSSOM 树都渲染完成之后，就会进入渲染树的构建阶段。渲染树就是 DOM 树和 CSSOM 树的结合，会得到一个可以知道每个节点会应用什么样式的数据结构。这个结合的过程就是遍历整个 DOM 树，然后在 CSSOM 树里查询到匹配的样式。DOM树 + CSSOM树 = 渲染树

DOM树：知道”有什么元素”，CSSOM树：知道”元素长什么样”，两者结合才能知道”如何在屏幕上绘制”

生成渲染树

渲染树是DOM树和CSSOM树的结合体，是浏览器实际用于布局和绘制的中间数据结构。它包含了页面上所有可见元素及其计算后的样式。

为什么要构建渲染树呢？DOM树可能包含一些不可见的元素，比如head标签，使用display:none;属性的元素等。所以在显示页面之前，还要额外地构建一棵只包含可见元素的渲染树。

渲染树：仅包含可见节点（排除 display: none、<head> 等）。

计算布局（Layout/Reflow）：

  • 计算每个节点的几何属性（位置、尺寸），即“盒模型”。
  • 首次布局称为 “回流”（Reflow），后续布局可能由 JavaScript 或 CSS 动画触发。

回流vs. 重绘

操作 触发条件 性能成本
回流 修改布局属性（如宽度、位置、字体大小） 高（需重新计算整个渲染树）
重绘 修改外观属性（如颜色、背景色） 中（不需重新布局）
合成 修改 transform、opacity 低（仅 GPU 合成）

回流

当操作引发了 DOM 树中几何尺寸的变化（改变元素的大小、位置、布局方式等），这时渲染树里有改动的节点和它影响的节点都要重新计算。这个过程就叫做重排，也称为回流。在改动发生时，要重新经历页面渲染的整个流程，所以开销是很大的。 以下操作都会导致页面重排：

  • 页面首次渲染；
  • 浏览器窗口大小发生变化；
  • 元素的内容发生变化；
  • 元素的尺寸或者位置发生变化；
  • 元素的字体大小发生变化；
  • 激活CSS伪类；
  • 查询某些属性或者调用某些方法；
  • 添加或者删除可见的DOM元素。

在触发重排时，由于浏览器渲染页面是基于流式布局的，所以当触发回流时，会导致周围的DOM元素重新排列，它的影响范围有两种：

  • 全局范围：从根节点开始，对整个渲染树进行重新布局；
  • 局部范围：对渲染树的某部分或者一个渲染对象进行重新布局。

重绘

当对 DOM 的修改导致了样式的变化、但未影响其几何属性（比如修改颜色、背景色）时，浏览器不需重新计算元素的几何属性、直接为该元素绘制新的样式（会跳过重排环节），这个过程叫做重绘。简单来说，重绘是由对元素绘制属性的修改引发的。 当我们修改元素绘制属性时，页面布局阶段不会执行，因为并没有引起几何位置的变换，所以就直接进入了绘制阶段，然后执行之后的一系列子阶段。相较于重排操作，重绘省去了布局和分层阶段，所以执行效率会比重排操作要高一些。

下面这些属性会导致回流：

  • color、background 相关属性：background-color、background-image 等；
  • outline 相关属性：outline-color、outline-width 、text-decoration；
  • border-radius、visibility、box-shadow。

注意： 当触发重排时，一定会触发重绘，但是重绘不一定会引发重排。

优化原则

避免频繁触发回流（如批量修改 DOM，使用 documentFragment）。使用 CSS transform 和 opacity 实现动画（跳过布局和绘制，直接合成）。

  • 在条件允许的情况下尽量使用 CSS3 动画，它可以调用 GPU 执行渲染。
  • 操作DOM时，尽量在低层级的DOM节点进行操作
  • 不要使用table布局， 一个小的改动可能会使整个table进行重新布局
  • 使用CSS的表达式
  • 不要频繁操作元素的样式，对于静态页面，可以修改类名，而不是样式。
  • 使用absolute或者fixed，使元素脱离文档流，这样他们发生变化就不会影响其他元素
  • 避免频繁操作DOM，可以创建一个文档片段documentFragment，在它上面应用所有DOM操作，最后再把它添加到文档中
  • 将元素先设置display: none，操作结束后再把它显示出来。因为在display属性为none的元素上进行的DOM操作不会引发回流和重绘。
  • 将DOM的多个读操作（或者写操作）放在一起，而不是读写操作穿插着写。这得益于浏览器的渲染队列机制。

阻塞渲染的资源：

  • JavaScript： 默认会阻塞 DOM 构建（除非用 async/defer）。 若脚本依赖 CSSOM（如访问 element.style），浏览器会等待 CSSOM 就绪。
  • CSS： 阻塞渲染树构建（浏览器会避免“无样式内容闪烁”）。 可通过媒体查询（media="print"）减少阻塞。

可以看到，DOM树中不可见的节点都没有包含到渲染树中。为了构建渲染树，浏览器上大致做了如下工作：

  1. 遍历DOM树中所有可见节点，并把这些节点加到布局中，而不可见的节点会被布局树忽略掉，如 head 标签下面的全部内容，再比如 p.p 这个元素，因为它的属性包含 dispaly:none，所以这个元素也没有被包含进渲染树中。
  2. 如果给元素设置了visibility: hidden属性，那这个元素会出现在渲染树中，因为具有这个样式的元素是需要占位的，只不过不需要显示出来。
  3. 这里在查找的过程中，出于效率的考虑，会从 CSSOM 树的叶子节点开始查找，对应在 CSS 选择器上也就是从选择器的最右侧向左查找。所以，不建议使用标签选择器和通配符选择器来定义元素样式。

除此之外，同一个 DOM 节点可能会匹配到多个 CSSOM 节点，而最终的效果由哪个 CSS 规则来确定，就是样式优先级的问题了。当一个 DOM 元素受到多条样式控制时，样式的优先级顺序如下：内联样式 > ID选择器 > 类选择器 > 标签选择器 > 通用选择器 > 继承样式 > 浏览器默认样式

绘制→ 合成

经过上面的步骤，就生成了一棵渲染树，这棵树就是展示页面的关键。到现在为止，已经有了需要渲染的所有节点之间的结构关系及其样式信息。下面就需要进行页面的布局。

通过计算渲染树上每个节点的样式，就能得出来每个元素所占空间的大小和位置。当有了所有元素的大小和位置后，就可以在浏览器的页面区域里去绘制元素的边框了。这个过程就是布局。这个过程中，浏览器对渲染树进行遍历，将元素间嵌套关系以盒模型的形式写入文档流：

  1. 绘制：将渲染树转换为屏幕上的像素（光栅化）。

在完成图层树的构建之后，渲染引擎会对图层树中的每个图层进行绘制，下面就来看看渲染引擎是怎么实现图层绘制的。渲染引擎在绘制图层时，会把一个图层的绘制分成很多绘制指令，然后把这些指令按照顺序组成一个待绘制的列表，绘制列表只是用来记录绘制顺序和绘制指令的列表，而绘制操作是由渲染引擎中的合成线程来完成的。当图层绘制列表准备好之后，主线程会把该绘制列表提交给合成线程。

  1. 分层与合成：浏览器将页面分为多个图层（如 will-change、opacity 会触发新图层）。合成线程将各图层合并后显示到屏幕（通过 GPU 加速）。

渲染引擎给页面分了很多图层，这些图层会按照一定顺序叠加在一起，就形成了最终的页面。这里，将页面分解成多个图层的操作就成为分层， 最后将这些图层合并到一层的操作就成为合成， 分层和合成通常是一起使用的。Chrome 引入了分层和合成的机制就是为了提升每帧的渲染效率。

至此，整个渲染流程就完成了，其过程总结如下：

  1. 将HTML内容构建成DOM树；
  2. 将CSS内容构建成CSSOM树；
  3. 将DOM 树和 CSSOM 树合成渲染树；
  4. 根据渲染树进行页面元素的布局；
  5. 对渲染树进行分层操作，并生成分层树；
  6. 为每个图层生成绘制列表，并提交到合成线程；
  7. 合成线程将图层分成不同的图块，并通过栅格化将图块转化为位图；
  8. 合成线程给浏览器进程发送绘制图块指令；
  9. 浏览器进程会生成页面，并显示在屏幕上。

React基础

React 是一个用于构建用户界面的 JavaScript 库，其核心开发思想是组件化和声明式编程。

React 将 UI 拆分为独立、可复用的组件，每个组件负责渲染自身的视图层，并通过 props 接收数据和回调函数进行通信，形成清晰的单向数据流。它采用虚拟 DOM（Virtual DOM）机制高效更新界面，开发者只需声明”UI 应该是什么状态”（声明式），而无需直接操作 DOM（命令式）。

基本原理

Fiber 树是虚拟 DOM 吗？不完全等同，但 Fiber 树是 React 对虚拟 DOM 概念的新一代实现。

传统虚拟 DOM（React 16 之前）： 是一个普通的 JavaScript 对象树，表示 UI 的层级结构（类似 { type: 'div', props: { ... } }）。 每次渲染都会生成新的虚拟 DOM 树，并通过 递归 Diff 算法 对比新旧树，计算最小 DOM 操作。

Fiber 树（React 16+）：

  • 增强版的虚拟 DOM，仍然是 JavaScript 对象，但结构更复杂，包含额外的调度信息（如优先级、副作用标记等）。
  • 不再是简单的树结构，而是链表结构（child、sibling、return 指针），支持可中断的异步渲染。
  • 每个 Fiber 节点不仅存储 UI 信息，还存储组件状态、副作用、更新队列等（如 memoizedState、updateQueue）。

Fiber 树是 React 对虚拟 DOM 的优化升级，使其不仅能描述 UI，还能管理渲染调度和状态更新。 传统虚拟 DOM 仅用于 Diff 计算，而 Fiber 树还承担了 任务调度 和 状态管理 的职责。

Fiber 树 vs. 浏览器 DOM

对比维度 Fiber 树（虚拟 DOM） 浏览器 DOM
本质 JavaScript 对象（内存中） 浏览器渲染引擎管理的节点树（内存 + 渲染管线）
更新方式 异步可中断（React 调度控制） 同步更新（直接操作，可能触发重排/重绘）
结构 链表（child、sibling、return） 树形结构（parentNode、childNodes）
存储内容 组件状态、props、副作用标记、更新队列等 纯 UI 节点（元素、属性、样式、事件监听等）
更新策略 增量更新（Diff + 批量提交） 直接修改（立即生效）
性能影响 避免直接操作 DOM，减少重排/重绘 频繁操作可能导致性能问题
调度能力 支持优先级调度（如高优先级交互先渲染） 无调度能力，依赖事件循环

声明式 UI 的单元：组件是状态（state/props）到 UI 的映射函数（UI = f(state)）。

  • 类组件：通过实例化 class 生成，生命周期方法与 Fiber 的 effectTag 和 flags 联动。
  • 函数组件：直接执行函数，依赖 Hooks 与 Fiber 的 memoizedState 链表绑定状态。

组件实例的载体：每个组件对应一个 Fiber 节点，Fiber 存储了组件的：

  • 状态（stateNode：类实例或 Hook 链表）
  • props（pendingProps/memoizedProps）
  • 副作用（updateQueue：effect 链表）

更新调度的最小单元：Fiber 的 tag 标记组件类型（如 FunctionComponent、ClassComponent），决定如何调和（Reconcile）。

组件更新的本质：

  • 触发更新：setState 或 props 变化时，创建更新（Update 对象）放入 Fiber 的 updateQueue。
  • 调和过程：React 对比新旧 Fiber 树，生成副作用列表（如 DOM 更新、effect 执行）。
  • 提交到 UI：根据副作用列表同步更新 DOM（Commit 阶段）。

为什么不能直接修改 State？

在 React 中，不能直接修改 State 的原因是 React 依赖于 State 的不可变性来优化组件的重新渲染。直接修改 State 会导致 React 无法检测到 State 的变化，从而无法触发组件的重新渲染。为了确保 React 能够正确跟踪 State 的变化，应该使用 setState 或 useState 的更新函数来更新 State。

  1. React 的渲染机制：React 通过对比前后两次渲染的 State 和 Props 来决定是否需要重新渲染组件。如果直接修改 State，React 无法检测到 State 的变化，因为 State 的引用没有改变，React 会认为 State 没有变化，从而不会触发重新渲染。

  2. 不可变性的重要性：React 的设计理念之一是保持数据的不可变性。不可变性意味着每次更新 State 时，都应该创建一个新的对象或数组，而不是直接修改现有的对象或数组。

如何正确更新 State：在 React 中，应该使用 setState 或 useState 的更新函数来更新 State。这些函数会确保 State 的更新是不可变的，并且会触发组件的重新渲染。

  1. 协调（Reconciliation）：

    • 可中断渲染：Fiber 的链表结构允许拆分渲染任务为小单元（时间切片）。

  2. 状态与副作用的统一管理：类组件的 this.state、函数组件的 Hook 状态，最终都存储在 Fiber 节点的 memoizedState 或 updateQueue 中。副作用（如 DOM 操作、useEffect）通过 Fiber 的 flags（如 Placement、Update、Deletion）标记并批量处理。

概念 本质 与 Fiber 的关系
组件开发 状态驱动 UI 的抽象单元 Fiber 是组件的运行时载体，管理状态、副作用和更新逻辑。
JSX 描述 UI 结构的语法糖 编译后的 Element 是 Fiber 节点的输入，决定 Fiber 的创建和更新策略。

关键结论：

  1. Fiber 是 React 的“引擎”：组件和 JSX 是开发者友好的抽象层，而 Fiber 是实现其动态更新的底层机制。
  2. 响应式编程模型：JSX 声明 UI，组件管理状态，Fiber 负责将状态变化高效同步到 UI。
  3. 性能优化的基础：Fiber 的可中断调度和优先级机制（如并发模式）使得 React 能处理复杂应用的高性能需求。

通常 React 运行时会有两个 Fiber 树，一个是根据当前最新组件状态构建出来的，另一个则是上一次构建出来的 Fiber 树，当然如果是首次渲染就没有上一次的 Fiber 树，这时就只有一个了。简单来说，render 过程就是 React 「对比旧 Fiber 树和新的 element」 然后「为新的 element 生成新 Fiber 树」的一个过程。

props 的本质

在 React Fiber 架构中，props 的本质是组件间数据流动的载体

每个 Fiber 节点对应一个 React 元素（如组件、DOM 节点等），其 pendingProps 和 memoizedProps 属性分别存储了：

  • **pendingProps**：即将生效的新 props（来自父组件的最新渲染结果）。
  • **memoizedProps**：当前已生效的旧 props（上一次渲染时使用的值）。

Props 在 Fiber 树更新中的生命周期：

  1. 调和（Reconciliation）阶段：React 比较新旧 Fiber 树，生成更新队列（Update Queue）。若父组件传递的 props 变化，子 Fiber 节点的 pendingProps 会被更新，标记为需要处理（effectTag）。
  2. 提交（Commit）阶段：将 pendingProps 应用到组件实例，更新为 memoizedProps。对于 DOM 节点，props 会转换为实际的 HTML 属性（如 className、onClick 等）。

组件

React的组件开发是一种基于模块化和声明式的UI构建范式，其核心本质是将复杂的用户界面拆分为独立、可复用的代码单元（组件），每个组件封装自身的结构（JSX）、样式（CSS）和行为（逻辑与状态）。

组件的本质是状态到UI的映射函数（UI = f(state)），它接收输入（props）并返回描述界面应该如何渲染的React元素。

React组件的设计哲学强调单向数据流和组件组合，通过将UI分解为层次化的组件树，开发者可以像搭积木一样构建应用，每个组件只需关注自身的职责范围，父组件通过props向下传递数据，子组件通过回调函数向上通信。这种模式实现了关注点分离，使得代码更易于维护、测试和复用。

组件开发在React中有两种表现形式：类组件（通过ES6 class定义，包含生命周期方法）和函数组件（通过普通函数定义，借助Hooks获得状态管理能力）。现代React更推崇函数组件+Hooks的组合，因其更符合函数式编程思想，消除了类组件中this绑定的复杂性，同时通过Hooks机制（如useState、useEffect）赋予了函数组件与类组件等同的能力。

组件化的核心价值在于可复用性（一次开发多处使用）、可维护性（隔离变化范围）和声明式编程（描述”UI应该是什么样子”而非具体操作DOM步骤）

Props【属性】

React 的 Props（属性）机制 本质上是一种单向数据流的信号与槽模型，它通过父组件向子组件传递数据（信号）和回调函数（槽），实现组件间的通信与协作。

可以看作React 的 Props 机制是观察者模式的变体：

  • 父组件：作为”发布者”，通过props下发数据和回调
  • 子组件：作为”订阅者”，接收数据并触发回调

  A[父组件] -- 传递props --> B[子组件]

信号（Signal）—— 数据传递

数据下行：父组件通过 props 向子组件传递数据（如字符串、数字、对象等），子组件接收后用于渲染或逻辑处理。

注意其：

  • 单向流动（父 → 子）
  • 只读性（子组件不能直接修改props）
  • 类型检查（可通过PropTypes或TypeScript约束）

槽（Slot）—— 回调通信

事件上行：父组件通过 props 传递回调函数，子组件调用该函数通知父组件（触发状态更新或行为）。

特点：子组件通过调用父组件的回调函数”传信”,实现子组件到父组件的间接通信,并且遵循React的单向数据流原则

其他应用

插槽（Children）：通过 props.children 传递子元素，实现内容分发

组件状态

React 的组件状态（State）是驱动组件动态交互和渲染的核心机制，它本质上是一个组件内部自维护的数据存储器，允许组件在生命周期中跟踪、更新并响应数据变化。

  • 状态是 React 组件的核心数据来源，决定了组件的渲染和行为。
  • 状态是可变的（不同于 props，它是只读的），用于实现动态交互。
  • 状态变化会触发组件重新渲染，使 UI 保持同步。

其状态的核心特性在于：

  • 动态性：状态是组件内部可变的私有数据，通过 useState（函数组件）或 this.state（类组件）管理，变化时触发组件重新渲染。
  • 响应式更新：状态更新自动触发 React 的协调（Reconciliation）过程，计算虚拟 DOM 差异并高效更新真实 DOM。
  • 局部性：状态默认仅对所属组件可见，需通过 props 或状态管理工具（如 Redux）实现跨组件共享。

React 早期（2015 年前）只有类组件，函数组件仅用于无状态 UI（Stateless Components）。2019 年 React 16.8 引入 Hooks，函数组件可以管理状态和副作用，几乎能替代类组件。

组件生命周期

React 组件的生命周期有三个不同的阶段：

  1. 初始渲染阶段：这是组件即将开始其生命之旅并进入 DOM 的阶段。
  2. 更新阶段：一旦组件被添加到 DOM，它只有在 prop 或状态发生变化时才可能更新和重新渲染。这些只发生在这个阶段。
  3. 卸载阶段：这是组件生命周期的最后阶段，组件被销毁并从 DOM 中删除。

生命周期方法

一些最重要的生命周期方法是：

  1. componentWillMount()– 在渲染之前执行，在客户端和服务器端都会执行。
  2. componentDidMount() – 仅在第一次渲染后在客户端执行。
  3. componentWillReceiveProps*() – 当从父类接收到 props 并且在调用另一个渲染器之前调用。
  4. shouldComponentUpdate() – 根据特定条件返回 true 或 false。如果你希望更新组件，请返回true 否则返回 false。默认情况下，它返回 false。
  5. componentWillUpdate()*– 在 DOM 中进行渲染之前调用。
  6. componentDidUpdate() – 在渲染发生后立即调用。
  7. componentWillUnmount() – 从 DOM 卸载组件后调用。用于清理内存空间。

React Hooks

React Hooks 是 React 16.8 引入的一项革命性特性，它允许你在函数组件中使用状态(state)和其他 React 特性，而无需编写类组件。下面我将详细介绍每一个主要的 Hook 及其用法。

基础 Hooks

useState

useState 是最基本的 Hook，用于在函数组件中添加局部状态。

特点：

返回一个数组，第一个元素是当前状态值，第二个是更新状态的函数。可以多次调用 useState 来声明多个状态变量。状态更新函数 (setCount) 不会自动合并对象，而是替换

useEffect

useEffect 用于处理副作用操作（数据获取、订阅、手动修改 DOM 等）。

特点：

默认情况下，effect 在每次渲染后都会执行。可以通过返回一个函数来指定如何”清除” effect（如取消订阅）。可以通过第二个参数传递依赖数组来优化性能（只在依赖变化时执行）

useContext

useContext 用于在函数组件中访问 React 的 Context。

特点：接收一个 context 对象（React.createContext 的返回值）并返回该 context 的当前值。当前的 context 值由上层组件中距离当前组件最近的 <MyContext.Provider> 的 value prop 决定

额外的 Hooks

useReducer

useReducer 是 useState 的替代方案，适用于复杂 state 逻辑。

特点：适合 state 逻辑较复杂或包含多个子值的场景。可以配合 useContext 实现深层组件通信

useCallback

useCallback 返回一个记忆化的回调函数，只有在依赖项变化时才会更新。

特点：用于性能优化，避免不必要的重新渲染。相当于 useMemo(() => fn, deps) 的语法糖

useMemo

useMemo 返回一个记忆化的值，只有在依赖项变化时才会重新计算。

特点：用于性能优化，避免每次渲染时都进行高开销计算。传入的函数会在渲染期间执行，不要在里面执行副作用操作

useRef

useRef 返回一个可变的 ref 对象，其 .current 属性被初始化为传入的参数。

特点：返回的 ref 对象在组件的整个生命周期内保持不变，可以保存任何可变值，类似于类组件中的实例字段。变更 .current 属性不会引发组件重新渲染

useImperativeHandle

useImperativeHandle 可以自定义暴露给父组件的实例值。

特点：应当与 forwardRef 一起使用，用于限制子组件暴露给父组件的内容

useLayoutEffect

useLayoutEffect 与 useEffect 相同，但它会在所有的 DOM 变更之后同步调用 effect。

使用场景：需要读取 DOM 布局并同步触发重渲染时，会阻塞浏览器绘制，尽可能使用 useEffect 以避免阻塞视觉更新

useDebugValue

useDebugValue 可用于在 React 开发者工具中显示自定义 hook 的标签。

特点：主要用于自定义 Hook 的调试。可以接受格式化函数作为第二个参数，用于延迟格式化

自定义 Hook

自定义 Hook 是一个 JavaScript 函数，其名称以 “use” 开头，可以调用其他 Hook。

特点：可以在多个组件之间重用状态逻辑。每次调用 Hook 都会获得完全独立的 state。命名必须以 “use” 开头

Hook 使用规则

  • 只在最顶层使用 Hook：不要在循环、条件或嵌套函数中调用 Hook。确保 Hook 在每次渲染时都按照同样的顺序被调用
  • 只在 React 函数中调用 Hook：在 React 的函数组件中调用 Hook。在自定义 Hook 中调用其他 Hook

从自变量/因变量的角度理解 React Hook：

  • **useState**：定义组件内部的自变量
  • Props：接收外部传入的自变量
  • **useMemo**：显式声明因变量及其依赖的自变量
  • **useEffect**：处理由自变量变化触发的副作用

NextJs基础

首先需要明确的是：

Next.js 是一个基于 React 的用于构建全栈 Web 应用程序的生产框架，而RSC 是 Next.js v13 的实现基础

RSC 是 React 设计的一种新架构，这种方法旨在利用服务器和客户端环境的优势，实现用户体验、易于维护和高性能的三角平衡。使用服务端组件有很多好处：

  • 数据获取：通常服务端环境（网络、性能等）更好，离数据源更近，在服务端获取数据会更快。通过减少数据加载时间以及客户端发出的请求数量来提高性能。
  • 安全：在服务端保留敏感数据和逻辑，不用担心暴露给客户端。
  • 缓存：服务端渲染的结果可以在后续的请求中复用，提高性能。
  • Bundle 大小：服务端组件的代码不会打包到 bundle 中，减少了 bundle 包的大小。
  • 初始页面加载和 FCP：服务端渲染生成 HTML，快速展示 UI。
  • Streaming：服务端组件可以将渲染工作拆分为 chunks，并在准备就绪时将它们流式传输到客户端。用户可以更早看到页面的部分内容，而不必等待整个页面渲染完毕。

动态路由

同时也可以看到诸如：[slug].js 用括号括起来的文件？这些是nextjs的动态路由

动态路由是一种路由模式，允许 URL 中的某些部分是变量，而不是固定的路径。例如 /users/123、/posts/hello-world 中的 123 和 hello-world 就是动态部分，同一个路由可以匹配不同的实际路径。

动态路由的概念存在于 Next.js 的所有版本中，只是在不同路由系统下的实现语法不同：

  • Pages Router 时代：通过 [param].js 文件名实现动态路由
  • App Router 时代：通过 [param]/page.js 文件结构实现动态路由

动态路由的核心价值在于：

  1. 灵活性：支持任意 URL 结构，适应不同业务需求。
  2. SEO 友好：结构化 URL 更容易被搜索引擎抓取。
  3. 减少重复代码：通过参数动态加载内容，避免重复文件。
  4. RESTful 风格：模拟 API 路由，前后端交互更直观。
  5. 嵌套路由支持：实现复杂的页面层级结构。

动态路由是现代 Web 开发的核心技术之一，广泛应用于电商、博客、社交平台等需要动态内容的场景。

App Router

上面提到的App Router是Next.js 13+引入的基于文件夹的路由系统，其是 Next.js 中实现文件系统路由的具体方案之一。

App Router 不是替代文件系统路由，而是实现文件系统路由的新方案。它保留了“文件即路由”的核心理念，但引入了更强大的布局能力、Server Components、流式渲染等现代特性，是 Next.js 推荐的新路由系统。Pages Router 仍被支持，但新项目建议使用 App Router。

与Pages Router相比，App Router的主要区别：

  1. 服务器组件: App Router默认使用React服务器组件，而Pages Router使用客户端组件
  2. 布局系统: App Router提供了更强大的嵌套布局系统，Pages Router需要使用自定义_app.js
  3. 数据获取: App Router允许在组件中直接使用async/await，Pages Router使用getServerSideProps等函数
  4. 文件约定: App Router使用page.js表示路由，Pages Router使用index.js或命名文件
  5. 路由分组: App Router支持路由组、平行路由和拦截路由等高级功能

服务端组件和客户端组件

App Router不标识就默认是Server组件，客户端组件使用use client，服务端组件use server。

use client（客户端组件）：标记组件在客户端运行，具有交互能力，可以使用 useState、useEffect 等 React 特性。

use server（服务端动作）：标记函数在服务端执行，用于 Server Actions（表单提交、数据变更等操作）。

在 Next.js 中，组件默认就是服务端组件。如果在文件顶部添加一个 “use client” 声明，则是声明为客户端组件。

使用服务端组件的好处：

  • 数据获取：通常服务端环境（网络、性能等）更好，离数据源更近，在服务端获取数据会更快。通过减少数据加载时间以及客户端发出的请求数量来提高性能。
  • 安全：在服务端保留敏感数据和逻辑，不用担心暴露给客户端。
  • 缓存：服务端渲染的结果可以在后续的请求中复用，提高性能。
  • Bundle 大小：服务端组件的代码不会打包到 bundle 中，减少了 bundle 包的大小。
  • 初始页面加载和 FCP：服务端渲染生成 HTML，快速展示 UI。
  • Streaming：服务端组件可以将渲染工作拆分为 chunks，并在准备就绪时将它们流式传输到客户端。用户可以更早看到页面的部分内容，而不必等待整个页面渲染完毕。

使用客户端组件的好处：

  • 交互性：客户端组件可以使用 state、effects 和事件监听器，意味着用户可以与之交互。
  • 浏览器 API：客户端组件可以使用浏览器 API 如地理位置、localStorage 等。

同时当服务器组件（默认）嵌套客户端组件（use client）时，所有组件都在服务器生成 HTML

  1. 客户端组件的初始内容会出现在服务器返回的 HTML 文档中，用户可以立即看到

  2. 客户端组件的 JavaScript 逻辑被单独打包，在浏览器中加载后通过”水合”使组件可交互

  3. 这种设计实现了最佳体验：

    首屏速度（内容立即可见）

    SEO（内容在 HTML 中）

    交互性（水合后获得完整功能）

这就是 Next.js App Router 的核心设计哲学：服务器优先，客户端增强。所有组件先服务器渲染确保内容可见，再通过水合获得交互能力。

服务端渲染（SSR）

首先需要明白：组件的渲染模式和页面的渲染策略有什么区别?

组件渲染模式（组件层），关注的是每个组件在哪个环境运行

  • Server Components：组件在服务器端执行，不发送 JavaScript 到客户端，不能使用 useState、useEffect 等交互特性
  • Client Components：组件在客户端执行，可以交互，需要发送 JavaScript 到浏览器

特点：这是组件级别的配置，同一个页面可以混合使用两种组件模式。

页面渲染策略（页面层）关注的是整个页面在什么时候生成 HTML

  • SSG（静态站点生成）：构建时生成 HTML，每次请求返回相同内容
  • SSR（服务端渲染）：请求时生成 HTML，每次请求动态渲染
  • ISR（增量静态再生）：构建时生成，按时间间隔或按需重新生成
  • CSR（客户端渲染）：返回空壳，浏览器端渲染内容

特点：这是页面级别的策略，决定页面的缓存行为和更新频率。

在做项目时，我时常听到跨境电商或者外贸做独立站经常要求谷歌搜索引擎优化【SEO 要求的网站（电商、博客、企业官网）】，而传统React 默认是客户端渲染，HTML 在浏览器中生成，首屏加载慢且 SEO 差。

Next.js 可以在服务器端生成 HTML，直接返回完整页面，提升首屏速度和搜索引擎友好度。所以那他做独立站再好不过，当然这里还需要更多的了解：

  4. 配合错误边界，优雅处理异常

SSR 的局限性与注意事项

  • 性能开销：每次请求都需要渲染，增加服务器负载，响应时间取决于数据获取速度，高并发场景需要良好的缓存策略
  • 部署限制：需要 Node.js 服务器环境，不能部署为纯静态文件（如 CDN），需要处理服务器资源

Middleware 中间件

  • A/B测试：根据用户特征分发到不同版本
  • 地理路由：根据访问者地理位置重定向到对应语言版本
  • 日志记录：记录请求信息用于分析
  • 维护模式：统一返回维护页面
