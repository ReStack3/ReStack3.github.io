Linux运维

系统运维基础

作为独立全栈开发者，除了掌握一流的开发技能外。我们还需要掌握一些基本的系统运维知识。毕竟单兵作战没人可以给你擦屁股。笔者这里简单总结了些个人觉得的运维重点，仅供大家参考。

从代码构建完成到上线，总体步骤概览：

  1. 环境准备：在云服务器上安装代码运行所需的环境
  2. 代码传输：将本地代码放到服务器上
  3. 配置运行：让代码在后台持续运行
  4. 暴露服务：配置Nginx和域名，让外界能访问
  5. 基础安全：防止被黑的基础配置
  6. 监控告警：知道什么时候出问题

这里笔者觉得环境搭建，日常操作，监控恢复，安全服务这四个方面。

环境搭建

在Linux运维中，环境搭建指的就是在裸机或云服务器上，从零开始安装、配置、优化一套能让应用程序或服务跑起来的软件生态系统。简单说就是：把一台空Linux机器变成能跑业务代码的机器。

这里在基础设施即代码 - Hermes中我们代替说过了在云服务器上如何利用Ansible 和 Terraform自动化安装配置我们需要的代码运行环境。但这里给出一些常见的需要配置服务：

环境类别 包含内容 典型用途 例子
基础系统环境 操作系统初始化、内核参数、时间同步、安全基线 任何服务器的基础 设置ulimit、关闭SELinux、配置ntp、创建普通用户
运行时环境 编程语言解释器/编译器、运行时、包管理器 运行特定语言开发的程序 Node.js、Python、OpenJDK、Go、PHP-FPM
Web服务环境 Web服务器、网关、代理 处理HTTP请求、分发流量 Nginx、Apache、Caddy、Traefik、LVS、HAProxy
数据存储环境 数据库、缓存、消息队列 数据持久化、缓存加速、异步解耦 MySQL、PostgreSQL、Redis、MongoDB、RabbitMQ、Kafka
应用容器环境 容器运行时、编排工具 隔离应用、标准化交付 Docker、containerd、Kubernetes（K8s）、Podman
监控与观测环境 指标收集、日志聚合、链路追踪 看清系统运行状态 Prometheus、Grafana、ELK/EFK（Elasticsearch、Filebeat、Kibana）、Loki、Jaeger
CI/CD环境 代码仓库、自动化构建与部署工具 自动化测试、打包、发布 GitLab（CI）、Jenkins、Drone、Argo CD
网络安全环境 防火墙、VPN、网关、证书管理 隔离、加密、访问控制 iptables/nftables、OpenVPN、WireGuard、Certbot（Let‘s Encrypt）

总的来说：环境搭建就是安装并配置好操作系统、运行时、中间件、数据库、监控等所有软件，让业务代码能够稳定运行并对外提供服务。

日常操作

独立开发者做 Linux 运维，和公司运维不一样——公司是管几百台服务器，你是 管自己的项目服务器。
所以 Linux 运维的核心不在“装系统”，而是让维护的服务器“活着、正常、安全”所必须做的一系列常规检查和维护动作。比如：

类别 操作 核心目的 频率 一句话命令/方法
1. 连接与登录 SSH登录服务器 进入操作界面 每天 ssh user@你的IP
2. 状态检查 查看系统负载、CPU、内存 判断服务器“累不累” 每天 top 或 htop
3. 磁盘检查 查看磁盘使用率 别让磁盘写满 每天 df -h
4. 日志查看 查看错误日志 程序出问题找原因 出问题时 tail -f /var/log/xxx
5. 服务管理 启动/停止/重启/查看状态 控制你的应用 经常 systemctl status/start/stop/restart 服务名
6. 进程管理 查看/杀死进程 处理卡死或占CPU高的程序 偶尔 `ps aux
7. 网络检查 查看端口监听、连通性 确认服务能否被访问 出问题时 netstat -tlnp、curl localhost:8080
8. 文件传输 上传/下载文件 部署代码、备份数据 经常 scp、rsync
9. 安全更新 更新系统补丁 防止被黑 每周 apt update && apt upgrade -y（Ubuntu/Debian）
10. 备份操作 备份数据库/配置文件 防删库跑路 定期 mysqldump、tar czf
11. 定时任务 查看/编辑crontab 自动化重复操作 偶尔 crontab -l、crontab -e
12. 防火墙操作 开放/查看端口 控制谁可以访问 偶尔 ufw allow 443、iptables -L

监控恢复

监控恢复往往是独立开发者最容易忽视、但出事之后最痛苦的环节。

监控恢复 = 自动发现服务器/程序出问题了 + 想办法让它自己好起来（或至少通知你来修）

虽然之前在在监控与日志已经说明了Prometheus 、Grafana 、ELK 但是在这里仍然说明一下：

故障排查与性能调优

  • 排查思维：从现象倒推 → 日志分析 → 资源监控 → 定位瓶颈
  • 常用工具：strace, tcpdump, perf, lsof, systemd-analyze
  • 常见问题：CPU飙升、内存泄漏、磁盘满、网络延迟、句柄泄露
监控对象 为什么重要 典型异常 后果
服务存活 你的程序在不在跑 进程挂了、端口不响应 用户访问直接报错
磁盘使用率 写不了日志/数据库 >85% 预警，>95% 崩溃 数据库无法写入、用户下单失败
CPU/内存 服务器累不累 持续 >80% 响应变慢、卡死、OOM被杀
HTTP/API 响应 用户体感好不好 5xx错误、响应>3秒 用户流失
证书过期 HTTPS还能不能用 SSL证书到期前7天 浏览器显示“不安全”，用户不敢进

而备份与恢复

  • 备份策略：全量、增量、差异备份
  • 工具：rsync、mysqldump、xtrabackup、快照技术
  • 演练：定期验证恢复流程，这是很多运维容易忽略但极其重要的环节

恢复分为三个层次：

层次 做法 适用场景 应对方法
自动恢复 程序挂了自动重启 进程崩溃、内存泄漏 用 systemd 或 Docker 的 restart: always
半自动恢复 监控触发一个脚本去修 磁盘清理、重启服务 写个脚本 + cron / webhook
手动恢复 收到告警，你 SSH 上去修 数据库损坏、配置错误 最现实，大部分情况靠这个

安全服务

防止别人拿到服务器控制权、偷你的数据、搞垮你的服务。

常见的安全配置：

层级 配置项 核心作用

7. 应用安全 非root运行、环境变量隔离 防止应用被拿下后提权
8. 备份 定期自动备份 防删库、防勒索

监控与日志

笔者有个好朋友hermes，是个独立开发者，一直过着“小而美”的惬意日子。他开发的 Next.js 应用跑在一台 2 核 2G 的服务器上，用户不多，流量平缓，日子倒也安稳。

那时候，他的运维方式很“原始”也很直接——出问题了，就 SSH 登上服务器，敲几行命令：

偶尔再用浏览器 F12 看看接口耗时，感觉“够用了”。毕竟，用户少，问题少，手动查一查总能找到原因。

直到有一天，他的应用突然“爆了”——不知道哪个博主推荐了一下，流量瞬间翻了 10 倍。他先是窃喜，然后很快笑不出来了：

  • 用户反馈页面打不开、接口超时
  • 他自己也一脸懵：到底是 CPU 不够？还是数据库连接池爆了？还是哪个 API 被疯狂刷？
  • 登上服务器，top 一看，CPU 飘红，但不知道是哪个请求导致的
  • 翻日志，几千行报错堆在一起，根本看不清故障从什么时候开始的
  • 更崩溃的是，问题只在高峰期出现，等他一顿操作猛如虎登上服务器，流量已经回落了，故障现场“完美消失”

过去那套“人肉运维”的方式，在面对突发流量时，暴露出三个致命短板：

  1. 被动响应，后知后觉 ：没有告警，永远都是用户先发现故障，他才知道出事了。等他登录服务器，可能已经过去了十几分钟，甚至错过了故障现场。

  2. 信息孤岛，无法关联 ：CPU 飙高时，不知道是哪个接口导致的；日志报错时，不知道当时的系统指标长什么样。指标、日志、调用链是割裂的，全靠人脑“脑补”关联。

  3. 手动操作，效率低下 ：每个问题都要手动敲命令、翻日志、查资料，故障处理时间动辄半小时以上。对于独立开发者来说，这段时间用户流失了多少，他根本不敢算。

当我得知他现在最想要的其实是：

  • 能 24 小时自动盯着系统，异常时主动告诉他，而不是等用户投诉
  • 能在一个界面上同时看到 CPU、请求量、响应时间、错误日志，而不是到处切窗口
  • 能回溯故障发生那一刻的完整现场，而不是靠“猜”和“回忆”

听着他的需求，我果断推荐了 Prometheus + Grafana + ELK 。

  • Prometheus 负责 7×24 小时采集指标，主动告警
  • Grafana 把散落的指标变成直观的仪表盘
  • ELK 把海量日志集中管理，让故障可追溯、可分析

用完他对我说：“早知道有这套东西，我就不至于这两天失眠了。”

Prometheus + Grafana

Prometheus

Prometheus 是一个开源的系统监控和告警工具包，最初由 SoundCloud 开发，现为 CNCF（云原生计算基金会）的毕业项目，是云原生监控的事实标准。

Getting started | Prometheus

特性 说明
多维数据模型 通过指标名称和键值对标签（如 method="GET"、status="500"）来标识时间序列
PromQL 查询语言 强大灵活的查询语言，支持聚合、运算、预测等复杂分析
拉取模式 主动从目标系统（ exporters ）拉取指标，而非被动接收
独立运行 不依赖外部存储，自带时序数据库
服务发现 自动发现监控目标（支持 Kubernetes、Consul、DNS 等）
告警管理 通过 Alertmanager 实现告警分组、静默、路由

其通过HTTP协议周期性抓取被监控组件的状态。输出被监控组件信息的HTTP接口称为exporter。常用组件大部分都有exporter可以直接使用，比如haproxy,nginx，Mysql,Linux系统信息（包括磁盘、内存、CPU、网络等待）。

虽然 Prometheus 提供的 Web UI 也可以很好的查看不同指标的视图，但是这个功能非常简单，只适合用来调试。要实现一个强大的监控系统，还需要一个能定制展示不同指标的面板，能支持不同类型的展现方式（曲线图、饼状图、热点图、TopN 等），这就是仪表盘（Dashboard）功能。

因此 Prometheus 开发了一套仪表盘系统 PromDash，不过很快这套系统就被废弃了，官方开始推荐使用 Grafana 来对 Prometheus 的指标数据进行可视化，这不仅是因为 Grafana 的功能非常强大，而且它和 Prometheus 可以完美的无缝融合。

Grafana

Grafana 是一个开源的可视化分析平台，支持连接多种数据源，将监控数据以仪表盘、图表的形式直观展示。

Grafana OSS 和 Enterprise | Grafana 文档 - Grafana 文档

特性 说明
多数据源支持 Prometheus、Elasticsearch、MySQL、PostgreSQL、Loki、CloudWatch 等 50+ 种
丰富的面板类型 时间序列图、柱状图、统计表、热力图、地图、日志面板等
交互式仪表盘 拖拽式构建、变量筛选、时间范围选择、钻取分析
告警可视化 支持在图表上直接配置告警规则
用户与权限 支持团队协作、角色权限控制
注释与协作 在图表上标注事件（如部署、故障），支持团队评论

ELK

Elastic Stack: (ELK) Elasticsearch, Kibana & Logstash | Elastic

ELK 是 Elasticsearch、Logstash、Kibana 三个开源项目的首字母缩写，合起来构成一套完整的日志集中管理解决方案，用于解决分布式系统中日志分散、难以检索、无法关联分析的问题。

在没有 ELK 之前，查看日志是这样的：

当有 10 台、100 台服务器时，这种“人肉登录翻日志”的方式完全不可行。ELK 把所有服务器的日志集中到一个地方，让你能在一个界面上搜索、分析、可视化所有日志。

Elasticsearch（存储与索引）

Elasticsearch 是一个基于 Lucene 的分布式搜索和分析引擎，是 ELK 的核心存储层。

特性 说明
分布式 自动将数据分片存储在多台服务器，支持水平扩展
实时搜索 数据写入后近乎实时可被搜索（约1秒延迟）
全文检索 支持复杂的文本搜索、模糊匹配、聚合分析
Schema Free 无需预定义表结构，自动识别字段类型
RESTful API 通过 HTTP API 进行所有操作

Logstash（采集与处理）

Logstash 是一个服务器端数据处理管道，负责从各种数据源采集日志，进行解析、转换、过滤，然后发送到 Elasticsearch 或其他存储。

特性 说明
多源输入 支持文件、TCP/UDP、Syslog、Kafka、数据库等 200+ 种输入插件
实时处理 边采集边处理，毫秒级延迟
灵活过滤 通过 Grok、正则、JSON、KV 等方式解析非结构化日志
无代理架构 只需在服务器上运行 Logstash 进程，无需在被采集应用上安装 Agent
可靠传输 支持持久化队列，防止数据丢失

Kibana（搜索与可视化）

Kibana 是 Elasticsearch 的可视化前端，提供 Web 界面让你搜索、分析、可视化 Elasticsearch 中的数据。

特性 说明
数据探索 交互式搜索、过滤、查看原始日志
可视化 柱状图、折线图、饼图、热力图、地图等多种图表
仪表盘 将多个可视化图表组合成一个页面
实时流 实时滚动显示最新日志
机器学习 自动检测异常模式（需付费功能）
告警 基于查询结果的告警通知
