frida-server 是 Frida 工具链的核心组件，主要用于在 目标设备（通常是 Android 或 Linux） 上运行，以便与 Frida 客户端（如 frida-tools、frida-python）通信。

frida-server 的核心作用

  • Frida 的核心功能（如动态 Hook、内存读写、调用函数）需要直接与目标进程交互。**frida-server 作为守护进程**，运行在目标设备上，负责执行 Frida 客户端的指令（如注入 JavaScript、修改内存）。

  • 普通应用无法直接 ptrace 其他进程（Android 的 ptrace_scope 限制）。**frida-server 以 root 或高权限运行**，可以绕过这些限制，实现跨进程调试和注入。

  • 默认情况下，Frida 通过 TCP 与客户端通信（如 frida -H 192.168.x.x）。frida-server 监听端口（默认 27042），允许远程设备（如 PC）通过 USB 或网络连接。

D-Bus

D-Bus 是 Linux 桌面环境的 标准 IPC 机制，允许不同进程（甚至是不同语言编写的工具）通过统一的接口通信。我们知道最初Linux是不支持桌面环境的。

D-Bus 最初是为 GNOME/KDE 等桌面环境 设计的，核心目标是解决桌面组件（如窗口管理器、音量控制、网络设置）之间的通信需求。

典型用例：

  • 用户点击音量按钮 → 通过 D-Bus 通知音频服务调整音量。
  • 文件管理器需要挂载磁盘 → 通过 D-Bus 调用 udisks2 服务。

与普通 Linux IPC 的对比

特性 D-Bus（桌面环境） 普通 Linux IPC
主要用途 桌面组件通信、用户交互 系统级进程通信（如 daemon、高性能服务）
通信模式 基于消息（异步/同步） 多样化（管道、消息队列、共享内存、Socket）
抽象层级 高级（对象/接口/方法） 低级（字节流、信号、文件描述符）
服务发现 支持（通过总线名称） 需手动实现（如配置文件或固定路径）
性能 较高延迟（适合低频操作） 极高（适合高频数据传输）
典型用户 GUI 应用、系统服务（如 NetworkManager） 后台服务、嵌入式系统、内核模块

Frida 通过 D-Bus 暴露核心功能（如 HostSession），使得第三方工具（如 GUI 调试器、自动化脚本）无需依赖 Frida 的私有协议，直接通过 D-Bus 调用功能。

在 Linux 桌面环境中，许多系统服务（如网络、硬件管理）本身通过 D-Bus 暴露接口。Frida 使用 D-Bus 可以更方便地与这些服务交互（例如通过脚本监控网络状态）

  • 例如：一个 Python 脚本可以通过 dbus-python 库直接调用 Frida 的 attach() 方法。

两种常见使用模式

我们知道Frida使用有两种模式：

其中**spawn() + resume()** 是 注入模式 的核心操作，适合控制进程从启动开始的行为。而附加模式 直接操作运行中的进程，无需 spawn/resume。两者底层均依赖 ptrace，但应用场景和权限要求不同。

操作 注入模式（Spawn） 附加模式（Attach）
进程状态 从零启动，初始挂起 附加到已运行的进程
API 调用 需调用 spawn() + resume() 直接调用 attach()
适用场景 需控制进程从启动开始的行为 动态修改已运行进程
权限要求 需能启动新进程（可能需 root） 需 ptrace 权限（可能需 root）

Q1: 为什么需要 spawn() 后挂起？

挂起进程后，Frida 可以在主线程执行前注入脚本，确保 Hook 所有关键函数（如 JNI_OnLoad）。

Q2: resume() 后还能继续注入吗？

可以，但动态注入可能错过早期代码（如构造函数）。推荐在 resume() 前完成核心 Hook。

Q3: 附加模式是否需要 resume()？

不需要，附加模式不会暂停目标进程（除非手动调用 Process.suspend()）。

总结

attach模式

attach到已经存在的进程，核心原理是ptrace修改进程内存，如果进程处于调试状态（traceid不等于0），则attach失败。

frida 的进程注入是通过 ptrace 实现的，注入之后会在远端进程分配一段内存将 agent 拷贝过去并在目标进程中执行代码，执行完成后会 detach 目标进程。

这也是为什么在 frida 先连接上目标进程后还可以用 gdb 等调试器连接，而先 gdb 连接进程后 frida 就无法再次连上的原因。

frida-agent 注入到目标进程并启动后会启动一个新进程与 host 进行通信，从而 host 可以给目标进行发送命令，比如执行代码，激活/关闭 hook，同时也能接收到目标进程的执行返回以及异步事件信息等。

spawn模式

启动一个新的进程并挂起，在启动的同时注入frida代码，适用于在进程启动前的一些hook，如hook RegisterNative等，注入完成后调用resume恢复进程。

frida-helper

在前面是spawn和attach两种模式中，都提到了frida-agant和frida-helper这些到底是什么呢？

frida-agant 在大多数时候充当了 app 内部的服务端。在用户向应用传递新脚本的时候，通过 RPC 服务与 frida-agant 通信，由它来负责注入 hook 。

frida-helper 是 frida-server 的辅助模块，专门处理 跨进程内存操作、Shellcode 执行、动态链接器交互 等脏活累活。

这三者关系可以用「医院手术团队」 的比喻来理解 Frida 的各个组件：

组件 比喻角色 功能
frida-server 主刀医生 在目标设备（如手机）上运行，拥有最高权限，负责调度所有操作（如开刀、注射）。
frida-agent 手术助手 注入到目标 App 内部，直接操作“病人器官”（Hook 函数、修改内存）。必须在目标 App 内部运行，否则无法直接修改其内存。
frida-helper 麻醉师/护士 辅助 frida-server，处理低级任务（如内存扫描、线程管理）。分担底层任务，让 frida-agent 更轻量（类似护士让医生专注关键步骤）。

在前面【InlineHook技术浅析】文章中，我们了解到 inlineHook 开发的几个关键点大抵如下：

  1. 动态替换需要 Hook 的指令片段为一段经过设计的跳板指令，即 trampoline ，目标为我们设计好的一段 shellCode
  2. 在内存中设计并生成一段 shellCode ，这是我们的可控 shellCode ，在该 shellCode 中需要实现 Hook 的功能函数（即打印/替换-参数/结果）

总结

各跳板作用

  • 一级跳板（on_enter_trampoline）：保存原始上下文（寄存器、标志位），跳转到通用处理逻辑。
  • 二级跳板（enter_thunk）：处理架构相关的上下文切换（如 ARM 的 LR 寄存器备份）。
  • 三级跳板（_gum_function_context_begin_invocation）：调用用户注册的 on_enter 回调，并动态决定下一步执行路径（原始函数或替换函数）。
  • 四级跳板（on_leave_trampoline）：恢复上下文，处理 on_leave 回调。

Stalker

可以实现指定线程中所有函数、所有基本块、甚至所有指令的跟踪。

一般而言调试器实现函数或者指令跟踪是通过断点，但是断点有几个问题。一是断点容易被反调试检测到，软件断点自不必说，会在原指令中插入断点指令，如果函数本身有完整性校验的话会检测出异常，而硬件断点本身也很容易被检测或者破坏掉；断点的另一个问题是性能，代码触发断点后会先中断到内核态，然后再返回到用户态(调试器)执行跟踪回调，处理完后再返回内核态，然后再回到用户态继续执行，这来来回回的黄花菜都凉了。

原理

因此，Stalker 不是使用断点，而是基于动态修改代码的方式实现。其基本思想很简单，在线程即将执行下一条指令前，先将目标指令拷贝一份到新建的内存中，然后在新的内存中对代码进行插桩，如下图所示:

这其中使用到了代码动态重编译的方法，好处是原本的代码没有被修改，因此即便代码有完整性校验也不影响，另外由于执行过程都在用户态，省去了多次中断内核切换，性能损耗也达到了可以接受的水平。由于代码的位置发生了改变，如前文 Interceptor 一样，同样要对代码进行重定位的修复。

Stalker 中可以任意单位基本进行跟踪，越细粒度的跟踪性能损耗越高。比如在流量分析时可以只针对 SSL_read、SSL_write 进行跟踪获取流量明文；又比如在 Fuzzing 中经常以基本块为单位进行覆盖率反馈，此时可以以块为单位进行跟踪，只对 blx、br、jmp、call 等跳转指令进行插桩；或者针对某些自定义的加密算法，可以以指令级别进行跟踪，通过动态运行的路径记录来辅助逆向分析还原加密流程.

此外 Stalker 中还针对动态编译进行了大量的性能优化，进一步减少运行时的额外开销。由于动态重编译与系统架构关系较大，代码中需要对当前平台的指令集进行准确的归类和处理，因此当前 Stalker 只支持常用的 ARM64、X86 和 IA32 架构，而且对于动态自修改的代码支持也不完善，但即便如此也足以满足大部分日常的需求了。

从 Dalvik 到 ART 的演进

ArtMethod 是 Android Runtime (ART) 的核心数据结构之一，它的设计源于对 Dalvik 虚拟机 的优化和改进。要理解 ArtMethod 的由来，需要回顾 Android 运行时的历史：

运行时 执行方式 方法表示 问题
Dalvik 解释执行 + JIT（后期支持） Method 结构体 1. 解释执行慢 2. JIT 编译开销大
ART AOT 编译 + JIT（优化补充） ArtMethod 结构体 优化执行效率，减少运行时开销
  • Dalvik 的 Method 结构:在 Dalvik 中，Java 方法通过 Method 结构体表示，主要存储字节码信息，执行时依赖解释器逐条解释字节码，性能较低。
  • ART 的改进:ART 在 Android 5.0（Lollipop）引入，核心变化是 ​​AOT（Ahead-Of-Time）编译​​，即在安装时就将 Java 字节码编译成机器码。为了高效管理编译后的方法，ART 设计了 ArtMethod。

针对Method结构体，不得不谈谈xposed，还有第一代指令抽取加固方式。实际就是找到Method 中的 insns指令码字段（加固时是在dex文件，hook则直接获取函数指针得到该指令码字段），然后运行时替换。 而ArtMethod，是ART下的产物。其结构教于Method发生了变化，当dex2oat的时候，还会有多种方法内联优化。而方法内联会改变原本的方法分布和调用流程，对加固、热修复、hook，实际上都有一定的影响。

ArtMethod 的诞生主要为了解决以下问题：

  1. 快速方法调用
    • Dalvik 的方法调用需要经过解释器，而 ART 希望直接跳转到编译后的机器码。
    • ArtMethod 存储 入口地址（entry_point），使得调用可以直接定位到机器码。
  2. 支持 AOT 和 JIT: AOT 编译后的方法需要固定入口，而 JIT 可能动态优化方法，ArtMethod 的 entry_point 可以动态更新。
  3. 支持虚方法（多态）:通过 ArtMethod 的 方法表（vtable） 实现高效的多态调用。

所以我们说在Android的ART虚拟机中，ArtMethod是Java方法在Native层的表示形式，表示了 Java 方法 的核心数据结构，其存储一个 Java 方法的 元数据（如类名、方法名、签名）和 执行逻辑。在 ART 中，所有 Java 方法调用（包括虚方法、静态方法、构造函数）都通过 ArtMethod 实现。

示例：调用MyClass.foo()时，ART通过ArtMethod的入口地址跳转到执行代码。

在 ART 虚拟机中，对于方法的调用，大部分会调用到 ArtMethod::Invoke，因此我们可以以此为起点理解实际调用的过程。

  2. Native → JNI：在Android/JVM环境中，Frida通过JavaVM和JNIEnv接口与Java层交互
  3. 关键桥梁：
    a) Native层访问JNI能力：需要获取JavaVM指针
    b) 获取正确的JNIEnv：每个线程需要正确的JNIEnv指针

总的来说frida-java通过两步实现js世界到java世界的单向通道，首先利用frida-gum提供的js接口操作native世界，然后再基于jni连通到java世界。

主要步骤如下：

  1. 连通native世界，获得拟机的接口，如JNI_GetCreatedJavaVMs
  2. 获得JavaVM
  3. 获得JNIEnv
  4. 获得java类的class引用
  5. 操作该java类，如创建对象，调用方法等。

虽然此时我们已经将目标 ArtMethod 改成了 Native 方法，且 JNI 的入口指向我们的 hook 函数，但如果该方法已经被 OAT 或者 JIT 优化成了二进制代码，此时在字节码层调用 invoke-xxx 时会通过方法的 entry_point_from_quick_compiled_code_ 直接跳转到 native 代码执行，而不是 quick_xxx_trampoline。

因此对于这种情况，我们可以将 entrypoint 的地址重新指向 trampoline，但如前文所说，对于系统函数而言，其地址已知，因此调用方被优化后很可能直接就调转到了对应的 native 地址，而不会通过 entrypoint 去查找。因此 frida 采用的方法是直接修改目标方法的 quickCode 内容，将其替换为一段跳板代码，然后再间接跳转到我们的劫持实现中。

quickCode 的替换使用使用 ArtQuickCodeInterceptor 完成，姑且理解为跳板管理器，保存在 MethodMangler 的 interceptor 属性中，这样在程序退出或者用户调用 method.implementation = null 时还会调用 interceptor.deactivate 恢复方法，防止残留 hook 代码导致的运行时崩溃。
