数据结构封装

Go 语言不像 C++ 那样有类似 STL 的内建模板库，提供了一套丰富的泛型容器和算法封装。不过，Go 提供了一些内建的数据类型和库，使得开发者能够有效地处理常见的数据结构和操作。为了实现类似于 STL 的功能，Go 通过以下几种方式来弥补：

1. Go 内建数据类型

Go 语言提供了一些常用的数据结构和类型，能够完成基本的容器操作。常见的有：

  • 数组（Array） 和 切片（Slice）：Go 的切片类似于 C++ 中的 vector，支持动态扩展，且非常灵活。
  • 映射（Map）：Go 提供了原生的哈希表（类似 C++ 的 unordered_map 或 map）。
  • 通道（Channel）：Go 内建的并发数据结构，用于在 goroutine 之间传递数据。

2. 标准库

Go 提供了一些标准库来处理常见的算法和数据结构操作。虽然它不如 C++ STL 那样提供完备的模板库，但提供了一些非常实用的工具：

  • **container/list**：提供双向链表。
  • **container/heap**：提供堆（优先队列）实现。
  • **sort**：对切片进行排序。
  • **sync**：提供并发控制结构，例如 Mutex、RWMutex 等。
  • **math 和 math/rand**：数学和随机数生成库。

还有一些常见的第三方 Go 库，可以用来实现类似 STL 的功能：

  • **golang-collections/collections**：提供一些额外的集合数据结构，例如队列、栈等。
  • **gods**（GoDS）：一个包含常见数据结构的包，如链表、堆、树、图、集合等。
  • **go-datastructures**：提供高级数据结构，如红黑树、跳表、堆等。

面向接口组合

Go 语言不像传统的面向对象编程（OOP）语言（如 Java 或 C++）那样具有类（class）和继承的概念。Go 语言的面向对象编程模型更加简洁，提供了通过 结构体（struct） 和 方法（method） 实现类似面向对象的设计思路。虽然没有类和继承，但 Go 通过组合（composition）和接口（interface）来实现面向对象的思想。

Go 面向对象编程的基本概念

  1. 结构体（Struct）
  2. 方法（Method）

  5. 多态（Polymorphism）

并发编程

  • goroutines：轻量级的线程，是 Go 实现并发的核心。

内存管理

Go 语言的内存管理采用了自动垃圾回收（GC，Garbage Collection）机制，并提供了类似于其他现代语言的 堆（Heap）和 栈（Stack）管理模型。Go 的内存管理机制设计旨在减少手动内存管理的复杂性，同时保持高效的性能。

Go 的内存管理包括以下几个关键概念：

  1. 堆和栈
  2. 垃圾回收（GC）
  3. 内存分配（Memory Allocation）
  4. 指针与引用
  5. 逃逸分析（Escape Analysis）

1. 堆和栈

Go 使用堆和栈来管理内存，像 C 语言一样，内存分为这两部分：

  • 栈（Stack）：用于存储局部变量、函数调用等。栈的内存分配是由编译器自动管理的，且随着函数的调用和返回自动分配和释放。
  • 堆（Heap）：用于存储动态分配的对象，比如使用 new 或 make 创建的对象。堆内存由垃圾回收（GC）机制管理。

栈内存：

  • 栈内存的分配非常高效，因为栈是一个先进后出的结构，内存分配和释放非常迅速。
  • 栈上的数据是自动回收的，局部变量的生命周期与其所在的函数的生命周期一致。

堆内存：

  • 堆内存是通过 new 或 make 显式分配的，内存释放由垃圾回收器管理。
  • 堆上的数据通常具有较长的生命周期，可以跨越多个函数调用和 goroutine。

2. 垃圾回收（GC）

Go 的垃圾回收（GC）机制是自动的，目的是减少内存泄漏和提高内存使用的效率。Go 使用 标记-清除（Mark-and-Sweep） 和 三色标记法（Tri-Color Marking） 来进行垃圾回收。

GC 的工作原理：

  1. 标记阶段：首先，GC 会扫描所有活动的对象，并标记它们为“活动”（Reachable）。活动对象包括从根对象（如全局变量、栈上的变量等）可直接访问到的对象。
  2. 清除阶段：接着，GC 会清除那些没有被标记为活动的对象，释放它们所占用的内存。
  3. 压缩阶段（optional）：对于某些实现，GC 可能还会进行内存的压缩（移动活动对象）以减少内存碎片。

Go 的垃圾回收器是 并行且增量的，可以在程序运行时进行垃圾回收，而不会阻塞程序执行过长时间。Go 1.5 之后，GC 的性能得到了大幅改进，减少了对程序的影响。

GC 触发时机：

Go 会定期进行垃圾回收，通常有以下几种情况会触发 GC：

  • 内存使用超过某个阈值：当堆内存的使用量超过了设定的阈值时，GC 会被触发。
  • **显式调用 runtime.GC()**：你可以通过调用 runtime.GC() 手动触发 GC，但这通常是不推荐的，除非在特定情况下需要精确控制。

配置垃圾回收：

你可以使用 GOGC 环境变量来调整垃圾回收的频率：

  • GOGC=100（默认）：表示在堆内存增长 100% 时触发 GC。
  • 设置为更高的值，如 GOGC=200，表示需要堆内存增长到 200% 才会触发 GC，通常可以降低 GC 的频率，从而提高性能，但会增加内存占用。

3. 内存分配（Memory Allocation）

Go 提供了多种内存分配方式，最常见的是通过 new 和 make 来分配内存：

多线程模型

模型 映射关系 代表系统 特点
1:1模型 一个用户线程 ↔ 一个内核线程 Linux、Windows、现代Unix 真正的并发，但创建开销大

现代 Linux/pthread 是 1:1 模型，所以写一个 pthread_create()，内核就创建一个内核线程（task_struct），这个内核线程最终由 CPU 调度。

CPU 调度只能调度内核态线程，用户态线程自己无法被 CPU 调度。为了让用户线程可以并行执行，内核必须为它创建对应内核线程。内核线程本身包含：寄存器上下文、栈、调度信息、信号处理等内核态数据结构。

而M:N 模型需要用户线程库负责映射和切换，内核只看到 N 个内核线程。

Go采用了更轻量的数据结构来代替线程，这种数据结构相比线程更轻量，他有自己的栈，切换起来更快。然而真正执行并发的还是线程，

线程切换原理

说简单的就是：当前线程放弃cpu执行片， 调度器安排另外一个线程接受cpu调度， 说白了存在一个“下马、换人、再上马”的切换过程， 我就问你要不要减个速嘛。

实际上：

  1. 保存当前线程的寄存器状态：操作系统首先需要保存当前正在运行的线程的所有寄存器值。这是因为每个线程都有自己独立的执行环境，包括程序计数器、栈指针、通用寄存器等。
  2. 选择下一个要执行的线程：调度器根据一定的算法（如时间片轮转、优先级调度等）选择下一个要执行的线程。
  3. 恢复选定线程的寄存器状态：一旦确定了下一个要执行的线程，操作系统就会从该线程的控制块（TCB, Thread Control Block）中恢复其寄存器状态，包括设置程序计数器到正确的指令位置，恢复栈指针以及其它通用寄存器的值。

Python等解释性语言采用的是多进程并发模型，进程的上下文是最大的，所以切换耗费巨大，同时由于多进程通信只能用socket通讯，或者专门设置共享内存，给编程带来了极大的困扰与不便；C++等语言通常会采用多线程并发模型，相比进程，线程的上下文要小很多，而且多个线程之间本来就是共享内存的，所以编程相比要轻松很多。

线程切换的时机

分为用户代码导致的 和 操作系统主动形成的线程切换。

① 自发性上下文切换 线程受用户代码指令导致的切出

object.wait() 线程等待锁
Thread.yield() 当前线程主动让出CPU，如果有其他就绪线程就执行其他线程，如果没有则继续当前线程
oThread.join() 阻塞发起调用的线程，直到oThread执行完毕

线程的时间片用完 ，cpu时间片雨露均沾

线程上下文切换的代价是高昂的：上下文切换的延迟取决于不同的因素，大概是50到100ns左右，考虑到硬件平均在每个核心上每ns执行12条指令，那么一次上下文切换可能会花费600到1200条指令的延迟时间。

线程切换的影响

  • 直接开销：保存当前/恢复新线程上下文所需的开销，线程调度器调度线程的开销
  • 间接开销：重新加载高速缓存，上下文切换可能导致 一级缓存被冲刷，写入下一级缓存或内存

于是出现了线程池技术，将线程先储存起来，保持一定的数量，来避免频繁开启/关闭线程的时间消耗，但是这种初级的技术存在一些问题，比如有线程一直被IO阻塞，这样的话这个线程一直占据着坑位，导致后面的任务排不到队，拿不到线程来执行；

用户态轻量级线程(协程)

如上面所述，常规线程切换会存在用户态程序和内核态调度程序的切换， 有一个减速换挡的瞬间。于是大佬们思考了另外一个思路：将调度尽量维持在用户态。

系统线程[goroutine的调度与内核对系统线程的调度原理是一样的，实质都是通过保存和恢复CPU寄存器的值来达到切换goroutine/切换线程的目的。

在go语言调度器源代码中，goroutine的数据结构g里面也有类似线程控制块那样的结构，来保存/恢复cpu寄存器值。

当goroutine被调离CPU时，调度器负责把CPU寄存器的值保存在g对象的成员变量之中;当goroutine被调度起来运行时，调度器又负责把g 的成员变量所保存的寄存器的值恢复到CPU的寄存器。这种用户态的调度最终 形成了著名的GMP调度模型

每个G（Goroutine）要想真正运行起来，需要通过用户态的调度器P 进入待调度本地队列中。
对于M来说，调度器P解耦了调度/执行 （P专做调度，M专做执行）；同时P上挂在的本地队列，也让M避免了对全局G队列的有锁抢占。

通过调度器将goroutine调度到线程中执行，并适时地释放和创建新的线程，并且当一个正在运行的goroutine进入阻塞（常见场景就是等待IO）时，将其脱离占用的线程，将其他准备好运行的goroutine放在该线程上执行。通过较为复杂的调度手段，使得整个系统获得极高的并行度同时又不耗费大量的CPU资源。

组成

GMP

  • M：指go中的工作者线程(操作系统线程)，是真正执行代码的单元，负责执行 Goroutine。

  • P：是一种调度goroutine的上下文，goroutine依赖于P进行调度，P是真正的并行单元,逻辑处理器，负责调度 Goroutine 并与 M 绑定。

  • G：即goroutine，是go语言中的一段代码（以一个函数的形式展现），最小的并行单元；

G（Goroutine）

Goroutine是 Go 语言中的轻量级线程，由 Go 运行时（Runtime）管理。它是 Go 并发编程的基本单位，比操作系统线程更轻量，创建和销毁的开销更小。每个 Goroutine 初始只有几 KB 的栈空间，栈空间可以动态扩容（最大可达 1GB）。栈的动态扩容和缩容由 Go 运行时管理，避免了固定栈大小的限制。

Goroutine 的调度是协作式的，Go 运行时会根据 Goroutine 的状态和调度策略决定是否切换 Goroutine。调度器会在 Goroutine 执行一定时间后强制切换（抢占式调度），避免某个 Goroutine 长时间占用 CPU。

M（Machine）

M 是操作系统线程（OS Thread）的抽象，代表真正的计算资源。每个 M 都与一个操作系统线程一一对应，负责执行 Goroutine 的代码。M 是操作系统线程的抽象，每个 M 都绑定一个操作系统线程。操作系统线程是真正的执行单元，负责运行 Goroutine。

每个 M 会绑定一个 P（逻辑处理器），并从 P 的队列中获取 Goroutine 执行。如果 M 在执行 Goroutine 时发生阻塞（如系统调用），Go 运行时会解绑 M 和 P，并将 P 交给其他空闲的 M。

P（Processor）

P 是逻辑处理器（Logical Processor），是 GMP 模型中的调度上下文。P 的数量由 GOMAXPROCS 决定，默认等于 CPU 核心数。每个 P 都有一个本地 Goroutine 队列，用于存储待运行的 Goroutine。本地队列的长度有限，如果本地队列满了，新的 Goroutine 会被放入全局队列。

绑定 M：每个 P 会绑定一个 M，M 从 P 的本地队列中获取 Goroutine 并执行。如果 M 阻塞，P 会被解绑并交给其他 M。

队列

本地运行队列

在go中有多个运行队列可以保存待运行(_Grunnable)的G, 它们分别是各个P中的本地运行队列和全局运行队列。入队待运行的G时会优先加到当前P的本地运行队列, M获取待运行的G时也会优先从拥有的P的本地运行队列获取。

本地运行队列入队和出队不需要使用线程锁。本地运行队列有数量限制, 当数量达到256个时会入队到全局运行队列。
本地运行队列的数据结构是环形队列, 由一个256长度的数组和两个序号(head, tail)组成.当M从P的本地运行队列获取G时, 如果发现本地队列为空会尝试从其他P盗取一半的G过来,
这个机制叫做Work Stealing。

全局运行队列

全局运行队列保存在全局变量sched中, 全局运行队列入队和出队需要使用线程锁。全局运行队列的数据结构是链表, 由两个指针(head, tail)组成.

空闲链表

空闲M链表

当M发现无待运行的G时会进入休眠, 并添加到空闲M链表中, 空闲M链表保存在全局变量sched.
进入休眠的M会等待一个信号量(m.park), 唤醒休眠的M会使用这个信号量.

go需要保证有足够的M可以运行G, 是通过这样的机制实现的:

  • 入队待运行的G后, 如果当前无自旋的M但是有空闲的P, 就唤醒或者新建一个M
  • 当M离开自旋状态并准备运行出队的G时, 如果当前无自旋的M但是有空闲的P, 就唤醒或者新建一个M
  • 当M离开自旋状态并准备休眠时, 会在离开自旋状态后再次检查所有运行队列, 如果有待运行的G则重新进入自旋状态

因为”入队待运行的G”和”M离开自旋状态”会同时进行, go会使用这样的检查顺序:

  1. 入队待运行的G => 内存屏障 => 检查当前自旋的M数量 => 唤醒或者新建一个M
  2. 减少当前自旋的M数量 => 内存屏障 => 检查所有运行队列是否有待运行的G => 休眠

这样可以保证不会出现待运行的G入队了, 也有空闲的资源P, 但无M去执行的情况.

空闲P链表

当P的本地运行队列中的所有G都运行完毕, 又不能从其他地方拿到G时,拥有P的M会释放P并进入休眠状态, 释放的P会变为空闲状态并加到空闲P链表中, 空闲P链表保存在全局变量sched
下次待运行的G入队时如果发现有空闲的P, 但是又没有自旋中的M时会唤醒或者新建一个M, M会拥有这个P, P会重新变为运行中的状态。

调度器

Go 调度器的两大思想（复用线程 和 利用并行）以及两小策略（抢占 和 全局 G 队列）。1. 调度器的两大思想

复用线程

复用线程是 Go 调度器的一个重要设计目标，目的是避免频繁创建和销毁线程，从而减少系统开销。具体体现在以下两个方面：

Work Stealing（工作窃取）

当一个线程（M）绑定的 P 的本地队列中没有可运行的 Goroutine（G）时，线程可能会进入空闲状态。

解决方案：Go 调度器实现了 Work Stealing 机制：当线程的本地队列为空时，它会尝试从其他线程绑定的 P 的本地队列中“偷取”一些 Goroutine 来运行。

Hand Off（交接）

当一个线程（M）因为 Goroutine 发起系统调用（如文件 I/O、网络 I/O）而阻塞时，线程无法继续执行其他 Goroutine。

解决方案：Go 调度器实现了 Hand Off 机制：当线程阻塞时，它会释放绑定的 P，并将 P 交给其他空闲的线程继续执行。

利用并行

利用并行是 Go 调度器的另一个核心思想，目的是通过多核 CPU 的并行计算能力，提高程序的执行效率。

GOMAXPROCS 的作用

  • GOMAXPROCS 是 Go 运行时的一个参数，用于设置 P（逻辑处理器）的数量。
  • P 的数量决定了同时可以有多少个线程（M）处于运行状态。
  • 默认情况下，GOMAXPROCS 的值等于 CPU 的核心数。

并行的实现

当 GOMAXPROCS > 1 时，Go 调度器可以同时运行多个线程（M），这些线程可能分布在多个 CPU 核心上，从而实现并行计算。例如：如果 GOMAXPROCS = 4，则最多有 4 个线程同时运行，每个线程可以绑定一个 P，充分利用 4 个 CPU 核心的计算能力。

限制并发程度

GOMAXPROCS 不仅决定了并行的上限，还可以用于限制并发的程度。

例如：如果 GOMAXPROCS = 核数 / 2，则最多只能利用一半的 CPU 核心进行并行计算。这种设置可以用于控制程序的资源占用，避免过度消耗 CPU 资源。

两小策略

抢占

抢占是 Go 调度器的一个重要策略，用于防止某个 Goroutine 长时间占用 CPU，导致其他 Goroutine 无法执行。

  • Go 调度器会在 Goroutine 执行一定时间后（默认 10ms）强制切换。
  • 抢占式调度通过 信号机制 实现，调度器会向 M 发送信号，强制切换 Goroutine。

避免了某个 Goroutine 长时间占用 CPU，导致其他 Goroutine 被“饿死”。确保了 Goroutine 的公平调度，提高了程序的响应性。

全局 G 队列

全局 G 队列是 Go 调度器的一个辅助机制，用于存储所有 P 共享的 Goroutine。当 M 执行 Work Stealing 从其他 P 偷不到 Goroutine 时，它会从全局 G 队列中获取 Goroutine。全局 G 队列的功能已经被弱化，主要用于辅助调度。

确保在没有本地 Goroutine 可执行时，M 仍然可以从全局队列中获取任务。提高了 Goroutine 的调度效率，避免了资源的浪费。

Goroutine 的特点

非阻塞

Goroutine 的引入是为了方便高并发程序的编写。当一个 Goroutine 进行阻塞操作（如系统调用）时，调度器会将当前线程中的其他 Goroutine 移交到其他线程中继续执行，从而避免整个程序的阻塞。

Go 调度器通过 Hand Off（交接） 机制处理阻塞操作：当 Goroutine 发起阻塞操作时，当前线程（M）会解绑 P（逻辑处理器），并将 P 交给其他空闲的线程继续执行。阻塞操作完成后，Goroutine 会被重新放入队列等待调度。

调度器

Go 语言实现了自己的调度器，负责 Goroutine 的调度和执行。调度器能够在执行垃圾回收（GC）时暂停 Goroutine，确保 GC 的正确性。Go 调度器基于 GMP 模型：调度器通过本地队列、全局队列和Work Stealing 机制，高效地调度 Goroutine。

自己维护堆栈

每个 Goroutine 都有自己的栈空间，用于存储局部变量、函数调用等信息。Goroutine 的栈空间是动态分配的，初始大小只有几 KB，可以根据需要动态扩容（最大可达 1GB）。

连续栈（Contiguous Stack）：Go 语言使用连续栈技术管理 Goroutine 的栈空间。当栈空间不足时，Go 运行时会分配一块更大的栈，并将旧栈的内容拷贝到新栈中。这种设计避免了 Split Stacks 技术可能导致的频繁内存分配和释放。

抢占式调度

Goroutine 的执行是可以被抢占的。如果一个 Goroutine 长时间占用 CPU，调度器会强制将其抢占，把 CPU 时间交给其他 Goroutine。

抢占式调度：Go 调度器会在 Goroutine 执行一定时间后（默认 10ms）强制切换。抢占式调度通过 信号机制 实现，调度器会向 M 发送信号，强制切换 Goroutine。

协作式调度：Goroutine 在执行某些操作（如 channel 操作、系统调用）时，会主动让出 CPU，切换到其他 Goroutine。

阻塞与非阻塞

nil Channel：向 nil Channel 发送或接收数据会永久阻塞（除非是非阻塞模式）。【nil Channel 是一个未初始化的 Channel 变量，其值为 nil。比如：var ch chan int // ch 是一个 nil Channel】

在 Go 语言中，阻塞模式和非阻塞模式是指 Goroutine 在执行 Channel 操作时的行为方式。这两种模式的区别在于，当 Channel 操作不能立即完成时，Goroutine 是否会挂起等待。

在阻塞模式下，如果 Channel 操作不能立即完成（例如向无缓冲 Channel 发送数据时没有接收方，或向有缓冲 Channel 发送数据时缓冲区已满），当前 Goroutine 会被挂起，直到操作可以继续。Goroutine 会等待，直到 Channel 操作完成。这是 Go 中 Channel 的默认行为。

  • 如果 ch 是无缓冲 Channel，ch <- 1 会阻塞，直到有其他 Goroutine 执行 <-ch。

  • 如果 ch 是有缓冲 Channel，ch <- 1 只有在缓冲区满时才会阻塞。

在非阻塞模式下，如果 Channel 操作不能立即完成，Goroutine 不会挂起，而是直接返回失败（例如返回 false）。

  • Goroutine 不会等待，而是立即返回。
  • 非阻塞模式通常通过 select 语句的 default 分支实现。

如果 ch 的缓冲区已满，ch <- 1 会立即执行 default 分支。如果 ch 的缓冲区为空，<-ch 会立即执行 default 分支。

接下来，是selectgo()函数的主处理逻辑，它会分三个阶段查找或等待某个channel准备就绪：

  1. 查找是否有可以立即收发的 channel。
  2. 如果没有，将当前 goroutine 加入所有 case 的 channel 的等待队列并挂起。
  3. 被唤醒后，找到被选中的 case 并执行相应的操作。

需要说明的是，runtime.selectgo 函数会根据不同情况通过 goto 语句跳转到函数内部的不同标签执行相应的逻辑。其中包括：bufrecv：可以从channel缓冲区读取数据；bufsend：可以向channel缓冲区写入数据；recv：可以从休眠的发送方获取数据；send：可以向休眠的接收方发送数据；rclose：可以从关闭的 channel 读取 EOF；sclose：向关闭的 channel 发送数据；retc：结束调用并返回；

第一阶段

按照 pollorder 的顺序遍历所有 case，检查是否有 channel 可以立即执行发送或接收操作。

  • 如果某个 channel 的 sendq 或 recvq 上有等待的 goroutine，或者缓冲区有数据（接收）或空闲空间（发送），则立即执行相应的操作。
  • 如果找到可以立即执行的 case，跳转到对应的标签（如 recv、send、bufrecv、bufsend）进行处理。
第二阶段

如果没有 channel 可以立即执行操作，将当前 goroutine 加入所有 case 对应的 channel 的发送队列（sendq）或接收队列（recvq），并挂起当前 goroutine，等待被唤醒。

  • 为每个 case 创建一个 sudog，并将其加入对应 channel 的等待队列。
  • 调用 gopark 挂起当前 goroutine，等待其他 goroutine 的唤醒。

第三阶段

当前 goroutine 被唤醒后，找到被选中的 case，并执行相应的操作。遍历所有 case，找到被选中的 case（即唤醒当前 goroutine 的 channel）。根据 case 的类型（发送或接收），执行相应的操作。清理未选中的 case，释放资源。

selectgo函数的执行分为四个步骤：首先，随机生成一个遍历case的轮询顺序 pollorder 并根据 channel 地址生成加锁顺序 lockorder，随机顺序能够避免channel饥饿，保证公平性，加锁顺序能够避免死锁和重复加锁；然后，根据 pollorder 的顺序查找 scases 是否有可以立即收发的channel，如果有则获取case索引进行处理；再次，如果pollorder顺序上没有可以直接处理的case，则将当前 goroutine 加入各 case 的 channel 对应的收发队列上并等待其他 goroutine 的唤醒；最后，当调度器唤醒当前 goroutine 时，会再次按照 lockorder 遍历所有的case，从中查找需要被处理的case索引进行读写处理，同时从所有case的发送接收队列中移除掉当前goroutine。

互斥锁的结构

Sync.Mutex由两个字段构成，state用来表示当前互斥锁处于的状态，sema用于控制锁状态的信号量。相信各位道友读完这两个字段的描述后，好像懂了，又好像没懂。下面我们详细理解下这两个字段到底都作了哪些事。

互斥锁state主要记录了如下四种状态：

  • waiter_num： 记录了当前等待抢这个锁的goroutine数量
  • starving： 当前锁是否处于饥饿状态 (后文会详解锁的饥饿状态) 0: 正常状态 1: 饥饿状态
  • woken： 当前锁是否有goroutine已被唤醒。 0：没有goroutine被唤醒； 1: 有goroutine正在加锁过程
  • locked： 当前锁是否被goroutine持有。 0: 未被持有 1: 已被持有

sema信号量的作用

当持有锁的gorouine释放锁后，会释放sema信号量，这个信号量会唤醒之前抢锁阻塞的gorouine来获取锁。

锁的两种模式

Go 语言中的 互斥锁（Mutex） 是用于保护共享资源的重要工具。为了在高并发场景下提高锁的公平性和性能，Go 的互斥锁设计了两种模式：正常模式 和 饥饿模式。这两种模式的主要目的是在保证性能的同时，尽可能避免某些 Goroutine 长时间无法获取锁（即“饥饿”问题）。

正常模式

在正常模式下，所有阻塞在等待队列中的 Goroutine 会按顺序进行锁获取。当唤醒一个等待队列中的 Goroutine 时，此 Goroutine 并不会直接获取到锁，而是会和新请求锁的 Goroutine 竞争。通常，新请求锁的 Goroutine 更容易获取锁，因为它正在占用 CPU 时间片执行，大概率可以直接执行到获取锁的逻辑。

优点：性能较高，因为新请求锁的 Goroutine 可以直接参与竞争，减少了上下文切换的开销。适合低竞争的场景。

缺点：可能导致某些 Goroutine 长时间无法获取锁（即“饥饿”问题）。

饥饿模式

在饥饿模式下，新请求锁的 Goroutine 不会直接参与锁的竞争，而是会被加入到等待队列的尾部，阻塞等待获取锁。只有等待队列中的 Goroutine 才能获取锁，确保了锁的公平性。

触发条件：当一个 Goroutine 等待锁的时间超过 1ms 时，互斥锁会切换到饥饿模式。

取消条件：当获取到锁的 Goroutine 是等待队列中的最后一个 Goroutine 时，互斥锁会切换到正常模式。当获取到锁的 Goroutine 的等待时间在 1ms 之内时，互斥锁会切换到正常模式。

优点：避免了某些 Goroutine 长时间无法获取锁的问题，提高了锁的公平性。适合高竞争的场景。

缺点：性能较低，因为新请求锁的 Goroutine 必须加入等待队列，增加了上下文切换的开销。

两种模式的切换

  • 正常模式 → 饥饿模式：当一个 Goroutine 等待锁的时间超过 1ms 时，互斥锁会切换到饥饿模式。
  • 饥饿模式 → 正常模式：当获取到锁的 Goroutine 是等待队列中的最后一个 Goroutine 时，互斥锁会切换到正常模式。当获取到锁的 Goroutine 的等待时间在 1ms 之内时，互斥锁会切换到正常模式。

使用 Mutext 锁虽然很简单，但仍然有几点需要注意：

  • 同一协程里，不要在尚未解锁时再次使加锁
  • 同一协程里，不要对已解锁的锁再次解锁
  • 加了锁后，别忘了解锁，必要时使用 defer 语句

RWMutex

读写锁的结构：

读操作如何防止并发读写问题的？

  • RLock(): 申请读锁，每次执行此函数后，会对readerCount++，此时当有写操作执行Lock()时会判断readerCount>0,就会阻塞。
  • RUnLock(): 解除读锁，执行readerCount–，释放信号量唤醒等待写操作的goroutine。

写操作如何防止并发读写、写写问题？

  • Lock(): 申请写锁，获取互斥锁，此时会阻塞其他的写操作。并将readerCount 置为 -1，当有读操作进来，发现readerCount = -1， 即知道有写操作在进行，阻塞。
  • Unlock(): 解除写锁，会先通知所有阻塞的读操作goroutine，然后才会释放持有的互斥锁。

为什么写操作不会被饿死？

写操作要等待读操作结束后才可以获得锁，而写操作在等待期间可能还有新的读操作持续到来，如果写操作等待所有读操作结束，很可能会一直阻塞，这种现象称之为写操作被饿死。

通过RWMutex结构体中的readerWait属性可完美解决这个问题。当写操作到来时，会把RWMutex.readerCount值拷贝到RWMutex.readerWait中，用于标记排在写操作前面的读者个数。前面的读操作结束后，除了会递减RWMutex.readerCount，还会递减RWMutex.readerWait值，当RWMutex.readerWait值变为0时唤醒写操作。

  • 读操作：通过 RLock() 和 RUnlock() 实现并发读操作。读操作不会阻塞其他读操作，但会阻塞写操作。

  • 写操作：通过 Lock() 和 Unlock() 实现独占写操作。写操作会阻塞其他读写操作。

  • 写操作不被饿死：通过 readerWait 属性，确保写操作在等待期间不会被新的读操作无限阻塞。

在 Go 语言中，反射（reflection）是指程序在运行时检查变量类型和值，并在运行时动态操作这些类型和值的能力。由于 Go 是强类型、静态编译语言，变量的具体类型通常在编译期就确定，但在很多场景下，如通用框架、插件系统、JSON/YAML 序列化、RPC 调用、ORM 映射等，程序无法在编译期知道所有类型，此时反射就提供了运行期类型自省的能力。

反射的核心在于两个接口：reflect.Type 用于获取变量的类型信息（如它是 struct、slice、map 或基本类型，结构体字段和方法信息等），reflect.Value 用于读取和修改变量的实际值。通过反射，程序可以在运行时动态读取字段、调用方法、修改值，甚至根据 struct tag 执行自动化逻辑，例如自动注入默认值或映射数据库字段。

需要注意的是，反射操作存在性能开销，并且绕过了编译期的类型检查，容易在运行期产生 panic，因此反射通常只用于框架层或底层库，而不应直接用于业务逻辑。

Go 的反射与接口密切相关：接口在运行时携带了类型信息，而反射就是操作这些类型信息的工具。在 Go 中有三个经典的反射定律，分别如下

  1. 反射可以将interface{}类型变量转换成反射对象
  2. 反射可以将反射对象还原成interface{}类型变量
  3. 要修改反射对象，其值必须是可设置的

这三个定律便是 Go 反射的核心，当需要访问类型相关信息时，便需要用到reflect.TypeOf，当需要修改反射值时，就需要用到reflect.ValueOf

panic

panic中文译为恐慌，表示十分严重的程序问题，程序需要立即停止来处理该问题，否则程序立即停止运行并输出堆栈信息，panic是 Go 是运行时异常的表达形式，通常在一些危险操作中会出现，主要是为了及时止损，从而避免造成更加严重的后果。

panic 的本质： 立即中断当前 goroutine 的正常执行，逐层函数返回（栈展开），如果未 recover，程序直接崩溃

defer

defer 是 Go 的“函数级后置钩子”，参数立即求值，函数延迟执行，与 return / panic 强绑定， 是资源安全和并发健壮性的核心工具

程序因为panic退出之前会做一些善后工作，例如执行defer语句。

defer 用来“延迟执行函数”，在当前函数返回之前执行，注意：defer 的参数在“defer 语句执行时”就已经确定了

defer + return 的真实执行顺序（核心）执行顺序是：设置返回值—>执行 defer—>真正

panic 发生时：当前函数的 defer 一定会执行并且按 LIFO 顺序执行
