问题分析

  1. 暴露内部实现：客户端代码直接访问了 BookShelf 内部的 ArrayList 集合。客户端不仅关心书架的内容，还关心了书架是如何存储书籍的，这增加了依赖性。
  2. 更换集合类型困难：如果我们决定将 BookShelf 类的内部实现从 ArrayList 改为 LinkedList 或其他集合类型，所有依赖 getBooks() 方法的客户端代码都需要做修改，因为它们与具体实现绑定了。
  3. 不符合封装原则：书架的具体实现（如使用 ArrayList）不应暴露给客户端，客户端只关心如何获取书籍，迭代器模式本来就是要避免这种问题。

定义

迭代器模式是一种行为型设计模式，它提供一种方法来顺序访问一个集合对象中所有的元素，而不暴露该对象的内部结构（列表、 栈和树等）。迭代器模式允许客户端以统一的方式遍历不同类型的集合对象，而不需要关心集合的具体实现。迭代器模式的主要思想是将集合的遍历行为抽取为单独的迭代器对象。

结构

Iterator（迭代器）：定义了访问集合元素的方法，如 next(), hasNext()，使得客户端能够顺序访问集合中的元素。

ConcreteIterator（具体迭代器）：实现了 Iterator 接口，负责跟踪当前迭代的位置，并实现具体的遍历方法。

Aggregate（聚合类）：提供一个创建迭代器的接口，定义了返回迭代器的方法。

ConcreteAggregate（具体聚合类）：实现了 Aggregate 接口，具体的集合类，提供元素的存储和管理。

正确示范

  1. 声明迭代器接口。 该接口必须提供至少一个方法来获取集合中的下个元素。 但为了使用方便， 你还可以添加一些其他方法， 例如获取前一个元素、 记录当前位置和判断迭代是否已结束。
  2. 声明集合接口并描述一个获取迭代器的方法。 其返回值必须是迭代器接口。 如果你计划拥有多组不同的迭代器， 则可以声明多个类似的方法。
  3. 为希望使用迭代器进行遍历的集合实现具体迭代器类。 迭代器对象必须与单个集合实体链接。 链接关系通常通过迭代器的构造函数建立。
  4. 在你的集合类中实现集合接口。 其主要思想是针对特定集合为客户端代码提供创建迭代器的快捷方式。 集合对象必须将自身传递给迭代器的构造函数来创建两者之间的链接。
  5. 检查客户端代码， 使用迭代器替代所有集合遍历代码。 每当客户端需要遍历集合元素时都会获取一个新的迭代器。

迭代器模式优缺点

优点

  • 单一职责原则。 通过将体积庞大的遍历算法代码抽取为独立的类， 你可对客户端代码和集合进行整理。
  • 开闭原则。 你可实现新型的集合和迭代器并将其传递给现有代码， 无需修改现有代码。
  • 你可以并行遍历同一集合， 因为每个迭代器对象都包含其自身的遍历状态。
  • 相似的， 你可以暂停遍历并在需要时继续。

缺点

  • 如果你的程序只与简单的集合进行交互， 应用该模式可能会矫枉过正。
  • 对于某些特殊集合， 使用迭代器可能比直接遍历的效率低。

使用场景

  • 需要访问一个集合对象的内容但又不希望暴露其内部结构：例如，访问一个数据库的记录，客户端可以使用迭代器来遍历记录，而无需关心数据库的内部实现。
  • 需要多种方式遍历集合对象：例如，客户端可能需要以不同的方式遍历集合（正向遍历、逆向遍历等），可以使用多个迭代器实现不同的遍历策略。
  • 访问不同类型的集合对象：当项目中有多个不同类型的集合（如列表、队列、栈等），使用迭代器模式可以让它们拥有相同的遍历接口，简化客户端代码。

访问者模式

假设我们有一个餐厅菜单系统，其中有不同的菜品和原料，每个菜品都可能包含多个原料。我们希望添加新的功能，如获取每个菜品和原料的健康评分、卡路里等信息。在这个场景中，使用访问者模式能够使得我们在不修改现有类的前提下，向系统添加新的功能。

错误实现:

如果我们在没有使用访问者模式的情况下，在菜单项和原料类中直接添加获取健康评分、卡路里、蛋白质等新功能，我们可能会遇到以下问题：

  1. 代码重复：每次增加新的功能时，我们需要修改菜单项和原料类，增加新的方法，这会导致每个类中有很多冗余的代码。
  2. 违背开闭原则：如果要添加新的功能（比如获取营养信息），我们需要修改原有的类，而不是仅仅在外部增加功能。
  3. 难以扩展：随着业务的发展，可能会增加更多的功能（例如“计算价格”、“生成购物清单”），如果每个类都需要修改，这将导致系统的扩展变得非常困难。

代码实现:

在这种反例中，每次增加新的功能时，必须修改现有类，导致代码膨胀，并且不利于未来的扩展。比如，如果需要添加更多功能，就必须再次修改每个类，这违反了开闭原则（应当对扩展开放，对修改封闭）。

定义

访问者模式是一种行为型设计模式，允许你为对象组合中的每个元素添加新的操作，而无需修改这些元素的类。访问者模式适用于对象结构稳定的场景，在对象结构不频繁变化时可以增加新功能而不修改现有类的代码。

观察者模式

简单介绍

观察者模式是一种行为型设计模式，用于定义对象间的一种一对多依赖关系，使得当一个对象的状态发生改变时，所有依赖于它的对象都会收到通知并自动更新。

它的核心目的是实现松耦合的通知机制，尤其适合事件驱动的系统。(可以类比发布—订阅者之间的关系【常见的消息队列都有类似功能，比如redis和rabbitmq中都有相应的思想的体现】)

观察者模式的工作原理

  • 被观察者（Subject）维护一个观察者列表。
  • 当被观察者状态发生变化时，调用 notifyObservers() 方法，通知所有注册的观察者。
  • 观察者通过实现 update() 方法，响应状态变化并更新自身。

存在的问题

定义

命令模式是一个高内聚的模式，其定义为：将一个请求封装成一个对象，从而让你使用不同的请求把客户端参数化，对请 求排队或者记录请求日志，可以提供命令的撤销和恢复功能。

UML类图

在该类图中，我们看到个整个结构：

  • 命令接口（Command）：定义所有具体命令需要实现的接口，通常包含 execute() 和（可选的）undo() 方法。
  • 具体命令（ConcreteCommand）：实现命令接口，绑定一个接收者，并调用接收者的相关操作。
  • 接收者（Receiver）：执行具体请求的逻辑，具体命令会调用接收者的方法来完成工作。
  • 调用者（Invoker）：负责存储和调用命令对象，触发命令的执行。
  • 客户端（Client）：创建具体命令并指定接收者，将命令传递给调用者。

核心思想

  • 将操作请求（方法调用）封装成独立的命令对象，解耦调用者和执行者之间的关系。
  • 调用者（Invoker） 不需要知道请求的具体执行细节，只需要持有命令对象。
  • 接收者（Receiver） 负责实际执行命令。

使用场景

当需要先将一个函数登记上，然后再以后调用此函数时，就需要使用命令模式，其实这就是回调函数。

有时候需要向某些对象发送请求，但是并不知道请求的接收者是谁，也不知道被请求的操作是什么。此时希望用一种松耦合的方式来设计程序，使得请求发送者和请求接收者能够消除彼此之间的耦合关系

例子：拿订餐来说，客人需要向厨师发送请求，但是完全不知道这些厨师的名字和联系方式，也不知道厨师炒菜的方式和步骤。 命令模式把客人订餐的请求封装成 command 对象，也就是订餐中的订单对象。这个对象可以在程序中被四处传递，就像订单可以从服务员手中传到厨师的手中。这样一来，客人不需要知道厨师的名字，从而解开了请求调用者和请求接收者之间的耦合关系

模板方法模式

模式定义

模板方法模式是一种行为型设计模式，它定义了一个操作中的算法骨架，将某些步骤的实现延迟到子类中。通过模板方法，子类可以不改变算法结构的情况下重新定义算法中的某些步骤。

模板方法模式的核心是定义一个父类，并在其中实现一个模板方法，该方法定义了算法的步骤，并且调用了一些抽象方法。子类通过继承父类并实现这些抽象方法，来实现具体的步骤。

真实世界类比：

模板方法可用于建造大量房屋。 标准房屋建造方案中可提供几个扩展点， 允许潜在房屋业主调整成品房屋的部分细节。

每个建造步骤 （例如打地基、 建造框架、 建造墙壁和安装水电管线等） 都能进行微调， 这使得成品房屋会略有不同。

模式结构

模板方法模式通常包含以下几个角色：

  • 抽象类（Abstract Class）：定义了模板方法和算法的框架，同时也可以实现一些步骤的默认行为。
  • 具体类（Concrete Class）：继承抽象类，并实现抽象方法，提供具体的实现。

模式优缺点

优点 缺点
1. 定义了一个算法的骨架，让子类可以更灵活地修改某些步骤，而无需改变整体结构。 1. 子类继承父类并实现某些步骤，增加了类的数量，可能会导致系统类数过多。
2. 通过模板方法的使用，可以减少代码重复，提高代码复用率。 2. 如果算法中有很多步骤需要修改，可能会让模板方法的结构变得复杂，维护难度增大。

使用场景

  1. 多个子类有共通的行为，但某些步骤的实现不尽相同。
  2. 算法的结构是固定的，某些步骤的实现可以延迟到子类中。
  3. 子类可以扩展或修改算法的某些部分，但不能改变算法的整体结构。

错误示范：

问题分析

  1. 条件判断繁琐： 每次方法执行时，都需要通过判断 state 来决定执行哪一块代码，随着状态种类增加，条件判断的复杂度也随之增加。
  2. 维护困难： 如果电梯系统的状态越来越多，代码中的条件判断就会变得越来越复杂，维护和扩展变得非常困难，增加了出错的可能性。
  3. 状态与行为混杂： 电梯的状态和电梯的行为被紧密地耦合在一起，这违背了单一职责原则（SRP），一个类承担了过多的责任。

定义

状态模式是一种行为型设计模式，它允许一个对象在其内部状态改变时改变其行为。对象看起来好像修改了其类。状态模式通过将不同的状态封装到单独的类中，使得对象的状态变化能够独立于客户端进行管理，从而避免了复杂的状态判断逻辑。

有限状态机

状态模式与有限状态机 的概念紧密相关。

其主要思想是程序在任意时刻仅可处于几种有限的状态中。 在任何一个特定状态中， 程序的行为都不相同， 且可瞬间从一个状态切换到另一个状态。 不过， 根据当前状态， 程序可能会切换到另外一种状态， 也可能会保持当前状态不变。 这些数量有限且预先定义的状态切换规则被称为转移。

状态机通常由众多条件运算符 （ if或 switch ） 实现， 可根据对象的当前状态选择相应的行为。 “状态” 通常只是对象中的一组成员变量值。 即使你之前从未听说过有限状态机， 你也很可能已经实现过状态模式。 正如我们前面的错误示例那样。

真实世界类比：

智能手机的按键和开关会根据设备当前状态完成不同行为：

  • 当手机处于解锁状态时， 按下按键将执行各种功能。
  • 当手机处于锁定状态时， 按下任何按键都将解锁屏幕。
  • 当手机电量不足时， 按下任何按键都将显示充电页面。

结构

状态模式建议为对象的所有可能状态新建一个类， 然后将所有状态的对应行为抽取到这些类中。

原始对象被称为上下文 （context）， 它并不会自行实现所有行为， 而是会保存一个指向表示当前状态的状态对象的引用， 且将所有与状态相关的工作委派给该对象。

状态模式通常包括以下角色：

  • 上下文（Context）：持有一个状态对象的引用，并通过这个引用来调用当前状态的行为。
  • 抽象状态（State）：定义一个接口，用于封装与上下文的每个状态相关的行为。
  • 具体状态（ConcreteState）：实现抽象状态接口，定义在特定状态下对象的行为。

UML类图

不使用状态模式时，整个状态机的控制逻辑集中在一个类中，导致了复杂的条件判断和易于出错的代码，相比之下，使用状态模式后，状态的逻辑被分离到了不同的状态类中，Elevator 类不再需要关心每个状态的行为，而是委托给各个具体状态类，避免了条件判断的繁杂，并且每个状态类只负责自己的行为，符合单一职责原则。

状态模式优缺点：

优点 缺点
1. 状态的行为被封装到不同的状态类中，符合单一职责原则，易于扩展和维护。 1. 状态数量多时，会导致系统中类的数量增多，增加系统复杂性。
2. 状态切换的逻辑集中管理，代码清晰，易于理解。 2. 每个状态都需要为所有操作实现方法，可能导致类的代码重复。
3. 可以动态地修改对象的行为，使得对象的行为依赖于其状态，避免了复杂的条件判断。 3. 增加了类的数量和系统的复杂度，需要针对每个可能的状态编写具体类。

使用场景：

对象的行为随其状态改变而不同当一个对象的行为根据其状态的不同而有所不同，并且需要在运行时改变对象的状态时，适合使用状态模式。

  • 例如，电梯、音响播放器、网络连接等有不同工作状态的系统。

避免复杂的条件判断语句在代码中频繁使用大量的 if-else 或 switch，判断不同状态的行为时，使用状态模式可以大大简化代码结构。

  • 例如，电商系统中根据订单状态（如待付款、已发货、已收货等）做不同操作。
