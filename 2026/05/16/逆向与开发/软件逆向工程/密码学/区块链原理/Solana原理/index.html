Solana原理

数据结构

区块结构

Slot 和 Epoch

  • Slot 是 Solana 网络中的一个时间单位。每个 slot 大约持续 400 毫秒。可以把 Slot 想象成一个时间段，预期在这个时间段内会生成一个区块。
  • Epoch 是一组连续的 slot 的集合。在 Solana 中，通常 1 Epoch 包含 432,000 个 slots，持续时间大约为 两天（具体时间取决于网络的交易量和验证器的速度）。

领导者计划表

在每个 Epoch 的开始时，Solana 会根据网络中各个 验证器（Validator） 的 权益大小（Stake） 来确定谁将在特定的 slot 中充当 领导者（Leader）。这意味着验证器拥有更多的 SOL 代币（通过质押Staking）会有更高的概率被选为领导者。

  • 领导者的角色： 当一个验证器被选为某个 slot 的领导者时，它负责在这个时间段内生成一个区块。即，领导者 负责为该 slot 创建并验证一个新区块，并将这个新区块广播到网络中。

领导者的任务

  • 收集交易： 当某个 slot 到达时，所有的交易会被转发给指定的领导者。领导者将收集在这个时间段内收到的交易，执行这些交易并将其打包成区块。
  • 交易选择与排序： 领导者有权决定哪些交易包含在区块中以及如何排序这些交易。换句话说，领导者不仅决定是否包含某个交易，还能决定区块内交易的顺序。

传播区块：Entries 和 Shreds

传统区块链的区块生产模式

在传统的区块链系统中，区块通常是一个单一的实体，生成一个区块后，必须等待下一个区块生产者接收整个区块并进行处理。处理过程包括：

  • 接收完整区块；
  • 处理区块中的所有交易；
  • 然后再基于该区块继续生成下一个区块。

这种模式会导致 显著的延迟和性能瓶颈。由于每个节点需要等待接收到完整的区块数据才能开始处理交易，因此存在以下问题：

  • 网络延迟：传输完整区块需要时间。
  • 处理延迟：节点必须处理完整的区块后，才能继续构建下一个区块。
  • 分叉问题：如果区块生成得太快，节点没有足够时间处理之前的区块，会导致网络分歧或共识失败。

这种机制可能导致 区块生成周期变长，进而影响区块链的吞吐量和响应速度。

Solana 的区块生产机制

Solana 采用了一种 创新的流式传输 方法，通过 分块 和 提前传播，最大限度减少区块传播过程中的延迟。具体流程如下：

区块分解为 Entries 和 Shreds：

  • Entries：Solana 在区块生产过程中，将区块分解为更小的部分，称为 entries。每个 entry 都包含一组交易数据。这些交易在领导者生成区块时，立即开始流式传输到网络的其他节点，而不是等到完整的区块生成后再发送。
  • Shreds：entries 进一步被划分为更小的单位，称为 shreds。这些 shreds 是数据传输的基本单元，在网络中传播以减少数据传输时的延迟。

流式传输：

在 Solana 中，区块生成的过程是流式的，也就是说，在区块完全生成之前，领导者就会开始将区块中的 entries 流式传输到网络中的其他节点。这样，其他节点在区块还没有完全生成时，就能提前开始处理这些数据。这种机制使得节点在接收到部分数据时，就可以开始执行交易处理，而不需要等到整个区块完成后再开始处理。

区块的定义

在 Solana 中，区块 被定义为领导者在某个 slot 内生成的所有 entries 的集合。这些 entries 被传输到其他节点，而节点无需等待完整区块数据完成后再开始处理，从而大幅降低了网络延迟。

唯一的延迟：唯一的延迟来自于 最终数据包的网络传输延迟，即在所有 shreds 到达其他节点之前存在的物理网络限制。然而，一旦数据包到达，节点几乎可以立即开始处理区块中的交易。

账户模型

在 Solana 上，所有数据都存储在称为账户的结构中。每个帐户都可以通过其唯一地址进行识别，地址以Ed25519算法生成32个字节的公钥来表示。您可以将地址视为帐户的唯一标识符。

账户与其地址之间的这种关系可以看作是键值对，其中地址用于定位账户相应链上数据。

  • data：存储账户状态的字节数组。如果账户是一个程序（智能合约），则存储可执行程序代码。该字段通常称为“账户数据”。
  • executable：一个布尔标志，指示该账户是否是一个程序。
  • lamports：账户余额的数字表示，单位为 lamports，这是 SOL 的最小单位（1 SOL = 10 亿 lamports）。
  • owner：指定拥有账户的程序的公钥（程序 ID）。

程序

原生程序

在 Solana 上，程序（Program）是执行特定功能的核心组成部分。

程序类型 描述 功能
系统程序（System Program） 默认情况下，所有新账户由 System Program 所拥有。 负责账户创建、空间分配和账户所有权的转移。系统程序是 Solana 网络的核心，管理基本账户操作和交易费用支付。
BPF 加载程序（BPF Loader） 负责管理和执行所有自定义程序。 部署、升级和执行用户自定义程序。它是所有非原生程序（如用户自定义程序）的“拥有者”。
Sysvar 账户 特殊账户提供对集群状态数据的访问。 存储和更新网络集群的状态信息，帮助用户读取网络的实时数据（如租金、区块时间等）。

用户自定义程序

程序账户（Program Account） 代表链上程序的账户，存储可执行字节码的地址以及更新权限。 是程序的主账户，通常用于存储指向可执行字节码账户的地址和程序的更新权限。可以通过此账户调用程序。
可执行数据账户（Executable Data Account） 存储程序的可执行字节码的账户。 包含程序的实际字节码，一旦程序部署或升级，字节码存储在此账户中。
缓冲账户（Buffer Account） 临时账户，用于存储程序部署过程中的字节码。 在程序部署或升级期间使用，字节码会暂时存储在此账户，直到部署完成后，字节码会被转移到可执行数据账户，缓冲账户则关闭。
数据账户（Data Account） 存储程序运行时的数据，Solana程序是无状态的，因此需要单独的账户存储数据。 用于存储和修改数据，数据账户的所有权由程序控制，可以存储由程序定义的任意数据。每个程序可以定义自己的数据格式和内容。

关键注意点：

  1. 程序账户与数据账户分开存储： 在 Solana 中，程序代码和程序的数据是分开存储的，这使得程序可以独立升级，而不影响存储的数据。这种设计有助于提升合约升级的灵活性。
  2. 账户所有权转移： 系统程序可以创建新账户，但它可以将账户所有权转移给任何自定义程序，允许用户创建和管理自己的程序数据。

POH

每个交易都经过 SHA-256 处理，这是一种以其能够接受任何输入并生成唯一、不可预测输出而闻名的加密哈希函数。当一个交易被哈希时，其输出成为下一个交易哈希的输入。这个过程在哈希输出中建立了交易的内置顺序，形成了一个长而连续的链。

PoH（历史证明）利用了可验证延迟函数（VDF），它在区块链中验证时间流逝的重要性。VDF 是计算密集型的函数，不仅依赖于先前的哈希，还包含经过的时间。这个机制允许 Solana 以加密的方式展示真实时间已经过去，生成连续的输出。因此，存在清晰、可验证的交易顺序，确保了一致的事件时间轴。验证者因此可以轻松验证经过的时间有多长，进一步增强了网络的可信度。

Tower BFT

Tower BFT 是 Solana 用于实现高效共识的一种 拜占庭容错机制。

Tower BFT 是一个类似于 pBFT 的共识算法，旨在利用来自Proof-of-History 的同步时钟计算。这在网络中建立了一个统一的时钟，使其能够有效地跳过那些缓慢或未响应的领导者分配的槽。这个过程消除了网络为每一个槽经历同步共识轮次的必要性，并使得连续的区块生成成为可能，因为验证者不必等待先前的区块到达再构建下一个区块。

PoS

尽管 Proof of History (PoH) 提供了区块生成的时间顺序，Solana 依然使用 Proof of Stake (PoS) 来保证网络的 安全性 和 去中心化。在 Solana 的网络中，验证者通过质押 SOL 代币来保障一切 — 本质上是将它们锁定为“押金”，以表明他们的承诺。他们质押的 SOL 越多，被选中验证交易并赚取奖励的机会就越大。这有点像赚取信任积分，使每个人都保持诚实并有动力确保网络安全。

激励机制

质押奖励

在 Solana 网络中，质押奖励 是 验证者 和 委托人 因参与网络验证和维护而获得的奖励。Solana 采用 Proof of Stake (PoS) 共识机制，通过 SOL 代币的质押 来选择验证者，并激励他们参与区块验证和交易确认。

  • 验证者奖励：作为 区块生产者，验证者通过验证交易和生成新区块来获得 质押奖励，通常以 SOL 代币的形式发放。
  • 委托人奖励：那些将自己的 SOL 代币委托给验证者的用户，也能分享验证者所获得的奖励。委托人根据他们委托的 SOL 数量，按比例分得验证者奖励的一部分。

Solana 的质押奖励机制使得网络中的参与者（包括验证者和委托人）都能从区块奖励和交易费用中受益，从而激励更多的用户参与到区块链的维护和治理中。

质押的惩罚

在 Solana 网络中，质押不仅是获取奖励的途径，也伴随着一定的风险。如果验证者出现不当行为或者没有按时完成任务，会受到 惩罚。

  • 离线惩罚：如果验证者在其被分配的 slot 时间内未能验证交易或生成区块，Solana 会对其进行 离线惩罚，即减少其抵押的 SOL 数量。这通常是由于验证者的节点出现故障、断线或其他原因导致的失误。
  • 恶意行为惩罚：如果验证者进行恶意操作（例如双重签名，尝试篡改交易记录），Solana 会对其进行更严重的惩罚，部分质押的 SOL 会被 削减（也称为 Slashing）。这种惩罚是为了防止网络攻击和保证网络的诚信。

质押惩罚机制是为了保持验证者的诚实性，确保他们始终按要求验证区块，且保持高水平的网络参与度。如果验证者的行为不端，质押奖励就会被削减，甚至失去其质押的代币。

交易费用

交易费用 是 Solana 网络上每笔交易所需支付的费用。Solana 的交易费用相对较低，这是其设计中的一个重要特性。

  • 费用目的：交易费用的主要作用是 防止垃圾交易 和 激励验证者 处理这些交易。每笔交易的费用会被 分配给验证者，作为他们处理这些交易的回报。
  • 费用计算：交易费用的计算是 动态的，取决于网络的拥堵情况。在 Solana 的设计中，每笔交易的费用都非常低，一般在 几美分 左右，这使得 Solana 非常适合处理高频交易和大规模的去中心化应用（dApp）。

尽管 Solana 的交易费用较低，但它仍然是网络中 激励验证者 和 防止垃圾交易 的一种手段。

租金

租金 是 Solana 网络上用于存储数据的费用。与以太坊等其他区块链相比，Solana 对存储的收费方式独具特色。

  • 存储空间的费用：在 Solana 上，数据存储并不是免费的。如果一个账户或程序占用了存储空间，Solana 会对这些存储空间收取一定的租金。这是为了确保网络中的每个账户都为其占用的存储空间付费，从而防止垃圾数据和无用账户占用资源。
  • 租金机制：
    • 租金的计算方式基于 账户存储的字节数。每个账户或程序都需要支付一定的费用来 维持其存储空间。如果账户余额不足以支付租金，Solana 会自动删除该账户或程序。
    • 租金通常以 SOL 代币支付，支付方式是定期的。账户需要持续存储足够的 SOL 来支付租金，否则这些账户的存储空间会被回收。
  • 避免垃圾存储：租金机制的引入确保了网络资源不会被浪费，防止了无效数据占用存储空间。租金的征收使得参与者更加注重存储的效率和必要性，有效优化了 Solana 网络的存储资源。

所有的 租金收入 将被 分配给网络中的验证者，作为他们参与网络维护和提供存储空间的回报。

租金收入的分配与 验证者的权益（staking） 相关，验证者根据其质押的 SOL 数量 和参与网络维护的程度，按比例分得租金收入。

网络传播

Gulf Stream

传统内存池（Mempool）的问题：

  • 在传统的区块链系统（如比特币、以太坊）中，交易首先被提交到 mempool（内存池），这是一个由节点维护的交易队列。矿工或验证者从 mempool 中选择交易，打包成新区块。
  • 问题：这种设计虽然简单，但是会导致 交易的延迟 和 拥堵，尤其是在网络流量较大时，mempool 中的交易会积压，导致交易确认时间延长，处理效率低下。

Gulf Stream 的具体工作原理

  • 交易传播：当一个用户在 Solana 网络上发起交易时，这个交易并不会像传统区块链那样进入一个临时存储池（mempool）。而是直接广播给网络中的多个验证者节点，验证者会在接收到交易时立即进行验证。
  • 区块生成：一旦一个验证者收到了足够的有效交易，它就会将这些交易打包到当前的区块中。Solana 采用了 并行处理 的机制，在交易传播过程中，所有验证者都能够 并行验证 不同的交易，从而减少了交易确认的延迟。
  • 去除内存池的需求：由于交易直接广播给验证者，而不需要通过传统的 mempool 队列，Gulf Stream 使得 Solana 不再依赖于内存池 来管理待处理的交易，从而减少了拥堵和延迟问题。

Gulf Stream 的创新：

  • Gulf Stream 是 Solana 的一种机制，它通过让交易直接 流式传输 给验证者，而不是先进入一个集中管理的 mempool 队列，来避免交易排队等待的延迟问题。
  • 在 Solana 中，交易一旦生成，立即广播给所有验证者节点，并且交易会直接被验证者接收和验证。这就避免了 mempool 排队 造成的延迟。

Turbine 协议

Turbine专门设计用以减轻领导者向网络发送数据的压力。

与传统的区块链不同，传统的区块链会按顺序或以洪泛的方式发送到所有节点，Turbine 采用更加结构化的方法来最大限度地减少通信开销，并减少各个节点的负载。在高层，Turbine 将一个块分解成更小的块，并通过节点层次结构传播这些块。在这里，单个节点不需要与所有其他节点联系，而只需与选定的几个节点进行通信。

随着网络规模的扩大，这一点变得越来越重要，因为传统的传播方法由于必要的通信量巨大而变得难以维持。因此，Turbine 确保了数据在 Solana 中快速高效的传播。区块传播和验证的速度对于维持 Solana 的高吞吐量和网络安全至关重要。

此外，Turbine 解决了数据可用性问题，确保所有节点都可以访问所需的数据，以有效地验证交易。这是在不需要大量带宽的情况下完成的，而这是其他区块链网络中的常见瓶颈。

当领导者构建并提出整个区块时，实际数据作为_shreds_（部分区块）发送到网络中的其他验证者。Shreds是验证者之间发送的原子单位。

从高层来看，Turbine将shreds发送给预定的验证者集合，这些验证者再将这些shreds中继到新的一组验证者。

Turbine树

Turbine树是Solana用于促进shreds（编码区块数据）在验证者之间高效传播的结构化网络拓扑。一旦shreds成功编码到相应的shred组中，它们就准备通过Turbine树进行传播，以通知网络中的其他验证者最新状态。

SVM原理

SVM 是 Solana 的虚拟机的高层次框架，它定义了整个交易处理管道和程序执行流程，并且包括了特定的指令集架构（SVM ISA）和系统调用（syscalls）。

rBPF 是 Solana 实现的 eBPF 虚拟机，负责执行编译后的 eBPF 程序。在 Solana 中，rBPF 是用于执行智能合约的实际虚拟机。

SVM 和 rBPF 的关系是：SVM 是一个更广泛的概念，涉及 Solana 的整个交易和程序执行流程，而 rBPF 是实现这一流程的 虚拟机引擎。

Solana 程序通常使用 Rust 编写，然后通过 Solana 平台工具编译为 eBPF。然而，程序也可以用 Zig、C 或汇编语言编写。平台工具确保程序编译到适当的 eBPF 格式，同时遵守 Solana VM 施加的 eBPF 限制

rBPF 与传统 eBPF 虚拟机

1. eBPF 的基本概念

  • eBPF（Extended Berkeley Packet Filter） 是一种高效的 虚拟机，它最初是用于操作系统内核中进行网络数据包过滤。eBPF 程序可以在内核中执行，但它们受到严格的限制，不能执行某些可能危害系统稳定性的操作。
  • eBPF 虚拟机：eBPF 程序在执行时受到虚拟机的约束，执行的是一组指定的低级指令，保证了程序的安全性和效率。它通常运行在 内核空间，以执行网络监控、安全检查等任务。

2. rBPF 的介绍

  • rBPF（Rust Berkeley Packet Filter）是一个 用 Rust 编写的 eBPF 虚拟机实现，它遵循 eBPF 的基本设计原则，但并不局限于运行在内核中，而是可以在 用户空间 中运行。
  • 用户空间与内核空间的区别：
    • 内核空间 是操作系统内核的一部分，直接与硬件交互，具有更高的权限和能力。
    • 用户空间 是操作系统中的应用程序运行区域，相比内核空间，它的权限更有限，操作也受到更严格的控制。
    • rBPF 是在 用户空间 运行的虚拟机，这对于 Solana 来说非常合适，因为 Solana 的验证者节点程序（即执行程序的运行时）也运行在用户空间。

3. rBPF 在 Solana 中的应用

  • Solana 和 rBPF：Solana 使用 rBPF 作为其程序执行的核心虚拟机（VM）。在早期，Solana Labs 将 rBPF 从原始的实现中分叉出来，并对其做了 定制修改，以支持 Solana 特有的功能和要求。这个修改后的版本被称为 Solana rBPF，它被用于 Solana 验证者节点 上执行智能合约（程序）。
  • SVM（Solana Virtual Machine）：虽然在 Solana 的开发者社区中，大家习惯性地将整个交易处理管道或执行层称为 “SVM”，但实际上 SVM 指的是 Solana 虚拟机指令集架构（SVM ISA）所定义的 eBPF 虚拟机。也就是说，SVM 是 Solana 运行时的一个总体概念，指代了包括交易处理和程序执行的整个执行过程，而 rBPF 则是执行这些程序的具体虚拟机。

4. rBPF 与纯正 eBPF 的区别

  • 内核 vs 用户空间：

    传统 eBPF 运行在内核空间，主要用于网络数据包过滤、性能监控和安全性分析等任务。rBPF 运行在 用户空间，这使得它更适合于 Solana 的要求，因为 Solana 的节点（验证者）运行时是在用户空间中。

  • 针对 Solana 的定制：

    Solana 在 rBPF 的基础上进行了 定制化修改，添加了 Solana 特有的功能，以支持智能合约的执行。Solana 使用了 SVM ISA（Solana 虚拟机指令集架构）来约束 rBPF 程序的行为，使得它们符合 Solana 网络的需求，例如在网络上进行交易的处理和智能合约的执行。此外，Solana 的虚拟机还支持对一些 系统调用（syscalls） 的访问，这些调用是 Solana 协议定义的低级操作，用于与网络、存储等其他系统组件进行交互。

Firedancer 是 Solana 项目的另一个重要部分，它是一个 完全重新实现的虚拟机，遵循了 Solana 的 SVM ISA。与 rBPF 不同，Firedancer 是一个新的虚拟机实现，旨在提高性能和可扩展性，但它仍然遵循与 rBPF 类似的设计思想，并与 Solana 网络兼容。

Solana网络的节点，称为验证者，每个节点都运行自己的Solana虚拟机（SVM）独立环境，以在区块链上保持共识。当部署智能合约时，它会将所需的状态变化传达给运行时。Solana运行时将这些状态变化转发给每个验证者系统内运行的SVM实例。所有验证者节点都会接收到并翻译这些变化，更新区块链。

这些SVM实例可以看作是执行必要操作的小型计算机，根据交易提供的指令更新Solana网络的状态。

SVM（Solana Virtual Machine）

SVM 这个术语常常被用来描述 Solana 网络的虚拟机，即用于执行交易和智能合约的整个执行环境。它是 Solana 运行时的一部分，负责在节点上执行智能合约（Solana 程序），处理交易、验证交易的有效性以及更新区块链状态。

SVM 不仅仅是一个虚拟机，它实际上包括整个 交易处理管道 和 执行层，也就是说，SVM 涉及了如何将交易从接收、验证到最终执行和区块生成的所有处理步骤。

  • 实际上，SVM 是基于 eBPF（扩展伯克利数据包过滤器） 的虚拟机架构，其目的是提供一个高效且安全的环境来执行程序。这个虚拟机执行的是符合 Solana 协议约束的 eBPF 程序。

SVM 和 rBPF 的关系

  1. SVM 和 rBPF 都是基于 eBPF 的执行环境：

    • SVM 作为 Solana 的虚拟机体系，实际上是建立在 eBPF 虚拟机（rBPF）的基础上的。SVM 通过 rBPF 虚拟机执行 Solana 程序（智能合约），并受到 Solana 自定义的虚拟机指令集架构（SVM ISA）的约束。
    • rBPF 是实现 eBPF 执行的工具，而 SVM 是使用 rBPF 来完成智能合约执行的整体框架。

  2. rBPF 是 SVM 的核心执行引擎：

    • rBPF 是一个 eBPF 虚拟机，负责执行 Solana 网络中的 eBPF 程序（即 Solana 智能合约）。这些程序可以用 Rust、C、Zig 等语言编写，然后通过 Solana 的工具编译成 eBPF 字节码。
    • SVM 的实际操作和执行是由 rBPF 虚拟机 执行的。SVM 定义了一个程序的执行过程和网络的协议约束，而 rBPF 实际上是运行这些程序的虚拟机。

  3. SVM 和 rBPF 的协同工作：

    SVM 是一个 高层次概念，它定义了 Solana 中的程序执行环境，包括交易处理管道、区块链状态的更新和程序执行的所有步骤。而 rBPF 则是 SVM 实现的一个具体的虚拟机，它负责在 Solana 节点上执行 eBPF 程序，即执行智能合约的具体指令集。

    SVM 负责确保程序符合 Solana 的运行时规范，并控制程序的执行流，而 rBPF 则负责实际的指令执行和资源管理。

  4. 系统调用（syscalls）：

    在 rBPF 虚拟机中，执行的程序会依赖于 Solana 协议定义的系统调用（syscalls）。这些系统调用为程序提供访问外部资源和执行协议层操作的能力。

    SVM 指定了这些系统调用，并通过 rBPF 执行它们。这使得 rBPF 能够在虚拟机中执行更复杂的操作，而不仅仅是简单的计算。

  5. Firedancer 与 rBPF：

    Firedancer 是 Solana 的另一个虚拟机实现，与 rBPF 的区别在于，Firedancer 是 完全重新实现的虚拟机，它也遵循了 SVM ISA，但它采用了不同的设计和优化。

    • Firedancer 是为 Solana 提供更高性能的虚拟机，它与 rBPF 类似，但不完全相同，并且专注于提升执行效率。

Sealevel引擎

SVM的关键组件是Sealevel引擎。Sealevel引擎通过允许多个智能合约同时运行而不影响彼此的性能，实现了Solana执行环境内的“水平”扩展，即并行处理。是 Solana 网络中用于处理并行交易执行的 并发引擎，它是 Solana 提供高吞吐量和低延迟的关键技术之一。Sealevel 使得 Solana 能够在同一时间并行处理多个交易，从而极大地提高了交易处理能力。

Sealevel 的核心概念

  1. 并行交易执行：

    在传统区块链系统（如以太坊）中，所有的交易必须按照先后顺序依次执行，这限制了交易的吞吐量。每个交易都必须等到前一个交易执行完才能继续执行，这就导致了处理效率低下。

    Sealevel 引入了 并行交易执行，它允许多个交易同时进行处理，显著提升了系统的吞吐量。Solana 通过分析交易之间的依赖关系，能够决定哪些交易可以并行执行，哪些交易必须顺序执行。

  2. 事务的并行性：

    Sealevel 引擎的工作原理基于事务的 数据依赖性分析。每个交易涉及的账户和数据可以被视为一组资源。Sealevel 通过分析这些资源的访问模式，确定哪些交易是独立的（即可以并行执行），哪些交易之间存在依赖关系（需要顺序执行）。如果多个交易不访问同一账户或同一数据，那么它们可以同时执行（并行）。如果交易访问了相同的账户或数据，它们则必须按照顺序执行。

  3. 状态和账户锁定机制：

    在 Sealevel 中，交易的执行是基于 账户 或 数据 的锁定机制的。当交易需要访问某个账户的数据时，Sealevel 会 锁定 该账户，确保同一时刻只有一个交易可以修改它。通过智能的账户锁定机制，Sealevel 可以保证交易的一致性和完整性，同时避免竞争条件（race conditions），并确保并行执行不引入错误。

  4. 优化并行度：

    Sealevel 对多个交易之间的依赖关系进行 静态分析，通过标识哪些交易之间相互独立，哪些需要按照顺序执行，进一步提高了并行度。这种优化减少了无效的等待时间，从而提升了吞吐量。

Sealevel 的工作原理

  1. 交易执行流程：

    每个交易都会被解析并确定它所涉及的账户和数据。如果交易中涉及多个账户，Sealevel 会检查这些账户是否有冲突或是否可以并行执行。在 Solana 中，交易的执行并不依赖于传统的单一事务执行模型，而是通过并行化计算来提升性能。Sealevel 会通过对 资源访问冲突的检查 来决定哪些交易可以并行，哪些交易需要排队等待。

  2. 并行性分析：

    Sealevel 使用的 并行性分析 是基于 账户访问分析，也就是说它在执行前通过检查交易所访问的账户是否重叠来判断是否可以并行执行。

    • 比如，如果两个交易都修改不同的账户（没有交集），则这两个交易可以并行执行；但如果两个交易都修改相同账户的数据，那么它们就必须顺序执行。

  3. 并行事务处理：

    Sealevel 不仅可以识别不同交易之间的独立性，还能根据节点的硬件资源进行优化，在多核 CPU 上并行执行交易，进一步提高吞吐量。

    集群中的并行化执行：Solana 网络中的多个验证者节点可以并行执行多个交易，通过高效的通信和共识机制，最终合并每个节点处理的结果。

SVM是多线程运行环境，利用验证者机器的所有核心并行处理多笔交易，使Solana随着硬件改进而更有效地扩展。SVM架构还改进了交易费用管理，开发了本地化费用市场，每个智能合约单独分配费用

概念

在 Solana 中，程序执行的存储空间（即智能合约的执行环境）与以太坊的 EVM 不同，主要通过 账户模型 进行管理。Solana 的存储体系不再细分为栈、内存和存储，而是通过以下几种存储结构来管理链上数据：

1. 账户（Account）

  • 账户 是 Solana 中存储数据的基本单位。Solana 网络的所有数据（包括智能合约状态、交易数据、资产余额等）都存储在账户中。

    每个账户都有一个 数据字段，这通常是智能合约的状态数据。Solana 的程序会使用这些账户来存储执行状态、用户数据、交易结果等信息。

    账户中存储的数据结构可以是任何类型的应用程序数据，通常是以字节数组的形式存储，智能合约程序会根据自己的需求对这些字节进行解析。

2. 程序账户（Program Account）

  • 程序账户 存储 Solana 程序（即智能合约）的执行代码。这些程序账户包含了编译后的可执行字节码（即智能合约代码），并通过 Solana 网络中的 BPF（Berkeley Packet Filter）虚拟机 执行。

    这个账户本质上是智能合约的部署位置，程序账户的地址通常被称为 Program ID，它用来标识程序并执行合约逻辑。

3. 数据账户（Data Account）

Solana 的 数据账户 存储程序状态。这些账户由程序控制，并且可以通过 程序账户 来修改。智能合约需要额外的账户来存储它的状态信息，通常在智能合约执行时通过 System Program 创建数据账户并将其与智能合约绑定。

这些账户通常有固定的存储空间，以适应程序的状态需求。不同的智能合约可能需要不同的数据账户，每个账户存储与合约相关的不同类型数据。

4. 内存（Memory）

在 Solana 中，内存 并不像 EVM 中那样是一个单独的抽象层。Solana 程序在执行时，使用 Solana 的 Rust 或其他语言的运行时内存来处理局部计算和临时数据存储。该内存是运行时的一部分，且由执行环境本身管理。需要注意的是，Solana 的程序执行是 无状态 的，程序本身并不直接管理永久性的内存数据，所有状态数据必须存储在外部的 账户 中。

5. 交易（Transaction）

Solana 的交易本身也包含了可执行的程序调用和数据传输，交易是由多个账户参与的，交易内的数据是程序执行时的输入（包括 用户账户 和 程序账户 中的数据）及输出。执行的结果会写入相关的账户（数据账户）。

6. 程序状态（Program State）

每个智能合约会通过 数据账户 来存储它的状态。这些状态是由程序账户创建和管理的，并且可能会被多个交易修改。状态存储 是由程序账户定义的，当某个智能合约需要读取或修改状态时，程序账户会确定哪些数据账户可以访问或更新。

Solana 存储模型的特点

  1. 无状态程序：

    Solana 的智能合约本质上是 无状态 的。也就是说，Solana 程序本身不保存自己的状态，所有的状态数据都保存在外部的账户中。这与以太坊的 EVM 存储模型有所不同，以太坊中的合约是有状态的，它们的状态直接存储在合约内。

  2. 高效的存储访问：

    Solana 的账户模型使得数据存储访问非常高效。智能合约（程序）可以通过操作账户来管理链上的状态，而这些操作不依赖于复杂的栈或内存结构。

  3. 灵活的存储设计：

    每个账户都是一个独立的存储单位，程序开发者可以根据需求定义每个账户的数据结构。这种模型灵活性较高，可以适应不同类型的应用需求。

Solana 程序的内存资源管理实际上是由节点的 操作系统 负责的。Solana 程序运行时在节点的内存空间中进行计算和临时数据存储。并且，这些内存资源不是由 eBPF 虚拟机本身管理，而是通过节点的操作系统进行分配。

与 EVM 不同，EVM 自身管理栈、内存和存储资源，Solana 的内存管理则通过节点操作系统和 eBPF 虚拟机进行协作管理。
