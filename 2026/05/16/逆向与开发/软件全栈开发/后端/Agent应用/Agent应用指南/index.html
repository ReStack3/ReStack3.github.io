Agent = LLM+ 记忆 + 规划技能 + 工具使用。

在之前的文章里我们简单聊过了：MCP协议(为agent赋能工具使用) 和 提示词工程(为任务进行规划)，而在本文中则重点聊一聊agent的记忆系统。

提示词工程

人与人之间的协作效率，很大程度上取决于沟通的质量——如何提问、如何描述需求、如何设定边界，决定了对方能否给出我们想要的答案。比如如何提问题？ / 提问的艺术和提问的艺术 (豆瓣)等书籍都着重描写如何提问

当把这种协作场景迁移到人工智能领域：与智能体（Agent）的交互，本质上也是一场对话，而对话的质量，同样取决于我们如何“沟通”。

这就是提示词工程（Prompt Engineering） 的核心价值——它不是简单的“问问题”，而是一门关于如何精准定义 Agent 角色、清晰描述任务目标、合理设定行为边界的艺术。

就像一位优秀的项目经理懂得如何给团队成员布置任务一样，优秀的提示词工程师懂得如何为 Agent 撰写“岗位说明书”。

提示词要素

指令：可以使用命令来指示模型执行各种简单任务，例如“写入”、“分类”、“总结”、“翻译”、“排序”等，从而为各种简单任务设计有效的提示。请记住，你还需要进行大量实验以找出最有效的方法。以不同的关键词（keywords），上下文（contexts）和数据（data）试验不同的指令（instruction），看看什么样是最适合你特定用例和任务的。通常，上下文越具体和跟任务越相关则效果越好。

具体性：要非常具体地说明希望模型执行的指令和任务。提示越具描述性和详细，结果越好。特别是当对生成的结果或风格有要求时，这一点尤为重要。不存在什么特定的词元（tokens）或关键词（tokens）能确定带来更好的结果。更重要的是要有一个具有良好格式和描述性的提示词。

避免不明确：给定上述关于详细描述和改进格式的建议，很容易陷入陷阱：想要在提示上过于聪明，从而可能创造出不明确的描述。通常来说，具体和直接会更好。这里的类比非常类似于有效沟通——越直接，信息传达得越有效。

做什么还是不做什么:设计提示时的另一个常见技巧是避免说不要做什么，而应该说要做什么。这样（说要做什么）更加的具体，并且聚焦于（有利于模型生成良好回复的）细节上。此外还需要注意：

  • 上下文：包含外部信息或额外的上下文信息，引导语言模型更好地响应。
  • 输入数据：用户输入的内容或问题。
  • 输出指示：指定输出的类型或格式。

提示技术

经过大量数据训练并调整指令的LLM能够执行零样本任务。指令调整本质上是在通过指令描述的数据集上微调模型的概念。

当零样本不起作用时，建议在提示中提供演示或示例，这就引出了少样本提示。少样本提示可以作为一种技术，以启用上下文学习

以下是在进行少样本学习时关于演示/范例的一些额外提示：

  • “标签空间和演示指定的输入文本的分布都很重要（无论标签是否对单个输入正确）”
  • 使用的格式也对性能起着关键作用，即使只是使用随机标签，这也比没有标签好得多。
  • 其他结果表明，从真实标签分布（而不是均匀分布）中选择随机标签也有帮助。

标准的少样本提示对许多任务都有效，但仍然不是一种完美的技术，特别是在处理更复杂的推理任务时。

链式思考(CoT)

核心思想：在少样本示例中，不仅给出问题和答案，还展示得出答案的中间推理步骤。这引导模型“一步一步地思考”。

效果：模型会效仿这个过程，先找出奇数（15, 5, 13, 7, 1），再求和（41），最后判断（41是奇数），从而得出正确答案 False。

自动CoT & 自洽性：

这是CoT的进阶技巧，旨在提升准确性和可靠性。

  • 自动CoT：在提示中不再提供人工编写的推理步骤，而是直接用一句神奇的指令（如 “让我们一步一步地思考”）触发模型自己的推理能力。这省去了构造示例的麻烦。
  • 自洽性：针对一个问题，让模型生成多条不同的推理链，然后从这些链得出的最终答案中进行多数投票。这有效减少了偶然的错误。

链式提示

注意：

  • 链式思考 是一种 提示设计技巧，用于改进模型单次推理的内容质量。
  • 链式提示 是一种 系统架构策略，用于将一个复杂任务拆分成多个模型调用步骤。

将一个宏大的、模型难以一步到位的任务，拆解成一系列有依赖关系的子任务，每个子任务由一个独立的提示和模型调用来完成。

  • 您提供的例子（文档问答） 是链式提示的经典案例：
    1. 提示1（子任务A：检索）：专门给模型下达指令：“从文档中提取相关引文”。模型执行并输出引文列表。
    2. 提示2（子任务B：生成）：将提示1的输出（引文） 和原始文档作为输入，再给模型下达新指令：“根据这些引文构建答案”。模型执行并输出最终答案。

思维树 (ToT)

核心思想：将一个复杂问题分解为多个步骤，在每一步，模型都生成多种可能的下一步，然后像在树结构中搜索一样，通过某种评分机制（如模型自我评分）选择最有希望的路径继续探索，直至找到最终答案。

ToT 维护着一棵思维树，思维由连贯的语言序列表示，这个序列就是解决问题的中间步骤。使用这种方法，LM 能够自己对严谨推理过程的中间思维进行评估。LM 将生成及评估思维的能力与搜索算法（如广度优先搜索和深度优先搜索）相结合，在系统性探索思维的时候可以向前验证和回溯。

思维分解与生成

  • 思维步骤：将一个大问题分解为多个、离散的中间推理步骤。例如，在“算24点”中，每一步就是一个中间方程。
  • 候选项：在每一步，不是只生成一个“想法”，而是并行生成多个（如5个）可能的下一步。这模拟了人类在遇到难题时会考虑多种可能性的过程。

状态评估与搜索

  • 启发式评估：使用大语言模型本身作为一个评估器，对每个候选思维进行前景判断（如 “sure/maybe/impossible”）。这为搜索提供了方向，可以优先探索最有希望的路径（“sure”），并果断剪枝无效路径（“impossible”）。
  • 搜索算法：通过经典的搜索算法（如 BFS、DFS）来系统地探索这棵“思维树”。这使得推理过程不再是一次性的盲目生成，而是一个有规划、可回溯的探索过程。

Hulbert (2023) 提出了思维树（ToT）提示法，将 ToT 框架的主要概念概括成了一段简短的提示词，指导 LLM 在一次提示中对中间思维做出评估。ToT 提示词的例子如下：

ReAct 框架

ReAct 是一种将 推理 和 行动 整合在一起的范式，旨在让大语言模型在解决复杂问题时更加可靠和可控。模仿人类解决问题的过程：我们不会盲目行动，而是先思考一步（Reason），然后采取行动（Act），根据行动结果再继续思考，如此循环，直到解决问题。

ReAct = Reason + Act

  • Reason：模型生成对当前情况的推理，解释它正在做什么、为什么这么做，以及下一步计划。这类似于 CoT，但更侧重于规划。
  • Act：模型执行一个具体的动作。这些动作通常是可执行的、受限制的.

将每次工具返回结果作为下一次思考的上下文+系统预设置的提示词输入给llm进行思考调用

注意ReAct只是一种agent设计思想，而不是一种框架

  • 思考（Reason）‌：代理基于当前上下文生成推理步骤（如是否需要调用工具、选择哪个工具）。借鉴“Chain-of-Thought（思维链）”，让模型先“自言自语”地分析问题。
  • ‌行动（Action）‌：根据推理结果，调用工具执行操作（如 API、计算器、搜索）或生成自然语言响应。
  • ‌观察（Observe）‌：获取工具执行结果或用户反馈，更新上下文。
  • 循环上述步骤直至任务完成‌。

由于每次工具调用都会将结果拼接到提示词上下文中中整体返回给大模型。LLM 没有记忆，它需要每轮都看到“过去做过什么”。拼接后的上下文能让 LLM 进行“链式推理”而非盲目重复调用工具。这也是 ReAct 比单步工具调用更智能的根本原因。

所以系统提示词里，不要写死 Thought / Action / Observation / Final Answer 的内容模板或范例中具体的推理结果。因为在 ReAct 框架中，这些字段（Thought: ... / Action: ...）会在每次 LLM 调用后自动拼接到输入上下文中。
如果系统提示词中“硬编码”了这些推理步骤，LLM 会被误导，以为要重复执行相同的工具调用，从而陷入死循环。

初次使用时我犯了一个：“教模型思考”的错误，错误地在系统提示词中放入具体范例

导致 不断循环执行 get_price → 拼接 → 再次执行 → 死循环。所以在系统提示词中只需定义角色功能和思考模式即可

结构化输出：默认的 ReAct 是“纯文本推理链”，输出是自然语言字符串，return_direct: bool = True

自动提示工程师 (APE）

如果说 ReAct 和 CoT 是让人来设计更好的提示，那么 APE 的目标是 让模型自己来设计最好的提示。

核心思想：将“寻找最优提示”本身定义为一个优化问题，并使用大语言模型作为搜索算法的主体来解决它。

工作流程：

  1. 指令生成：给定一个任务描述和几个示例，让一个大语言模型（作为“指令生成器”）生成大量候选的指令/提示。
  2. 指令评估：让另一个大语言模型（作为“评分器”）在验证集上运行这些候选指令，并根据任务目标（如准确性）对它们的表现进行评分。
  3. 指令选择：选择得分最高的指令作为最终结果。

APE 示例：

  • 任务：让模型执行“情感转换”——将负面评论重写为正面评论。
  • 初始想法：人工可能会设计提示为：“请将以下负面评论改写为正面评论，同时保持原意。”
  • APE 过程：
    1. 生成：模型可能会生成多种候选指令，例如：
      • “用积极的语气重写这个。”
      • “把这个抱怨变成赞美。”
      • “进行情感转换：负面 -> 正面。”
      • “写出这个句子的反面，但说的是同一件事。”
    2. 评估：在一批负面评论上测试这些指令，看哪个指令产生的正面评论最准确、最自然。
    3. 选择：假设评估发现 “写出这个句子的反面，但说的是同一件事。” 得分最高，那么这个指令就被 APE 选定为最优提示。

APE 的价值：

  1. 超越人类直觉：模型可能会发现人类想不到的、更有效或更鲁棒的提示方式。
  2. 自动化与规模化：为大量任务自动生成高质量提示，节省了大量人工试错成本。
  3. 发现新范式：有助于发现新的、可推广的提示策略。

检索增强生成 (RAG)

要完成更复杂和知识密集型的任务，可以基于语言模型构建一个系统，访问外部知识源来做到。这样的实现与事实更加一性，生成的答案更可靠，还有助于缓解“幻觉”问题。

为什么需要 RAG？解决大模型的三大痛点:

痛点 问题描述 RAG 的解决方案
知识幻觉 模型会自信地编造看似合理但完全错误的信息。 强制模型基于检索到的文档片段生成答案，言之有物，大大减少胡编乱造。
知识过时 模型的训练数据有截止日期，无法知晓最新事件。 知识库可以随时更新，让模型能够回答关于最新新闻、政策或产品的问题。
事实溯源 你无法知道模型的答案来自哪里，难以验证其真实性。 答案来源于具体的文档，可以提供引用来源，方便用户核对，增强信任。

RAG 是一种将 信息检索 系统与 大语言模型 相结合的技术架构。它的核心思想是：在让大模型回答问题之前，先从一个外部知识库中检索相关的信息，然后让模型基于这些确凿的依据来生成答案。

RAG 会接受输入并检索出一组相关/支撑的文档，并给出文档的来源（例如维基百科）。这些文档作为上下文和输入的原始提示词组合，送给文本生成器得到最终的输出。这样 RAG 更加适应事实会随时间变化的情况。这非常有用，因为 LLM 的参数化知识是静态的。RAG 让语言模型不用重新训练就能够获取最新的信息，基于检索生成产生可靠的输出。

自我反思(Reflexion）

自我反思是一个通过语言反馈来强化基于语言的智能体的框架。

在高层次上，自我反思将来自环境的反馈（自由形式的语言或者标量）转换为语言反馈，也被称作 self-reflection，为下一轮中 LLM 智能体提供上下文。这有助于智能体快速有效地从之前的错误中学习，进而提升许多高级任务的性能。

传统的提示技术是单向的：输入 -> 模型 -> 输出。而 Reflexion 技术引入了一个 “自我反思循环”：

核心目标：通过让模型进行自我反馈，显著提升其在复杂任务（尤其是推理和编程任务）上的准确性和可靠性。

  1. 生成初始答案：模型根据问题和指令，生成第一个版本的答案。
  2. 自我评估与反思：这是最关键的一步。模型被要求扮演一个“审阅者”或“批评者”的角色，基于特定的标准来审视自己刚刚生成的答案。常见的反思指令包括：
    • “检查你的答案中是否有计算错误或逻辑错误。”
    • “你的推理过程是否完整？有没有跳过必要的步骤？”
    • “你的结论是否符合常识？”
    • “如果你是老师，你会给这个答案打几分？为什么？”
  3. 决策与迭代：
    • 如果反思后没有发现严重问题，模型就输出当前答案作为最终结果。
    • 如果反思后发现了错误或不足之处，模型需要将这次的“反思内容”作为新的上下文，重新生成一个改进后的答案。这个循环可以进行多次，直到模型对自己满意为止。

向量数据库

传统数据库(Mysql/redis)可以类比图书管理员：如果想找一本关于“人工智能伦理”的书，得告诉管理员明确的关键词，比如书名或作者。管理员去一个精确的目录柜（索引）里找到匹配项，然后去对应的书架把书拿出来。如果书名里没有“人工智能伦理”，这本书可能就永远找不到了。

但是RAG知识库解决的是：大模型在回答用户时尽量减少幻觉。问题提问不是固定的，可预测的，这样的情况下：如何在海量数据中，快速找到“最相似”的那些项？

向量数据库解决这个问题主要分三步：

向量化（嵌入）

首先，它用一个叫“嵌入模型”的“翻译官”，把所有非结构化数据（如文本、图片、声音）都转换成一串很长的数字列表。这个列表就叫向量。
比如，“苹果”这个词可能被翻译成 [0.1， 0.3, -0.2， 0.5, ...， 0.8]。最关键的是，这个向量的位置在数学上代表了它的语义。意思相近的词（比如“苹果”和“梨”），它们在多维空间中的位置也离得很近。

这一步通常不由向量数据库本身完成，而是依赖像BERT、ResNet这样的深度学习模型。这些模型充当了“翻译官”，负责将原始数据转换成高质量的向量。

建立索引

数据量一大，在一个几十上百维的空间里，逐一比较这些长向量的距离，计算量是天文数字。所以，向量数据库需要建立一种特殊的索引，本质上是一种“预排序”或“高效过滤”机制，让你不必比较所有数据，就能快速锁定最相似的候选集。

这是向量数据库最核心的“黑科技”。它不能像传统数据库那样，只建一个B树或哈希索引，而需要特殊的算法来高效地寻找“邻居”。最流行的算法之一是 HNSW（分层的可导航小世界）。可以把它想象成一张城市的地铁+高速公路图：

  • 上层（高速公路）：稀疏的节点连接，让你能快速跨越到目标区域附近。
  • 下层（地铁/街道）：密集的节点连接，让你在目标区域里精确找到最近的点。
    通过这种方式，HNSW算法实现了“先快速定位，再精确查找”，兼顾了速度和准确性。

相似性搜索

当查询时，系统会把问题也转成向量，然后用这个向量去索引里快速查找，并计算它和候选集中向量的距离。距离越近，就代表越相似。最后，把距离最近的那些结果返回。

如何定义了如何计算两个向量之间的距离，也就是“像不像”。常用方法有：

  • 余弦相似度：更看重方向，常用于文本，衡量两个向量在方向上是否一致。
  • 欧氏距离：看重绝对位置，常用于图像，计算多维空间中的直线距离。

在大体理解了向量数据库的原理后，在后续的使用上大体也围绕着着三点完成。

检索增强生成

基本步骤

第一步：知识库准备与加载

这是最基础的一步，目标是把散落在各处的文档汇集起来。

  1. 数据源接入：连接企业内部的知识源，如Word、PDF、PPT、Excel、TXT等文件，或是Wiki、Notion、Confluence等在线文档，甚至是数据库里的数据。
  2. 数据加载：使用解析器读取这些不同格式的文件，将内容转化为纯文本。

第二步：文档预处理与分割

大模型和向量数据库无法一次性处理长篇的整本书，需要把长文本切成小的片段。

  1. 文本清洗：去除页眉页脚、特殊符号、多余的空格或无关的HTML标签，提高文本质量。
  2. 文本分割：按照一定的策略（如按段落、按句子、按固定字数）将文档切成一个个块。通常需要设置重叠窗口，让上下文保持连贯，避免在切分处丢失语义。

第三步：向量化与索引构建

这是为了让计算机能理解文本的语义，并快速找到相关信息。

  1. Embedding（嵌入）：调用嵌入模型，将上一步切好的文本块转换成高维空间中的向量。简单来说，就是把文字变成一串代表语义的数字。
  2. 存储到向量数据库：将这些向量连同原始的文本内容、文档来源等元数据，一起存入向量数据库中，并建立索引。

第四步：检索

当用户提出问题时，系统需要去知识库里找最相关的内容。

  1. 问题向量化：将用户的提问用同一个嵌入模型转换成向量。
  2. 相似性检索：在向量数据库中执行相似性搜索（余弦相似度或欧氏距离），找出与问题向量最相似的Top-K个文本块。
  3. 重排序：初步检索出的结果可能包含噪声。可以引入重排序模型，对结果进行重新打分和排序，把最相关的内容排在最前面。

第五步：增强生成与问答

最后一步是把找到的知识还给大模型，让它结合上下文给出答案。

  1. 构建提示词：将用户的问题 + 检索到的相关文本组合成一个完整的提示词。通常会加上明确的指令，比如“请根据以下上下文回答问题，如果找不到答案，就说不知道”。
  2. 调用大模型：将组合好的提示词发送给大语言模型。
  3. 生成答案：模型根据提供的知识生成答案，返回给用户。

在生产环境中搭建，除了以上5步，还需要关注：

  • 路由：根据问题类型（如闲聊 vs. 专业问题）决定是走RAG流程，还是直接调用大模型。
  • 多路召回：除了向量检索，结合关键词检索（如ES、BM25），混合取并集再排序，效果通常更好。
  • Query改写：对于复杂问题，先让大模型把问题拆解成几个子问题，或者把口语化的说法改写成书面语，再分别去检索。

召回率

在向量搜索中，召回率指的是系统返回的正确结果，占所有真正正确结果的比例。

  • 公式：系统返回的正确答案数 / 数据库中总共有多少正确答案

假设图书馆里有 100 本关于“人工智能”的书。

  • 方法 A（理想情况）：在目录中检索，找回了 80 本关于 AI 的书，而这 80 本确实都是关于 AI 的。另外 20 本 AI 书没有被找到。召回率 = 80%（80/100）
  • 方法 B（敷衍了事）：只在门口的书架上随便拿了 10 本关于 AI 的书。召回率 = 10%（10/100）

所以，召回率衡量的是检索系统是否“漏掉”了本该找到的内容。 召回率越低，说明漏掉的越多。所以RAG怎样提高召回率呢？我觉得可以从以下几点：

数据预处理层面（源头问题）

文本分割（Chunking）时

  • 块太小：比如一句话一个块。可能导致语义不完整，比如”李明的父亲”和”叫张伟”被切到两个块里，检索时只找到”叫张伟”，丢失了核心实体”李明”。

  • 块太大：比如一页一个块。可能包含太多冗余信息，导致向量被”平均化”，无法精确匹配到问题对应的细节。

  • 当文档中如果有大量无关的页眉页脚、广告、HTML标签、OCR错别字，这些噪音会污染向量表示。

向量化层面（语义理解问题）

这是核心中的核心。

  • 通用Embedding模型（如OpenAI的text-embedding-ada-002） vs. 特定领域模型。如果用通用模型处理法律、医疗等垂直领域文本，语义捕捉能力会下降。影响：模型没理解文本的真正含义，导致召回率天花板较低。
  • Embedding模型是静态的，而用户的问法千变万化（比如”车玻璃碎了” vs. “挡风玻璃破裂”）。如果模型语义泛化能力弱，可能无法把同义词联系起来。影响：因为用词不同，导致相关文档被漏掉。
  • 如果知识库是专业领域（如生物医药、金融研报），用通用Embedding模型，召回率会明显下降。需要微调Embedding模型或在领域数据上继续预训练。

索引与检索层面（算法与参数问题）

  • 如果知识库支持按时间、类别过滤（比如只查2024年的文档），但过滤逻辑写错了或者太严格，把正确答案排除在外，召回率会骤降。
  • 权衡索引提高速度和降低召回率之间的关系

查询处理层面（用户问题优化）

  • 问题太短/太模糊：用户问”它怎么样？”，代词”它”没有具体语义，Embedding模型很难找到对应的”它”指代的内容。

  • 问题包含错别字或口语化表达：如”引芹” vs. “引擎”，向量空间里距离很远。

  • 是否做查询优化：直接拿原始问题去检索 vs. 先用大模型把问题改写成更规范、更接近文档风格的句子。

记忆系统

类比于人类，记忆是指对信息的获取、存储、保持与后续检索过程。认知心理学通常将人类记忆划分为多种类型：

  • 感觉记忆（Sensory Memory）：对视觉、听觉等原始刺激的极短暂保留，持续时间通常只有几百毫秒到数秒，用于决定哪些信息进入注意阶段。

  • 短期记忆 / 工作记忆（Short-term / Working Memory）：保存当前意识中的信息，用于推理、决策与问题求解，容量有限（经典结论约为 7±2 个项目），持续时间约 20–30 秒。

  • 长期记忆（Long-term Memory）：可长期保存信息，容量巨大，进一步分为：

    • 显性 / 陈述记忆：包括情景记忆（个人经历）与语义记忆（事实与概念）；
    • 隐性 / 程序记忆：以技能和习惯的形式存在，如骑车、打字等自动化行为。

进一步思考可以发现：隐性/程序记忆体现为“无需思考即可执行的技能”。在 Agent 系统中，其对应形式通常不是显式存储的数据，而是：

  • 固化在 Prompt 模板中的行为模式（如 ReAct、Plan-and-Execute 结构）
  • 编排在 Agent 工作流图（LangGraph / AutoGen Flow）中的执行策略

以及模型本身在预训练阶段学到的隐含推理路径

虽然 AI Agent 并不存在生物学意义上的记忆结构，但在工程实现上，如果希望 Agent 具备连续对话能力、跨任务知识积累能力以及复杂规划能力，就必须构建一套在功能上对应上述记忆分层的存储与检索机制。因此，当前主流 Agent 框架通常将“记忆系统”拆解为如下三类：

记忆类型 描述 类比人类记忆 技术与实现
短期记忆（Short-term Memory） 保存最近的原始对话流与中间推理结果，是上下文的“滑动窗口缓冲区”。 对刚刚发生事件的即时记忆，对应人类的短期/工作记忆的瞬时部分。 通常就是 Prompt 中的历史对话窗口；实现上是固定长度的列表或 Token 截断策略，存储 (用户输入, Agent响应, 中间推理)。
长期记忆（Long-term Memory） 从多轮交互与多任务中抽取出的稳定知识与经验，用于跨会话复用。 对应人类的长期语义记忆与情景记忆。 核心是向量数据库 + Embedding 模型；将文本、事件、总结转成向量，通过语义相似度检索相关记忆。
工作记忆（Task / Working Memory） 为当前任务临时组装的“认知工作台”，整合所有与当前目标最相关的信息。 人类在解决问题时主动回忆并集中注意的信息集合。 一个临时数据结构，在任务开始时由调度器构建：= 当前指令 + 短期上下文 + 从长期记忆检索到的相关片段 + 工具返回结果。

从系统架构角度看：

  • 短期记忆 = 上下文管理问题
  • 长期记忆 = 信息检索问题（IR / RAG / 向量索引）
  • 工作记忆 = 任务编排与状态管理问题

这三者共同决定了 Agent 是否具备：

  • 连续对话能力
  • 跨任务学习能力
  • 多步规划与工具协同能力

结合上图，一个典型的工作流程如下：

  1. 记忆写入：
    • 原始记录：每一次与用户的交互都会被自动存入短期记忆。
    • 总结提炼：在对话间隙或任务结束时，系统会主动总结对话要点，并将关键信息（如用户偏好、重要结论）转化为向量，存入长期记忆（向量数据库）。
  2. 记忆读取（检索）：
    • 触发：当新的用户查询到来时，记忆系统被激活。
    • 多路检索：系统会同时进行：从短期记忆中获取最近的几条对话，保持话题连贯。将用户当前查询向量化，在长期记忆（向量数据库/关系数据库）中进行语义搜索，找到历史上相关的对话片段和知识。
  3. 记忆合成：所有检索到的信息（近期对话 + 相关长期记忆）被共同组装到工作记忆中，形成一份为当前任务定制的、完整的上下文背景。
  4. 决策与行动：这份丰富的工作记忆被作为上下文，与当前的用户问题和系统指令一同提交给大语言模型。LLM 基于这份“带有记忆的上下文”做出更精准、更个性化的决策和回答。

短期记忆

在 Agent 系统中，短期记忆是 Agent 在当前会话中维持上下文连贯性的核心机制。与长期记忆不同，短期记忆关注的是“此刻正在发生什么”，它决定了 Agent 能否理解对话的前后文、能否在多次交互中保持逻辑一致。短期记忆通常表现为：

  • 对话历史：最近 N 轮的用户输入和 Agent 响应
  • 中间变量：当前任务执行过程中的临时状态
  • 上下文引用：前文提到的实体、概念、待办事项

大语言模型（LLM）本身有一个上下文窗口（Context Window）的概念——它能够“看到”的输入文本长度有限。短期记忆的核心工作，就是在这个窗口内高效组织信息：

人的短期记忆会自然消退——不再关注的事情，很快就会遗忘。Agent 的短期记忆也需要类似的生命周期管理，避免无限膨胀导致上下文污染，减少token使用。

短期记忆与长期记忆的协同：

短期记忆中反复出现的信息，经过加工和巩固，逐渐存入长期记忆。比如让大模型对一定时间段中的短期记忆进行摘要处理，进行剪枝。

长期记忆

人类的学习与成长，离不开记忆的积累。一位资深的工程师，之所以能避开潜在的技术陷阱，是因为他经历过无数项目的教训沉淀。这种跨越时间的经验积累，让人类得以不断进步，而非每次都从零开始。

同样，一个真正智能的 Agent 系统，也不能只活在当下的对话中。它需要拥有长期记忆——能够记住过去的交互、积累过往的经验、沉淀历史的知识，让每一次新的任务都能站在之前的基础上前行。

在多 Agent 系统中，长期记忆可以实现：

  • 跨会话的连续性：当用户再次与系统交互时，Agent 能回忆起之前的偏好、历史决策和未完成的事项，提供真正的个性化体验
  • 知识的持续积累：多个 Agent 协同工作的结果、成功案例、失败教训，都可以沉淀为系统的集体智慧，让后续任务越来越高效
  • 故障恢复的保障：正如前文提到的，当某个 Agent 中途失败时，持久化的记忆让系统能够从断点恢复，而非功亏一篑

实践中，我觉得采用Redis和向量数据库是不错的选择

Redis：结构化记忆

Redis 作为高性能的内存数据库，是存储 Agent 结构化记忆的理想选择：

Redis 的优势：

  • 高性能读写，适合实时记忆存取
  • 丰富的数据结构（String、List、Hash、Set）适配不同记忆模式
  • 支持过期时间，便于管理会话生命周期

向量数据库：语义记忆

如果说 Redis 存储的是“结构化的事实记忆”，那么向量数据库存储的则是“语义化的经验记忆”——它能根据含义相似性检索相关内容，让 Agent 拥有真正的“联想能力”：

向量数据库的优势：

  • 语义检索：不需要精确关键词匹配，能理解含义相近的查询
  • 经验复用：过往成功的策略可以被相似场景的 Agent 检索调用
  • 持续学习：每次任务完成后的经验都可以沉淀为系统的集体智慧

混合架构

在实际生产环境中，推荐采用混合架构，让两类记忆各司其职：

记忆类型 存储方案 适用场景
会话状态 Redis 当前对话的上下文、未完成任务、临时变量
用户偏好 Redis 用户画像、历史偏好、个性化设置

经验知识 向量数据库 成功案例、失败教训、策略模式
故障恢复点 Redis 断点状态、检查点快照

思考规划

在现代 AI Agent 架构中，思考与规划系统是 Agent 的核心中枢，负责将外界输入、内部状态和可用工具转化为可执行的行动序列。其主要功能包括：状态建模、任务分解与规划、决策执行以及反馈闭环。

  • 具体实现上，首先 Agent 会通过短期记忆捕获当前上下文、通过长期记忆检索历史经验，并将这些信息汇总到工作记忆中形成完整任务视图；
  • 然后 Planner 模块根据当前目标、工具能力和约束条件，将复杂任务拆解为子任务或调用工具的指令序列；
  • 接着 Executor 模块根据 Planner 输出逐步执行任务，同时将执行结果反馈回工作记忆，形成闭环；

在高级 Agent 中，还可能引入 Reflection 或 Critic 模块，对 Planner 输出进行评估、修正和优化，确保决策合理性。工程上，这种思考与规划系统可以通过 Graph-based Workflow（如 LangGraph）、状态机（FSM）、行为树（Behavior Tree）或多 Agent 协作节点实现，每个节点负责不同子任务或工具调用，通过可组合的上下文协议（如 MCP）将记忆、工具和提示整合，从而支持复杂的连续对话、多任务学习和多步工具协作。

什么是MCP

如何让大语言模型高效、安全地访问和操作外部数据与工具？

传统上，AI开发者需要为每个应用场景编写大量定制化的连接代码，这种紧耦合的集成模式不仅开发效率低下，还导致了严重的系统碎片化。正是在这样的背景下，模型上下文协议应运而生，MCP本质上是一个开放协议，为AI应用定义了一套统一的外部资源访问规范，用于将 AI 应用程序连接到外部系统。

它创造性地构建了一个三层架构模型：

  • 在核心是MCP服务器，作为数据源和工具的标准化接口；
  • 上层是MCP客户端（通常是AI应用或界面），通过协议与服务端通信；
  • 而MCP传输层则确保了通信的安全与效率。这种设计使得大模型无需关心底层数据源的具体实现细节，只需通过标准化协议即可无缝访问数据库、API、文件系统乃至实时数据流。

Agent 不能靠硬编码知道系统里有哪些能力。 MCP 通过标准描述接口，让 Agent 动态获知：

  • 有哪些工具（Tools）
  • 有哪些资源（Resources，如文件、数据库、知识库）
  • 有哪些可复用提示模板（Prompts）

这使得 Agent 可以：调用本地工具，调用远程服务，操作文件 / 数据库……….，而不需要模型知道真实系统结构，属于 安全代理调用模型。

其本质是 能力注册与能力发现协议。但如果只是“给模型一个函数能调用”，那是插件机制；与之不同的是MCP 则强调：明确输入输出 Schema，权限边界，与宿主环境解耦

可能的误区:

1）MCP出现之前是不是没有办法调度工具？

不是的。它算是一个通用管理协议，把一个个工具按照一定的规范装在一个量身定做的箱子里。之前也可以进行调度，调度工具关键的点在于大模型识别出使用什么工具以及工具相对应的参数。langchain等在MCP之前就已经支持了工具调度的能力。

2）MCP可以代替function call？

不行，他们是一起工作的关系。如上个问题所述，它只是一个通用协议层。具体函数调用还是需要大模型的支持，而这个协议并不是必须的，在它出现之前就有不少方式，可以直接把工具也放在系统层，直接在系统内调用就可以。

3）MCP能减少调用的token数么？

不行，它只是整合了工具，但实际还是需要把工具参数都发给大模型。整体tokens数消耗相比之前的方式是没有本质区别的，整体依赖于系统的实现。

4）是不是有了MCP，agent应用就能轻而易举搭建了？

不是。MCP只是把工具管理和获取调用这里规范了，但agent应用关键点还有：LLM调用（含function call、prompt工程），记忆系统（RAG，上下文管理），思考和计划系统等。如果想要做好一个agent系统应用，还需要仔细打磨前面提到的模块。

协议内容

MCP 的核心是使用 JSON-RPC 2.0 作为消息格式，为客户端和服务器之间的通信提供了一种标准化的方式。

基础协议定义了三种基本消息类型，分别是请求、响应和通知。

以下是这三种消息类型的详细说明：

请求

请求消息用于从客户端向服务器发起操作，或者从服务器向客户端发起操作。请求消息的结构如下：

  • **jsonrpc**：协议版本，固定为"2.0"。
  • **id**：请求的唯一标识符，可以是字符串或数字。
  • **method**：要调用的方法名称，是一个字符串。
  • **params**：方法的参数，是一个可选的键值对对象，其中键是字符串，值可以是任意类型。

响应

响应消息是对请求的答复，从服务器发送到客户端，或者从客户端发送到服务器。响应消息的结构如下：

  • **jsonrpc**：协议版本，固定为"2.0"。
  • **id**：与请求中的id相对应，用于标识响应所对应的请求。
  • **result**：如果请求成功，result字段包含操作的结果，是一个键值对对象。
  • **error**：如果请求失败，error字段包含错误信息，其中：
    • **code**：错误代码，是一个数字。
    • **message**：错误描述，是一个字符串。
    • **data**：可选的附加错误信息，可以是任意类型。

通知

通知消息是一种单向消息，不需要接收方回复。通知消息的结构如下：

  • **jsonrpc**：协议版本，固定为"2.0"。
  • **method**：要调用的方法名称，是一个字符串。
  • **params**：方法的参数，是一个可选的键值对对象，其中键是字符串，值可以是任意类型。
