Ethereum原理

数据结构

以太坊区块数据有三棵树，分别为状态树，交易树和收据树。整个以太坊系统中只有一棵状态树，记录整个以太坊系统的所有账户状态。每个区块保存着一棵交易树，记录该区块的交易情况，一棵收据树用来记录该区块的交易收据。 状态树采用Merkel-Patrica(MPT)树，而交易树和状态树采用Merkel树。

对于交易树和收据树来说，一旦树已经建立，花多少时间来编辑这棵树并不重要，因为树一旦建立了，它就会永远存在并且不会改变。所以交易树和收据树采用Merkel树。 对于状态树，每个节点基本上包含了一个键值映射，其中的键是地址，而值包括账户的声明、余额、随机数nounce、代码以及每一个账户的存储。不同于交易历史记录，状态树需要经常地进行更新：账户余额和账户的随机数nonce经常会更变，更重要的是，新的账户会频繁地插入，存储的键也会经常被插入以及删除。我们需要这样的数据结构，它能在一次插入、更新、删除操作后快速计算到树根，而不需要重新计算整个树的Hash。Patricia树具有Trie树快速查找特点，并且比Trie树更加节省空间，所以以太坊中，对Merkel树改造成Merkel-Patrica(MPT)树。

Mempool（Memory Pool）：又称交易池，是 以太坊节点维护的一个内存集合，存放 已经广播到网络但还未打包进区块的交易。

它类似一个 待处理队列，所有节点都会维护自己的 mempool（不是全局统一的，每个节点可能略有不同）。

  1. 单个交易对象（Transaction）

    • 每个交易包含：
      • nonce：账户发起交易序号
      • from / to 地址
      • value：转账金额
      • gasPrice / maxFeePerGas / maxPriorityFeePerGas
      • gasLimit
      • data（如果是调用智能合约）
      • signature（签名验证交易合法性）
    • 所以可以说 Mempool 是一个个交易组成的集合。

  2. 按账户和 Gas 排序

    节点通常会：

    • 按 账户 nonce 排序（确保顺序合法）
    • 按 Gas 价格/优先级排序（矿工/验证者优先打包高 Gas 交易）

状态数据库

世界状态是地址（账户）到账户状态的映射(存储所有账户的全局状态（余额、Nonce、合约代码和存储根）)。由树来保存数据（此树也被称为状态数据库或者状态树）。世界状态可以被视作为随着交易的执行而持续更新的全局状态。以太坊就像一个去中心化的计算机，世界状态则是这台电脑的硬盘。

以太坊中所有的账户信息都体现在世界状态之中，并由世界状态树保存。如果你想知道某一账户的余额，或者某智能合约当前的状态，就需要通过查询世界状态树来获取该账户的具体状态信息。

账户存储树是保存与账户相关联数据的结构。该项只有合约账户才有，而在 EOA 中， storageRoot 留空、 codeHash 则是一串空字符串的哈希值。

世界状态不直接存在链上是因为如果每次交易都全量存储所有账户状态，区块链会变得极其臃肿（比如以太坊有数亿个账户，每个区块都存一遍不现实）。因此，只存变化的部分（交易），而状态由全节点动态计算。

世界状态通过MPT组织：

  • 只有状态树的根哈希（stateRoot）写入区块头。
  • 全节点在本地维护完整的键值数据库（如 LevelDB、RocksDB），存储所有账户状态。
  • 轻节点只需验证 stateRoot 即可信任某账户的状态（通过默克尔证明）。

每个以太坊全节点都会在本地硬盘存储完整的世界状态（State DB）。数据是去中心化的，没有单点依赖。每个区块头包含 stateRoot，代表该区块处理后的世界状态。如果全节点篡改状态，stateRoot 会不一致，其他节点会拒绝。新节点同步时，会从创世区块开始重放所有交易，逐步构建最新状态。也可以直接下载快照（Snapshot）加速同步，但仍需验证 stateRoot。

以太坊中有两种账户类型：外部所有账户（Externally Owned Accounts 简称 EOA）以及合约账户。

  • 我们用来互相收发以太币、部署智能合约的账户就是 EOA 账户，
  • 而部署智能合约时自动生成的账户则是合约账户。

每一个智能合约都有其独一无二的以太坊账户。

账户状态中不容忽视的一个细节是，上述对象在内的所有对象都可变（除了 codeHash）。举例来说，当一个账户向其他账户发送以太币时，除了 nonce 会增加，账户的余额也会相应改变。

而 codeHash 的不可变性使得，如果部署了有漏洞的智能合约，也无法修复更新此合约。对应的，只能部署一个新合约（而有漏洞的版本会一直存在于区块链上）。

这也是为什么使用 Truffle 进行智能合约的开发和部署十分必要，并且用 Solidity 编程时要遵循 最佳实践 的要求。

账户存储树是保存与账户相关联数据的结构。该项只有合约账户才有，而在 EOA 中， storageRoot 留空、 codeHash 则是一串空字符串的哈希值。所有智能合约的数据都以 32 字节映射的形式保存在账户存储树中。此处不再赘述账户状态树如何维持合约数据。账户状态中的 storageRoot 区域负责维持账户存储树根节点哈希值。

举个例子：查询地址 0x123 的余额

  1. **初始化 StateDB**：从区块头读取 stateRoot（假设为 0xabcd）。从数据库加载 Trie（根节点哈希 = 0xabcd）。
  2. **查询 Trie**：计算 key = keccak256(0x123)。从 Trie 获取 RLP(Account)。
  3. **缓存到 stateObjects**：解码 Account，生成 stateObject，存入 stateObjects。
  4. 后续操作：如果该账户状态被修改（如 SetBalance），stateObject 会标记为 dirty。提交时，将 dirty 对象重新 RLP 编码并更新到 Trie，生成新的 stateRoot。

验证者选举

准入控制

这个函数 ProcessDeposits 是以太坊信标链（Beacon Chain）中处理验证者存款（Validator Deposits）的核心逻辑，属于权益证明（PoS）共识机制的关键组成部分。它的主要功能是批量处理来自以太坊 1.0 存款合约的质押交易，将符合条件的质押者加入信标链的验证者队列。

ProcessDeposit 是信标链处理单个验证者存款的核心函数，负责：

  1. 验证存款合法性（Merkle 证明、签名等）。
  2. 更新 Eth1 存款索引（确保顺序处理）。
  3. 应用存款到状态（新增验证者或更新余额）。

核心作用：将合法的 Eth1 存款转换为信标链验证者状态变更，是 PoS 准入控制的核心环节。

ApplyDeposit 是信标链处理存款的最终执行层，负责将验证者存款数据写入区块链状态，具体分为：

  • 新增验证者（首次质押）
  • 追加余额（已有验证者增持）

AddValidatorToRegistry 是信标链中将新验证者正式注册到状态的核心函数，完成以下操作：

  1. 初始化验证者对象：根据存款数据生成验证者实例。
  2. 更新状态数组：将验证者追加到信标链的全局状态中。
  3. 处理 Altair 硬分叉字段：为升级后的网络初始化新增字段。

激活验证者

ProcessRegistryUpdates 是信标链中管理验证者生命周期状态转换的核心函数，负责处理以下三类验证者状态变更：

  1. 加入激活队列：满足条件的质押者进入激活等待列表。
  2. 驱逐低余额验证者：质押余额不足的活跃验证者被强制退出。
  3. 激活验证者：等待期满的验证者正式加入共识网络。

区块提议

选举机制

每个时隙（Slot，12秒）通过 RANDAO + LMD-GHOST 随机选择一个验证者作为提议者。

ComputeProposerIndex 是信标链中选举区块提议者（Block Proposer）的核心算法，其通过以下步骤实现：

  1. 遍历活跃验证者列表：按伪随机顺序检查每个验证者。
  2. 权重比较：根据验证者的 EffectiveBalance 计算选择概率，与随机数比较决定是否选中。
  3. 版本兼容：支持 Electra 硬分叉前后的不同参数（如 MaxEffectiveBalanceElectra）。

职责

在 validator.ProposeBlock 函数中，区块提议者的职责被分解为以下步骤：

  1. 准备阶段：检查当前 slot 有效性（跳过 genesis slot）。加锁防止重复提案（async.NewMultilock）。
  2. 生成 Randao Reveal：签署 epoch 相关的随机数，用于后续区块请求（signRandaoReveal）。
  3. 获取区块数据：向信标节点请求区块模板（包含交易、投票等）（BeaconBlock 请求）。
  4. 签名与构建：对区块进行签名（signBlock），并构建完整签名区块（BuildSignedBeaconBlock）。
  5. 防罚没检查：验证提案是否违反罚没规则（SlashableProposalCheck）。
  6. 广播区块：提交签名区块到网络（ProposeBeaconBlock）。

GetPayload 是共识层（信标链）从执行层（如 Geth）获取已打包交易数据（ExecutionPayload）的核心方法，其工作流程如下：

  1. 发起 RPC 请求：通过 Engine API 调用执行层客户端的 engine_getPayloadV1。
  2. 接收预构建区块：获取执行层生成的交易列表、状态根等数据。
  3. 返回格式化响应：封装为 GetPayloadResponse 供共识层使用。

罚没

  1. 罚没检测：CheckProposerSlashing / CheckAttesterSlashing（检测双重提案或投票）。
  2. 惩罚执行：ProcessSlashings / SlashValidator（扣除余额并强制退出）。
  3. 怠惰惩罚：ProcessInactivityScores / ProcessInactivityPenalties（惩罚长期离线验证者）。
  4. 举报机制：SubmitProposerSlashing / SubmitAttesterSlashing（链上提交证据）。

1. 核心委员会分配函数：ComputeCommittee

(1) 功能

在以太坊信标链的共识机制中，委员会分配（Committee Assignment）和区块提议者（Proposer）的选举是两个独立的过程，但通过协作共同完成区块验证和共识。以下是关键解析：

1. 委员会与提议者的角色区别

角色 职责 选举方式
提议者 打包并广播区块 每个 Slot 随机选 1 个验证者（基于 EffectiveBalance 和 RANDAO 种子）。
委员会成员 对区块进行投票（Attestation） 每个 Epoch 随机分组（基于 ComputeCommittee 洗牌算法）。

2. 委员会分配是否包含提议者？

(1) 默认情况下不包含

  • 委员会分配（ComputeCommittee）仅用于选择投票验证者（Attesters），而提议者是单独选举的。
  • 源码逻辑：
    • 提议者通过 GetProposerIndex 选举（依赖 RANDAO 和有效余额）。
    • 委员会成员通过 ComputeCommittee 分配（依赖洗牌种子 attesterSeed）。

(2) 动态重叠可能性

  • 自然随机性：
    由于两者均基于随机算法，提议者可能恰好被分配到当前 Slot 的某个委员会中，但这是概率性事件，非设计强制。

  • 统计分布：
    若全网有 10 万验证者，提议者被分配到同一 Slot 委员会的概率约为：

    委员会大小（64）活跃验证者数（100,000）≈0.064%活跃验证者数（100,000）委员会大小（64）≈0.064%

POW

工作量证明（PoW） 是一种基于计算竞赛的分布式共识机制，要求网络参与者通过消耗计算资源来解决一个复杂的密码学难题，以此竞争获得区块链记账权并获取相应奖励。其核心设计思想是通过提高作恶的经济成本来保障系统安全，遵循“最大计算力代表最大信任”的原则——攻击者要想篡改交易记录必须掌握全网51%以上的算力，这使得攻击成本远超潜在收益。在典型实现中（如比特币和早期以太坊），矿工不断调整区块头中的随机数（Nonce）并重复进行SHA-256哈希运算，直到找到满足特定难度目标的哈希值（例如前导零个数达到要求），这个寻找过程本质上是概率极低的随机碰撞，唯一优化途径就是提升计算设备的速度与能效。PoW机制完美解决了去中心化系统中的双重支付问题和女巫攻击风险，但同时也带来了巨大的能源消耗和专业矿机导致的中心化趋势，这些固有缺陷成为后来权益证明（PoS）等替代方案兴起的主要驱动力。

区块构建

在区块打包交易后、挖矿开始前，矿工需要预计算区块奖励，写入区块头的状态根。

动态奖励规则：根据以太坊的硬分叉阶段调整区块奖励：

  • FrontierBlockReward：以太坊初始阶段的区块奖励（5 ETH）。
  • ByzantiumBlockReward：拜占庭分叉后降至 3 ETH。
  • ConstantinopleBlockReward：君士坦丁堡分叉后进一步降至 2 ETH。

叔块定义：被当前区块引用的最多 2 个旧区块（高度需在 [currentBlockNumber - 8, currentBlockNumber) 范围内）。

交易执行

交易执行时，Gas费用会被累加到矿工余额Coinbase（statedb.AddBalance）。注意交易执行时已扣除：当用户交易被执行时，GasUsed * GasPrice 会从其账户余额中扣除。

矿工自动获得：扣除的手续费实际上留在了全局状态中，而矿工通过打包交易间接获得这些资金。因为：

  • 区块的 Coinbase（矿工地址）在最终状态中被赋予所有交易手续费的汇总。
  • 无需显式转账，只需确保状态根包含这些余额变更。

挖矿阶段

矿工在找到有效Nonce后，会将包含奖励和交易费的区块广播。

commitNewWork() 的主要步骤：

  1. 初始化新区块头：基于父区块计算区块号、时间戳、GasLimit 等。设置矿工地址（Coinbase）。

  2. 处理 DAO 硬分叉逻辑（历史遗留，现代以太坊无影响）。

  3. 准备挖矿环境（makeCurrent）：创建状态数据库（statedb）的副本，用于交易执行。

  4. 选择叔块（Uncles）：从本地或网络叔块池中选择最多 2 个叔块。

  5. 打包交易：从交易池（TxPool）获取待处理交易，按 GasPrice 和 Nonce 排序。优先打包本地交易（localTxs），再打包远程交易（remoteTxs）。

  6. 提交区块：调用 commit() 生成候选区块，交给共识引擎（如 Ethash）进行挖矿。

广播

协议管理器（ProtocolManager）

以太坊节点启动 P2P 网络服务的核心入口，主要完成：

  1. 交易广播：将本地交易池的新交易广播给全网。
  2. 区块广播：将本地挖出的新区块分阶段广播。
  3. 同步管理：确保节点与网络保持区块和交易的同步。

本地新区块广播

minedBroadcastLoop() 是一个后台协程，监听本地挖矿模块的NewMinedBlockEvent事件，当节点成功挖出新区块时，分两阶段广播：

  1. 优先广播完整区块给部分节点（propagate=true）
  2. 再广播区块哈希给剩余节点（propagate=false）

最终一致性保障

  1. 被动同步：未及时收到广播的节点会通过定期 sync 协议同步最新区块。
  2. 主动请求：节点发现链高度落后时，主动通过 downloader 模块拉取缺失区块。
  3. 分叉处理：若不同节点收到冲突区块，最终以累计难度（TD）最高的链为准。

接力传播（Relay）

以太坊通过多级节点接力实现全网覆盖，具体流程：

(1) 第一跳（本地节点 → 直接邻居）

  • 本地节点将区块/哈希发送给直接连接的邻居节点。

(2) 第二跳（邻居 → 邻居的邻居）

  • 收到完整区块的邻居节点会：
    1. 验证区块有效性（PoW、交易等）
    2. 存储到本地链
    3. 继续广播给自己的邻居节点（同样分两阶段）

Fetcher模块的工作流程：

  1. 验证区块头：检查PoW、时间戳等
  2. 检查重复性：确认本地链尚未包含该区块
  3. 触发广播：若验证通过，调用broadcastBlock接力传播
  4. 链上写入：最终通过InsertChain写入区块链

广播哈希的过程跟广播区块的过程非常的类似，最终是由远程节点去处理NewBlockHashesMsg消息。广播区块的过程完毕之后，会直接进入下一个阶段，调用fetcher模块去同步这些广播的区块

(3) 递归传播

  • 每个收到新区块的节点都成为新的传播源，重复上述过程。
