Mutil-Agent系统

背景

亚当·斯密在《国富论》中，用制针工厂说明——如果一个人从头到尾完成所有工序，一天可能做不出1枚针；但通过分工（拉丝、切断、磨尖、包装等），10个人一天能做出48000枚针。分工允许个体专注于某一环节，重复带来熟练，熟练催生技巧改进，最终形成专业知识的深度积累。人类文明的进步，很大程度上就是分工不断细化、深化的历史。

如果说大模型是个通才，已经具备了认知的核心。从之前的文章里，可以总结出：

  • 记忆系统赋予他经验，让他不再每次从零开始；
  • MCP协议赋予他手脚，让他能真正作用于现实世界；
  • 系统提示词赋予他人格，让他扮演合适的角色；
  • 思考与规划赋予他理性，让他的行动有逻辑、有章法。

理论上看，这已构成一个万能智能体，足够聪明并能够足以应对任何任务。

但就像人类一样，Agent智能体也无法做到每一个领域样样精通【在具体领域（比如医疗诊断、法律分析、代码调试）往往不如专门的微调模型表现好。就像你不会请一个全科医生做心脏外科手术】。

即使是最先进的模型，上下文窗口也有上限。当任务变得复杂时：

  • 单个智能体需要记住的信息量可能超过窗口限制
  • 长上下文中的“注意力稀释”会导致细节丢失
  • 长期任务需要记忆和状态管理，单智能体难以持续追踪

更不要说单智能体本质上是串行处理的：一个任务接一个任务。但现实中很多场景需要并行：

  • 同时监控多个数据流
  • 同时与多个用户交互
  • 同时执行多个独立子任务

这时如果从人类社会中借鉴点经验，让多个Agent担任不同的角色，进行不同的分工，协调完成任务。或许就可以大幅度提高生产效率。

事实上，目前已经有多种mutil-agent框架出现了，比如CrewAI、AutoGen和Langgraph，其中CrewAI更是完全参考了人类团队运行的模板，比如其核心的几个概念：任务，团队，流程，协作 。这篇文章试做简单的介绍

核心概念

通信机制

就像人类社会一样，团队成员可以通过发邮件进行合作，多Agent之间的协调工作势必要进行沟通交流。首先以AutoGen为例，其消息与通信主要通过主题和订阅来实现。

AutoGen 核心中的代理可以对消息进行响应、发送和发布，消息是代理之间相互通信的唯一方式。而在langgraph中必须事先定义一个状态。

不同的Agent必须事先定义一个共同的消息,比如：

而在CrewAI中则简单很多，Agent 按预定义流程依次执行，通信本质是任务上下文传递

Crew → 按顺序执行 Task → 每个 Task 分配给指定 Agent

Agent 之间不直接对话，通过 Task 的 output 传递给下一个 Task 的 context，支持委托（delegation）：一个 Agent 可以生成新任务交给另一个 Agent（但仍是流程化），通信是单向数据流，而非双向对话

比对上述三种框架可以看出：

维度 AutoGen CrewAI LangGraph
通信模式 点对点对话 + 群聊管理 任务链单向传递 中心化状态共享
通信显式程度 高（Agent 主动发送） 中（通过任务隐式传递） 低（节点读写状态）

其本质大多是依赖公共内存，即多个 Agent 实时共享的、可读写的内存空间，通常位于 RAM 中，用于当前运行会话内的状态同步。

跨 Agent 状态持久化

每一家大型公司在软件项目开发之际都会要求开发人员写文档，目的之一便是为了让将来接手的新人能快速理解前人的工作。同理，在多 Agent 系统中，如果某个 Agent 在中途失败了，如何避免之前所有 Agent 的工作成果付诸东流？

答案是一样的：留下必要的记录。

通过将 Agent 间的共享状态持久化存储，即便某个节点崩溃，系统也能从最近一次记录中恢复，无需从头开始。这既是系统的“文档”，也是它的“断点续传”机制。

回顾三大框架三大框架中的体现

  • 在AutoGen中需要自己实现（将对话历史存数据库，或用 RedisAgent 扩展）
  • 在CrewAI中memory=True 时启用长期记忆（向量数据库），存储的是知识片段而非运行状态
  • 在LangGraph中checkpointer 将每个超级步骤的 State 自动持久化到数据库

LangGraph 的设计最能说明两者关系：

同前面的通信机制对比：

维度 公共内存 跨 Agent 状态持久化
存储层级 内存层 持久化层
生命周期 单次运行/会话 跨运行、跨会话
访问速度 极快（微秒级） 较慢（毫秒级）
主要目的 实时协作 记忆延续、恢复
是否可选 多数框架内置 需主动配置

某种程度上可以将其视为整个团队的记忆系统。

Agent身份与生命周期

每个人都有各自的身份，Agent也不例外。

维度 AutoGen CrewAI LangGraph
Agent 的本质 对象实例（有状态） 对象实例（声明式） 函数节点（无状态）
身份绑定 强绑定（实例名） 中绑定（role 定义） 弱绑定（节点 ID）
生命周期长度 长（整个会话） 中（任务序列） 短（单次调用）
状态存储位置 Agent 自身 Agent + 可选长期记忆 State 对象（集中）
运行时可变性 可动态注册行为 执行前确定 图编译后固定
销毁时机 显式或作用域结束 Crew 执行完成 节点调用返回后

AutoGen

在AutoGen中每个 Agent 有明确的角色标签（Assistant、UserProxy、自定义），但身份是逻辑概念而非实例隔离，agent之间通过 name 属性区分，但多个同名 Agent 在群聊中会被视为不同个体，Agent 之间可以直接通过名称发送消息

生命周期

阶段 特点
创建 实例化时定义 system message、LLM 配置、工具
运行时 长期存活，在对话循环中持续接收和发送消息
状态变化 可通过 register_reply 动态增减行为，但实例本身不变
销毁 显式删除或作用域结束

关键特征：

  • 有状态：每个 Agent 维护自己的 _oai_messages 历史
  • 长生命周期：设计上 Agent 创建后会持续存在整个会话
  • 身份绑定：身份与实例强绑定，运行时不能替换 Agent 的“角色本质”

CrewAI

而CrewAI则不同，Agent 由其 role、goal、backstory 定义，身份是声明式的

多个 Agent 组成 Crew，身份在 Crew 内唯一，而身份决定了可以调用哪些工具

生命周期

阶段 特点
创建 定义 role、goal、llm、tools
执行 每个 Agent 在单个任务期间活跃，任务完成后输出结果
复用 同一 Agent 实例可顺序执行多个任务，但不保留跨任务的状态（除非启用 memory）
销毁 Crew 执行完成后，Agent 实例通常被丢弃

关键特征

  • 相对无状态：每个任务执行时，Agent 的上下文主要来自当前 Task 的输入
  • 短生命周期倾向：虽然实例可以复用，但设计哲学是“Agent 完成任务即交付结果”
  • 身份与任务解耦：同一个 Agent 可以执行不同 Task，但身份（role）通常暗示其适合的任务类型

LangGraph

在LangGraph中，Agent 是图中的节点（node），身份由节点函数定义，而非对象，节点本身没有“名字”意义上的身份，只有节点标识符，节点只是函数，可以轻松替换实现，不改变图结构

生命周期

阶段 特点
创建 定义节点函数（可以是 Agent 调用、工具、任何逻辑）
运行时 每个节点在调用时临时存在，执行完即“消失”
状态传递 节点之间不保留实例，只通过 State 对象传递信息
复用 节点函数是无状态的，每次调用使用当前 State

关键特征：

  • 无状态节点：Agent 节点本身不保留任何记忆，所有状态在 State 中
  • 极短生命周期：节点在调用期间存在，返回后即可被垃圾回收
  • 身份与行为分离：同一个节点函数可以被多个图复用，身份由图的组织方式决定

由此可以看出三者设计哲学差异和使用场景的不同：

AutoGen：Agent 是“角色演员”， 是有身份、有记忆、持续存在的实体

  • 适合：需要长期对话、Agent 之间建立关系的场景（如人机协作、多轮协商）

CrewAI：Agent 是“岗位说明书”，是按需分配、完成任务即走的专业角色

  • 适合：线性工作流、自动化处理（如内容生成、数据处理 pipeline）

LangGraph：Agent 是“函数调用”，是无状态的计算步骤，所有智能体现在 State 和图结构中

  • 适合：复杂状态机、需要精确控制执行路径、需要断点恢复的场景

多代理设计模式

人类社会的演进，本质上是从个体到组织的发展脉络。我们不断探索如何将不同能力的个体，通过架构有效链接，共同完成超越个体极限的复杂任务。

公司里的层级结构、职能划分、协作流程，正是这种组织架构的体现——它将独立的个人凝聚成有机整体。当新人加入时，组织架构本身就是知识的沉淀，岗位职责就是经验的固化。

将这个视角投射到人工智能领域，也正经历类似的演进：从单一的智能体，走向多智能体协同的有机系统。这就是多代理设计模式（Multi-Agent） 的核心思想——通过定义不同角色的 Agent，设计通信机制与协作流程，让多个智能体像一家运转有序的公司那样，各司其职、相互配合，共同完成单个 AI 无法胜任的复杂任务。

接下来介绍几个重点的架构方式：

(这里以langgraph为例，其中autogen同理，crewai由于只有流程和协作 两种模式 适合简单固定任务，不做过多介绍)

群聊：从会议室讨论到多智能体协作

人类社会中的会议讨论，往往需要一个主持人来维持秩序、决定谁发言、何时结束，否则会议将陷入混乱。

在 LangGraph 中，群聊模式通过图结构和条件边来实现类似会议主持人的功能。多个 Agent 共享同一个 State，通过路由函数决定下一个发言者，并设定终止条件。

输出结构：LangGraph 的群聊输出是一个完整的 State 对象，包含了所有消息历史、最终结论和讨论轮次。通过 thread_id 可以随时恢复中断的讨论。

多代理辩论：从法庭辩论到观点碰撞

法庭上的辩论遵循严格的程序：原告陈述、被告反驳、法官裁决。这种结构化对抗能够暴露观点的弱点和盲区。

多代理辩论模式模仿了这种结构化对抗，通过定义正反双方和裁判角色，让不同 Agent 在观点碰撞中逼近真理。

输出结构：辩论输出包含完整的辩论历史、正反方观点演进过程，以及裁判的最终裁决，类似于法庭的庭审记录。

反思模式：从工匠打磨到自我迭代

工匠制作器物时，会反复审视自己的作品，发现问题、改进、再审视，直到满意为止。这种自我反思是技艺精进的源泉。

反思模式让 Agent 像工匠一样审视自己的输出，通过“执行者-批评者”的双循环实现自我迭代优化。

输出结构：反思模式的输出包含每一版的草稿、对应的批评意见，以及最终经过多轮打磨的成品，完整记录了从粗糙到精炼的演进过程。

并发代理：从工厂流水线到并行作业

现代工厂的生产线，多个工序同时进行，互不阻塞，极大提升了生产效率。这种并行作业模式是人类工业化的重要里程碑。

并发代理模式允许多个 Agent 同时处理不同任务或同一任务的不同部分，通过共享状态实现结果的汇聚。

输出结构：并发模式的输出包含拆分的子任务清单、每个子任务的独立结果，以及合并后的完整答案，类似于项目管理中的 WBS 和最终交付物。

社会模式 对应设计模式 LangGraph 实现
会议室讨论 群聊 条件边 + 路由函数
法庭辩论 多代理辩论 正反方节点 + 裁判节点
工匠打磨 反思 执行者-批评者循环
工厂流水线 并发代理 状态共享 + 并行分支

当然更多的设计如下：

多代理设计模式 功能简介 单体公司使用场景 优势 注意点
顺序工作流（Sequential Workflow） 任务按顺序由不同代理处理，每个代理完成后交给下一个 财务报表生成流程、审批流程自动化 易于调试和监控，每步可验证 对任务失败敏感，需要异常处理
移交（Handover） 将任务从一个代理移交给更合适的代理 客服场景：简单问题→复杂问题转人工或专家代理 提高任务处理准确性 需要明确移交条件
代理混合（Hybrid Agents） 同一任务由不同类型代理混合完成（LLM + 工具 + 人类） 产品文档生成 + 自动校对 灵活处理不同任务类型 设计复杂，需要协调不同代理能力
