安全机制

使用方式

先从使用路径入手，再深入底层实现。

OpenClaw 实际上有两种不同的通信路径：

  • Gateway ↔ 渠道（Channel），作为 Bot 客户端连接第三方服务器，出站 HTTPS 连接。是 Gateway 主动连接出去，不是外部连接进来
  • Gateway ↔ 远端设备（电脑/手机），这里存在三种方式：

这里我们谈谈第二种方式中的 VPN方式 和 公网方式：

公网方式 将本地电脑设备当作了服务器，在电脑上部署 OpenClaw 后：

  1. 启动服务（一般是 localhost:xxxx）
  2. 用内网穿透（关键），如：ngrok
  3. 手机打开内网穿透的网址，输入指令。

VPN方式 将本地电脑设备当作了客户端。是通过内置的渠道将任务推送到后端服务器上，本地电脑实时请求该服务器获得指令任务。

按照VPN方式，可以将整体架构分成：

  • 远程控制端（Client）
  • Gateway服务端（Hub）
维度 架构一：VPS常驻网关 架构二：台式机网关+笔记本远程 架构三：笔记本网关+远程访问
Gateway位置 VPS/云服务器（24h在线） 家庭台式机（长期在线） 笔记本电脑（移动设备）
控制端位置 笔记本/手机 笔记本 其他台式机/手机
连接方式 Tailscale/SSH隧道 SSH远程隧道 SSH隧道/Tailscale Serve
Gateway.bind "loopback" "loopback" "loopback"
公网暴露 无（仅VPN/隧道） 无 无
渠道通信 从VPS出站 从台式机出站 从笔记本出站
会话持久性 高（永不掉线） 较高（台式机常开） 低（笔记本休眠会断）
延迟 取决于VPS位置 家庭网络延迟 取决于笔记本网络

譬如：远程访问 - OpenClaw (Clawdbot) 文档这里：

将 网关主机 视为“代理驻留的地方”。它拥有会话、身份验证配置文件、频道和状态。您的笔记本电脑/台式机（以及节点）都连接到该主机。

可以看出此时电脑节点是 WebSocket客户端连接到 Gateway（服务器）并建立“持久连接”。后续并通过渠道将指令发送到 GateWay 路由到正确Agent，电脑通过 WebSocket 被动接收推送任务。

从安全性上看：

公网方式 把电脑“暴露成一个公网服务”，其本质是Web直连。而 VPN方式 通过Bot中转( 通常运行在一台服务器上)，使用VPN/Tailnet 设置 等价于“内网调用”，不会直接暴露公网端口。进一步减少了攻击面【Tailscale 是一个基于 WireGuard 的零信任 VPN 服务，可以简单理解为：把所有设备组成一个安全的私有网络，无论这些设备在哪里（家里、公司、云端)】，所以一般人使用也大多使用第二种。

天下没有攻不破的系统，即使是内网环境下也可以通过横向移动进而控制整个系统。那么对于这样的部署方式，可能的攻击点有哪些呢？又该什么防御呢？

这里我按照数据流的顺序，讲一讲每个环节的攻击点以及Openclaw是如何应对的：

  • Gateway服务端怎么确认客户端的真实性并且防止重放攻击
  • 工具调用劫持怎么办？如何防范滥用工具对系统资源的破坏和权限提升？

Gateway安全连接与认证

这一个阶段主要用于验证客户端的真实性 并且 每次新连接都生成一个全新的、不可预测的 UUID 作为 nonce 用于防止重放攻击。

预认证与注册

Gateway 的客户端认证主要靠 Token / TLS（设备指纹）/ Tailscale / Origin ** 四个手段。这一过程的核心思想是先认证身份再检查权限再分配会话/技能访问**

src\gateway\server.impl.ts

Gateway 可启用 TLS 并验证指纹，确保控制端和 Gateway 之间的流量加密，同时校验身份。

TLS（传输层安全协议）是一种加密协议，用于在计算机网络中提供安全通信。它的主要作用是确保两个应用程序（如Web服务器和浏览器）之间传输的数据具有机密性（不被窃听）、完整性（不被篡改）和身份验证（确认对方身份可信）。

同时启动时生成或配置的认证 token，每个客户端必须提供该 token 才能注册到 Gateway

并且会检查控制 Origin 白名单【跨域请求控制机制】。Openclaw有一个控制 UI ，是一个由 Gateway 网关提供的小型 Vite + Lit 单页应用，它会直接连接到同一端口上的 Gateway 网关 WebSocket。该白名单用于限制哪些网站/域名可以访问网关控制台 UI。

~/.openclaw/openclaw.json 的配置：

对企业或跨网络节点，用 Tailscale 作为身份和访问控制，设置配置gateway.auth.allowTailscale: true

当客户端接入 Gateway 时，会走 预认证和注册流程：

  1. 客户端发起 WebSocket / HTTP 请求。
  2. Gateway 验证 Token 、allowedOrigins 、 TLS 指纹。
  3. 认证通过后，将客户端信息记录到 clients 或 nodeRegistry。
  4. 分配 sessionKey / agentRunSeq 等用于会话追踪。

src\gateway\node-registry.ts

nodeRegistry 保存注册节点和它们可用的技能（agents）。

在const sessionRow = loadGatewaySessionRow(sessionKey);中注意Session Scope / Subagent Role表示每个 agent 或客户端有独立的权限范围【不同客户端信任级别不同，权限需要分层】

工具权限与沙盒隔离机制

做计算机病毒分析时，刚入门的逆向工程师都不会直接把可疑样本直接扔进真实系统，而是搭建一个隔离的沙盒环境，

  • Linux 下常用 Docker
  • Windows 下可以使用 Windows Sandbox
  • Android 系统中存在 VirtualApp

在“笼子”里观察病毒的每一个动作。即便病毒爆发，损失也仅限于这个可以一键还原的快照。

OpenClaw 的 Agent 在某种意义上，就是一个“有益但不可预测的病毒”。当它以最高权限运行时，拥有读取文件、执行命令、修改配置的能力——这与勒索病毒的破坏力在技术层面没有什么区别。尤其是当LLM 犯错，出现幻觉乃至误解指令。一个“rm -rf /”的误判，一个错误的文件覆写，就足以让“有益的助手”变成“灾难性的病毒”。

Sandbox配置

配置类别 选项 含义
Mode(启用范围) off 完全禁用沙盒，所有工具直接在宿主机运行（风险最高）
non-main (默认) 仅非主会话（群聊/频道）启用沙盒，主会话（私聊）在宿主机运行
all 所有会话强制使用沙盒，最高隔离级别
Scope(共享范围) session 每个会话独立容器，隔离最彻底，资源开销大
agent (默认) 同一智能体的所有会话共享一个容器，资源利用率高
shared 所有沙盒会话共享全局容器，资源开销最小但隔离弱
workspaceAccess(工作区访问) none (默认) 无法访问宿主机工作区，技能文件自动复制到容器临时目录
ro 只读挂载工作区到 /agent，写入工具（write/edit）自动禁用
rw 读写挂载工作区，允许修改工作区内文件（无法访问外部系统文件）

遗憾的是，一顿搜索我只找到了：

OpenClaw 可以在 Docker 容器中运行工具以减少爆炸半径。在沙盒隔离 - OpenClaw文档中提到：

  • "docker"（默认）：本地基于 Docker 的沙盒运行时。
  • "ssh"：通用的基于 SSH 的远程沙盒运行时。
  • "openshell"：基于 OpenShell 的沙盒运行时。

agents.defaults.sandbox.backend 控制由哪种运行时提供沙盒：

Docker SSH OpenShell
运行位置 本地容器 任意可通过 SSH 访问的主机 由 OpenShell 管理的沙盒
设置 scripts/sandbox-setup.sh SSH 密钥 + 目标主机 启用 OpenShell 插件
Workspace 模型 bind mount 或 copy 远程规范源（初始化一次） mirror 或 remote
网络控制 docker.network（默认：none） 取决于远程主机 取决于 OpenShell
浏览器沙盒 支持 不支持 尚不支持
Bind mounts docker.binds 不适用 不适用
最适合 本地开发，完全隔离 将执行卸载到远程机器 具有可选双向同步的受管远程沙盒

所以OpenClaw 在 Windows 下通常无法直接开启 Docker 沙盒模式，普遍建议在采用 SSH 或 OpenShell（远程 Linux）来做工具隔离。

OpenClaw 通过 SSH 连接到远程主机（通常是 Linux），在远程主机上执行工具。远程主机本身不是完全隔离的容器，可以把远程主机的一个用户、目录或者 chroot/容器作为“沙盒”来限制工具执行。OpenClaw 并不会在 SSH 后端额外创建 Docker 容器，它只是把远程机器当作受控执行环境，借助远程主机的权限和隔离机制来减少风险。

OpenShell 提供了完整的沙盒生命周期管理：创建工作区、执行命令、同步文件、销毁环境。远程主机（通常是 Linux）在 OpenShell 管理下，被当作专门的“沙盒环境”。隔离主要靠文件系统路径和远程主机权限，不依赖 Linux Namespace/Cgroups。可以用 chroot、虚拟用户、容器化命令（如果管理员手动启用）增强隔离，但默认只是逻辑隔离。适合 远程受控执行，可审计、可回溯，但隔离强度比 Docker 低。

所以再看看基于docker 实现的沙盒：

曾经我在什么是Docker - Hermes这篇文章中，就已经了解过docker的底层实现原理了，记得当时还跟着这本书自己动手写Docker - 陈显鹭 - 微信读书 写过一个demo。其本质是利用了Linux内核的三大支柱技术：

  • Linux Namespace
  • Linux Cgroups
  • Union File System

利用 Linux Namespace 实现环境隔离，Cgroups 实现资源限制，Union File System 实现写时复制（“省空间”）。这三项技术都已在内核层面经过十余年生产环境验证，成熟度极高。

因此，OpenClaw 基于 Docker 构建沙盒环境，在技术上是完全可靠的。将 Agent 的文件读写、命令执行等高权限操作全部放入 Docker 容器中执行，即便容器内执行 rm -rf / 或恶意篡改系统配置，破坏范围也被严格限制在容器内部，宿主机丝毫无损。

需要注意的是默认情况下，Docker 沙盒容器会在无网络模式下运行。 可通过 agents.defaults.sandbox.docker.network 覆盖。
