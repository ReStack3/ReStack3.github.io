配置管理

注意在loadPluginManifestRegistry()中可以看出OpenClaw 按以下顺序扫描插件：

  1. plugins.load.paths 指定路径
  2. 工作区扩展：*/.openclaw/extensions/*
  3. 全局扩展：*~/.openclaw/extensions/*
  4. 捆绑扩展（默认禁用）

同 ID 插件按优先级加载，低优先级版本会被忽略。

路由系统

从前面知道startGatewayServer是核心函数。这里偷个懒，直接把export async function startGatewayServer()喂给AI，分析一下大致轮廓。

这里先看到Agent 事件监听器，其作用是将 Agent 执行过程中的实时事件（流式文本、工具调用、生命周期状态）广播给所有需要监听的客户端（WebSocket、控制界面、节点等）。

Agent 的选择发生在 getReplyFromConfig 内部（通过 replyResolver 参数）

可以看出OpenClaw 将用户聊天命令路由到正确的 Agent主要通过配置决策，而非 LLM 字段决策。比如通过配置某个渠道来执行对应任务。

决策层级 来源 示例
1. 会话绑定 配置/数据库 sessionKey: "user:123" → agentId: "personal-assistant"
2. 渠道默认 配置 webchat 渠道 → agentId: "web-agent"
3. 全局默认 配置 defaults.agentId: "default-agent"

Agent 路由是基础设施层的配置问题，而非模型层的智能决策。

下面展示一个真实场景配置：一个团队同时使用 Telegram 和 WhatsApp，需要根据消息来源与风险等级将任务路由到不同智能体。

场景描述

  • assistant：默认助手，处理日常问题，无外部工具权限
  • devops：运维智能体，绑定特定 Telegram 群组（DevOps-team），拥有 exec（执行命令）和 ssh（远程连接）工具
  • writer：写作智能体，绑定特定 WhatsApp 对端（产品编辑），拥有 document（文档编辑）工具，无执行权
