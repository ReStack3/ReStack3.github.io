RESTful后端开发(FastAPI与Gin)

RESTful 规范

RPC 风格

RPC 风格的 API 设计基于调用远程过程的思想，API 通常是针对特定动作进行设计，URI 中会带有操作名，而不是直接表示资源。

操作 HTTP 方法 资源 URI 描述
创建用户 POST /createUser 创建新用户
获取用户信息 GET /getUser 获取指定用户信息
更新用户信息 POST /updateUser 更新指定用户信息
删除用户 POST /deleteUser 删除指定用户

多平台的接口设计问题

功能 Web 端 iOS 端 Android 端 小程序端
获取商品信息 GET /getProductList GET /iOS/getProducts GET /android/productInfo GET /weapp/product
获取购物车信息 POST /fetchCartData GET /cartInfo POST /android/getCart POST /weapp/cart
用户登录 POST /authenticate POST /iOS/login POST /android/login POST /weapp/login

可以看到同样的功能在不同平台上采用了不同的请求路径、HTTP 方法，导致接口设计不统一，开发人员在后端可能要实现多个几乎完全相同的接口，每次更新逻辑时，需要分别维护多个接口，容易导致版本不同步。

如果后端接口需要变更，比如添加分页功能，每个客户端都需要重新适配，增加了工作量。

强制所有客户端都使用 相同的接口路径 和 一致的数据格式

所以一套结构清晰、符合标准、易于理解、扩展方便让大部分人都能够理解接受的接口风格就显得越来越重要，而 RESTful 风格的接口（RESTful API）刚好有以上特点，就逐渐被实践应用而变得流行起来。

在 RESTful 风格中，设计的是 资源，而非”操作”。操作（如获取、创建、更新、删除）通过 HTTP 方法（GET、POST、PUT、DELETE）来体现，而不是在 URI 中写明动作。

操作 HTTP 方法 资源 URI 描述
创建用户 POST /users 创建新用户
获取用户信息 GET /users/{id} 获取指定用户信息
更新用户信息 PUT /users/{id} 更新指定用户信息
删除用户 DELETE /users/{id} 删除指定用户

REST 架构特征和限制条件

REST 架构特征

以资源为基础：资源可以是一个图片、音乐、一个 XML 格式、HTML 格式或者 JSON 格式等网络上的一个实体，除了一些二进制的资源外普通的文本资源更多以 JSON 为载体、面向用户的一组数据（通常从数据库中查询而得到）。

统一接口：对资源的操作包括获取、创建、修改和删除，这些操作正好对应 HTTP 协议提供的 GET、POST、PUT 和 DELETE 方法。具体的 HTTP 方法和方法含义如下：

  • GET（SELECT）：从服务器取出资源（一项或多项）。
  • POST（CREATE）：在服务器新建一个资源。
  • PUT（UPDATE）：在服务器更新资源（客户端提供完整资源数据）。
  • PATCH（UPDATE）：在服务器更新资源（客户端提供需要修改的资源数据）。
  • DELETE（DELETE）：从服务器删除资源。

URI 指向资源：URI = Universal Resource Identifier 统一资源标志符，用来标识抽象或物理资源的一个紧凑字符串。RESTful 是面向资源的，每种资源可能由一个或多个 URI 对应，但一个 URI 只指向一种资源。

无状态：服务器不能保存客户端的信息，每一次从客户端发送的请求中，要包含所有必须的状态信息，会话信息由客户端保存，服务器端根据这些状态信息来处理请求。

REST 架构限制条件

Fielding 在论文中提出 REST 架构的 6 个限制条件，也可称为 RESTful 6 大原则：

  1. 客户端-服务端（Client-Server）：更专注客户端和服务端的分离，服务端独立可更好服务于前端、安全以及 Android、iOS 等客户端设备。
  2. 无状态（Stateless）：服务端不保存客户端状态，客户端保存状态信息每次请求携带状态信息。
  3. 可缓存性（Cacheability）：服务端需回复是否可以缓存以让客户端甄别是否缓存提高效率。
  4. 统一接口（Uniform Interface）：通过一定原则设计接口降低耦合，简化系统架构，这是 RESTful 设计的基本出发点。
  5. 分层系统（Layered System）：客户端无法直接知道连接的是终端还是中间设备，分层允许你灵活的部署服务端项目。
  6. 按需代码（Code-On-Demand，可选）：按需代码允许我们灵活的发送一些看似特殊的代码给客户端，例如 JavaScript 代码。

FastAPI依赖注入Depends

依赖注入（Dependency Injection，简称DI）是一种软件设计模式，它有助于解耦应用程序的组件。在依赖注入中，一个对象的依赖关系不是由该对象自己创建或管理的，而是由外部容器或框架来提供和管理。

FastAPI 在其设计中实现了依赖注入机制，允许开发者以声明式的方式定义依赖项，并在需要的地方自动注入它们。以下是 FastAPI 中实现依赖注入的基本步骤：

  1. 定义依赖项：创建一个类或函数作为依赖项，通常会包含一些业务逻辑或者服务功能。

  2. 装饰器标记：使用 Depends 装饰器将依赖项标记为可注入的。这个装饰器告诉 FastAPI 在调用依赖此依赖项的函数时应提供它。

常见的使用常见：

  • 身份认证与授权
  • 数据库会话管理
  • 分页、排序、过滤参数封装
  • 配置管理
  • 请求上下文数据

会话控制

Session是”服务器记住你是谁”，JWT是”你自己证明你是谁”。Session适合传统Web应用，JWT适合现代API和分布式架构。

Cookie 是三者中最底层的机制，它只解决一个问题：如何让客户端在每次请求时自动携带凭证。

无论是 Session 还是 JWT，都需要一个凭证来标识用户身份：

  • 使用 Session 时，凭证是 Session ID，可以通过 Cookie 传输
  • 使用 JWT 时，凭证是 JWT 令牌，既可以通过 Cookie 传输，也可以通过 Authorization 请求头传输

可见Cookie 只是一个传输通道，Session 和 JWT 是两种不同的状态管理哲学。Cookie 不是 Session 的专属，它只是凭证的载体之一。

选择哪种组合，取决于应用架构和安全需求。传统Web应用选Session+Cookie，现代API选JWT+Authorization Header，折中方案选JWT+Cookie。

FastAPI 异常和错误处理机制

FastAPI 采用抛出异常 + 全局处理器的模式。当发生错误时，通过抛出异常来中断正常流程，FastAPI 会自动捕获并转换为规范的 JSON 响应返回给客户端。

HTTPException（内置异常）：这是最常用的异常类。直接在代码中抛出 HTTPException，指定 status_code 和 detail 参数，FastAPI 会自动将其转换为 JSON 格式的错误响应。例如用户未认证时抛出 401 异常，资源不存在时抛出 404 异常。

自定义异常处理器：通过 @app.exception_handler() 装饰器可以为特定异常注册处理器。当业务代码抛出自定义异常（如 InsufficientFundsError、PermissionDeniedError）时，注册的处理器会拦截并返回自定义的响应格式，实现业务错误码与 HTTP 状态码的解耦。

请求验证错误处理：当 Pydantic 模型校验失败（类型错误、必填字段缺失、格式不符等）时，FastAPI 会自动抛出 RequestValidationError。可以自定义该异常的处理器，将默认的验证错误格式化为更友好的提示信息，简化前端处理逻辑。

全局异常兜底：为了防止未捕获的异常导致服务器返回 HTML 错误页或暴露敏感信息，通常需要注册一个全局 Exception 处理器。它会拦截所有未被处理的异常，记录错误日志后返回统一的 500 错误响应。

如何对 FastAPI 应用进行单元测试？

FastAPI 官方推荐使用 pytest 作为测试框架，并提供了 TestClient 工具，它基于 httpx，可以让你像调用真实 HTTP 客户端一样测试你的应用，但完全在内存中运行，速度极快。

测试步骤：

  1. 安装依赖：pip install pytest httpx
  2. 创建 TestClient：导入你的 FastAPI app 实例，并用 TestClient 包装它。
  3. 编写测试用例：使用 client.get(), client.post() 等方法发起请求，并断言响应的状态码、JSON 内容等。
