Docker 的定义

Docker 是一个开源的 容器化平台，用于自动化应用程序的部署、扩展和管理。它通过容器技术，允许开发人员将应用及其所有依赖打包成一个标准化的单元（容器），并在任何环境中一致地运行，无论是开发环境、测试环境，还是生产环境。

具体来说，Docker 提供了一个轻量级、可移植、可扩展的容器化解决方案，它通过将应用程序及其依赖打包为一个容器镜像，从而解决了“在我电脑上能跑”的问题，确保了不同环境中的应用行为一致性。

Docker 的核心概念

容器（Container）：是 Docker 中的一个运行时实例，它打包了应用和所有依赖的运行环境。容器是轻量级、独立的，可以快速启动和停止。

镜像（Image）：是容器的静态模板，包含应用的所有依赖、环境变量、库文件等。容器是由镜像启动的，每次启动都会基于镜像的状态创建一个新的容器实例。

Docker 引擎（Docker Engine）：是一个客户端-服务器的应用，提供了容器化技术。它包括一个守护进程（Docker Daemon）、一个 REST API 和一个命令行界面（CLI）。Docker 引擎负责容器的创建、管理和运行。

数据卷（Volumes）：用于持久化和共享容器中的数据。容器退出后，数据卷中的数据仍然存在，可以跨容器使用。

Docker Hub：是一个公共的 Docker 镜像仓库，用户可以从中获取或上传镜像，类似的镜像仓库还有很多，不一一列举了。

Docker与传统虚拟化(VM)的区别？

虚拟化技术：传统的虚拟化技术通过在硬件上运行多个虚拟机，每个虚拟机都包括操作系统和应用程序。每个虚拟机都需要大量的资源，并且启动时间较长。

Docker 容器化技术：容器技术通过共享宿主机的操作系统内核来提供虚拟化，它是操作系统级别的虚拟化。每个容器都包含应用及其依赖，但不需要额外的操作系统。容器更轻量级，启动速度快。

Docker 的优势

从与传统虚拟化技术进行对比可以明显看出docker的优势所在：

  • 轻量级：容器使用宿主机操作系统的内核，因此比虚拟机更小，启动更快，资源消耗更少。
  • 可移植性：容器包含了应用及其所有依赖，可以在任何支持 Docker 的环境中运行，确保跨平台的一致性。
  • 快速部署和高效开发：由于容器化的隔离特性，开发人员可以在本地快速部署应用，进行测试和调试，然后直接将容器迁移到生产环境。
  • 扩展性：Docker 可以轻松地通过 Docker Compose、Kubernetes 等工具进行集群管理，支持大规模的容器部署。

基础技术

Linux Namespace

Linux Namespace是Linux Kernel的一个功能，它可以隔离一系列的系统资源，比如PID（Process ID）、User ID、Network等。一般看到这里，很多人会想到一个命令chroot，就像chroot允许把当前目录变成根目录一样（被隔离开来的），Namespace也可以在一些资源上，将进程隔离起来，这些资源包括进程树、网络接口、挂载点等。

简单介绍

Linux Namespace 是 Linux 内核提供的一种机制，用于实现资源的隔离。通过 Namespace，可以将系统的全局资源（如进程、网络、文件系统等）隔离成不同的命名空间，使得每个命名空间中的资源相互独立，互不干扰。Docker 正是利用 Namespace 技术来实现容器的资源隔离。

Linux 提供的 Namespace 类型

Namespace 类型 隔离的资源 作用
PID Namespace 进程 ID (PID) 不同 Namespace 中的进程可以有相同的 PID，实现进程 ID 的隔离。
Mount Namespace 文件系统挂载点 不同 Namespace 中的文件系统挂载点相互独立，实现文件系统的隔离。
UTS Namespace 主机名和域名 不同 Namespace 中的主机名和域名可以不同，实现主机名和域名的隔离。
IPC Namespace 进程间通信 (IPC) 资源，如消息队列、信号量、共享内存等 不同 Namespace 中的进程无法直接通过 IPC 通信，实现 IPC 资源的隔离。
Network Namespace 网络设备、IP 地址、端口等网络资源 不同 Namespace 中的网络栈相互独立，实现网络资源的隔离。
User Namespace 用户和用户组 ID (UID 和 GID) 不同 Namespace 中的用户和用户组可以有相同的 UID 和 GID，实现用户权限的隔离。

命名空间建立系统的不同视图，从用户的角度来看，每一个命名空间应该像一台单独的Linux计算机一样，有自己的init进程（PID为1），其他进程的PID依次递增，A和B空间都有PID为1的init进程，子命名空间的进程映射到父命名空间的进程上，父命名空间可以知道每一个子命名空间的运行状态，而子命名空间与子命名空间之间是隔离的。从图2.1所示的PID映射关系图中可以看到，进程3在父命名空间中的PID为3，但是在子命名空间内，它的PID就是1。也就是说用户从子命名空间A内看进程3就像init进程一样，以为这个进程是自己的初始化进程，但是从整个host来看，它其实只是3号进程虚拟化出来的一个空间而已。

Linux Cgroups

讲述的是构建Linux容器的Namespace技术，它帮助进程隔离出自己单独的空间，但Docker是怎么限制每个空间的大小，保证它们不会互相争抢的呢？这就要用到Linux的Cgroups技术

简单介绍

Cgroups（Control Groups） 是 Linux 内核提供的一种机制，用于限制、控制和监控进程组的资源使用。通过 Cgroups，可以对进程组的 CPU、内存、磁盘 I/O、网络等资源进行精细化的管理和分配。Cgroups 是容器技术（如 Docker）实现资源隔离和限制的核心技术之一。

Cgroups 的核心概念

子系统（Subsystem）

  • Cgroups 通过子系统来管理不同类型的资源。每个子系统负责管理一种资源。

  • 常见的子系统包括：

    • cpu：限制 CPU 使用。
    • memory：限制内存使用。
    • blkio：限制块设备 I/O。
    • net_cls：标记网络数据包，用于流量控制。
    • devices：控制设备访问权限。
    • freezer：挂起或恢复进程组。

    每个subsystem会关联到定义了相应限制的cgroup上，并对这个cgroup中的进程做相应的限制和控制。

控制组（Control Group）
  • 控制组是 Cgroups 的基本单位，每个控制组可以包含一组进程。
  • 每个控制组可以绑定一个或多个子系统，并为这些子系统设置资源限制。
层级结构（Hierarchy）
  • Cgroups 以树形结构组织控制组，形成一个层级结构。
  • 每个层级结构可以绑定一个或多个子系统。
  • 子控制组会继承父控制组的资源限制。

hierarchy的功能是把一组cgroup串成一个树状的结构，一个这样的树便是一个hierarchy，通过这种树状结构，Cgroups可以做到继承。比如，系统对一组定时的任务进程通过cgroup1限制了CPU的使用率，然后其中有一个定时dump日志的进程还需要限制磁盘IO，为了避免限制了磁盘IO之后影响到其他进程，就可以创建cgroup2，使其继承于cgroup1并限制磁盘的IO，这样cgroup2便继承了cgroup1中对CPU使用率的限制，并且增加了磁盘IO的限制而不影响到cgroup1中的其他进程。

三个组件相互的关系
  1. 层级结构绑定子系统：
    • 每个层级结构可以绑定一个或多个子系统。
    • 例如，一个层级结构可以绑定 cpu 和 memory 子系统，用于同时管理 CPU 和内存资源。
  2. 控制组属于层级结构：
    • 控制组是层级结构中的节点，每个控制组属于某个层级结构。
    • 控制组会继承层级结构绑定的子系统，并可以设置具体的资源限制。
  3. 进程属于控制组：
    • 进程被添加到某个控制组中，受到该控制组的资源限制。
    • 进程的资源使用情况会被子系统和层级结构监控和管理。

Union File System

Union File System，简称UnionFS，是一种为Linux、FreeBSD和NetBSD操作系统设计的，把其他文件系统联合到一个联合挂载点的文件系统服务。它使用branch把不同文件系统的文件和目录“透明地”覆盖，形成一个单一一致的文件系统。这些branch或者是read-only的，或者是read-write的，所以当对这个虚拟后的联合文件系统进行写操作的时候，系统是真正写到了一个新的文件中。看起来这个虚拟后的联合文件系统是可以对任何文件进行操作的，但是其实它并没有改变原来的文件，这是因为unionfs用到了一个重要的资源管理技术，叫写时复制。

写时复制（copy-on-write，下文简称CoW），也叫隐式共享，是一种对可修改资源实现高效复制的资源管理技术。它的思想是，如果一个资源是重复的，但没有任何修改，这时并不需要立即创建一个新的资源，这个资源可以被新旧实例共享。创建新资源发生在第一次写操作，也就是对资源进行修改的时候。通过这种资源共享的方式，可以显著地减少未修改资源复制带来的消耗，但是也会在进行资源修改时增加小部分的开销。

AUFS介绍

AUFS（Advanced Multi-Layered Unification Filesystem，高级多层统一文件系统）是一种联合文件系统，它允许你将多个目录（称为分支）挂载到同一个挂载点上，并以一种统一的方式呈现这些目录中的文件。AUFS 的主要特点是支持写时复制（Copy-on-Write, CoW），这意味着只有在文件被修改时才会复制文件，而不是在文件被读取时。

AUFS 的核心功能包括：

  1. 分层存储：多个目录（层）可以叠加在一起，形成一个统一的视图。
  2. 写时复制：当文件被修改时，AUFS 会复制该文件到可写层，而不是直接修改原始文件。
  3. 高效存储：多个容器可以共享相同的只读层，从而节省存储空间。

AUFS 是 Docker 早期版本中默认使用的存储驱动，但由于其未被合并到 Linux 内核主线，Docker 逐渐转向了其他存储驱动（如 overlay2）。

Docker 如何使用 AUFS

Docker 使用 AUFS 来实现镜像和容器的分层存储。

镜像分层：

  • Docker 镜像由多个只读层（Read-Only Layers）组成，每一层代表镜像的一个变更（例如安装软件包、添加文件等）。
  • 这些只读层通过 AUFS 叠加在一起，形成一个统一的文件系统视图。

容器层：

  • 当容器启动时，Docker 会在镜像的最上层添加一个可写层（Read-Write Layer）。
  • 容器的所有修改（如创建、修改或删除文件）都会记录在这个可写层中，而不会影响底层的只读镜像。

写时复制（CoW）：

  • 当容器需要修改一个文件时，AUFS 会将该文件从只读层复制到可写层，然后在可写层中进行修改。
  • 这种方式确保了镜像的不可变性，同时允许多个容器共享同一个镜像层。

高效存储：

  • 多个容器可以共享同一个镜像的只读层，从而减少存储空间的占用。
  • 只有容器的可写层是独立的，因此容器的启动速度非常快。

image layer和AUFS

每一个Docker image都是由一系列read-only layer组成的。image layer的内容都存储在Docker hosts filesystem的/var/lib/docker/aufs/diff目录下。而/var/lib/docker/aufs/layers目录，则存储着image layer如何堆栈这些layer的metadata。

container layer和AUFS

Docker使用AUFS的CoW技术来实现image layer共享和减少磁盘空间占用。CoW意味着一旦某个文件只有很小的部分有改动，AUFS也需要复制整个文件。这种设计会对容器性能产生一定的影响，尤其是在待复制的文件很大，或者位于很多image layer下方，又或者AUFS需要深度搜索目录结构树的时候。不过也不用过度担心，对于一个容器而言，每个image layer最多只需要复制一次。后续的改动都会在第一次拷贝的container layer上进行。

启动一个container的时候，Docker会为其创建一个read-only的init layer，用来存储与这个容器内环境相关的内容；Docker还会为其创建一个read-write的layer来执行所有写操作。container layer的mount目录也是/var/lib/docker/aufs/mnt。container的metadata和配置文件都存放在/var/lib/docker/containers/＜container-id＞目录中。container的read-write layer存储在/var/lib/docker/aufs/diff/目录下。即使容器停止，这个可读写层仍然存在，因而重启容器不会丢失数据，只有当一个容器被删除的时候，这个可读写层才会一起删除

Linux网络虚拟化

Namespace和Cgroups技术实现了容器进程的隔离，并且通过AUFS让容器拥有自己的“文件系统”，容器中的进程所感受到的环境就像在一台虚拟机上一样，但是这台“虚拟机”还没有插上“网线”，那么在这里就会通过网络虚拟化技术构建容器的网络，给这个“虚拟机”插上网线。

网络虚拟化基石：network namespace

在前面什么是Docker? - The Peak Tower中简单谈到了Linux Namespace技术，这里简单回顾一下：

Linux的namespace（名字空间）的作用就是“隔离内核资源”。在Linux的世界里，文件系统挂载点、主机名、POSIX进程间通信消息队列、进程PID数字空间、IP地址、user ID数字空间等全局系统资源被namespace分割，装到一个个抽象的独立空间里。而隔离上述系统资源的namespace分别是Mount namespace、UTS namespace、IPC namespace、PID namespace、network namespace和user namespace。对进程来说，要想使用namespace里面的资源，首先要“进入”（具体操作方法，下文会介绍）到这个namespace，而且还无法跨namespace访问资源。

Linux的namespace给里面的进程造成了两个错觉：

（1）它是系统里唯一的进程。

（2）它独享系统的所有资源。

默认情况下，Linux进程处在和宿主机相同的namespace，即初始的根namespace里，默认享有全局系统资源。

再回到网络虚拟化技术(network namespace)它在Linux内核2.6版本引入，作用是隔离Linux系统的设备，以及IP地址、端口、路由表、防火墙规则等网络资源。因此，每个网络namespace里都有自己的网络设备（如IP地址、路由表、端口范围、/proc/net目录等）。从网络的角度看，network namespace使得容器非常有用，一个直观的例子就是：由于每个容器都有自己的（虚拟）网络设备，并且容器里的进程可以放心地绑定在端口上而不必担心冲突，这就使得在一个主机上同时运行多个监听80端口的Web服务器变为可能，如图所示。

一个全新的network namespace会附带创建一个本地回环地址。除此之外，没有任何其他的网络设备。仅有一个本地回环设备是没法与外界通信的。如果我们想与外界（比如主机上的网卡）进行通信，就需要在namespace里再创建一对虚拟的以太网卡，即所谓的veth pair。顾名思义，veth pair总是成对出现且相互连接，它就像Linux的双向管道（pipe），报文从veth pair一端进去就会由另一端收到。

我们都知道，Linux实际是通过网络设备去操作和使用网卡的，系统装了一个网卡之后会为其生成一个网络设备实例，比如eth0。而随着网络虚拟化技术的发展，Linux支持创建出虚拟化的设备，可以通过虚拟化设备的组合实现多种多样的功能和网络拓扑。常见的虚拟化设备有Veth、Bridge、802.1.q VLAN device、TAP等

仅有veth pair设备，容器是无法访问外部网络的。为什么呢？因为从容器发出的数据包，实际上是直接进了veth pair设备的协议栈。如果容器需要访问网络，则需要使用网桥等技术将veth pair设备接收的数据包通过某种方式转发出去。

在计算机网络课本上学的网桥正如其字面含义所描述的，有“牵线搭桥”之意，用于连接两个不同的局域网，是网线的延伸。网桥是二层网络设备，两个端口分别有一条独立的交换信道，不共享一条背板总线，可隔离冲突域。网桥比集线器（hub）性能更好，集线器上各端口都是共享同一条背板总线的。后来，网桥被具有更多端口、可隔离冲突域的交换机（switch）所取代。

Linux bridge就是Linux系统中的网桥，但是Linux bridge的行为更像是一台虚拟的网络交换机，任意的真实物理设备（例如eth0）和虚拟设备（例如，前面讲到的veth pair和后面即将介绍的tap设备）都可以连接到Linux bridge上。

需要注意的是，Linux bridge不能跨机连接网络设备。

Linux bridge与Linux上其他网络设备的区别在于，普通的网络设备只有两端，从一端进来的数据会从另一端出去。例如，物理网卡从外面网络中收到的数据会转发给内核协议栈，而从协议栈过来的数据会转发到外面的物理网络中。Linux bridge则有多个端口，数据可以从任何端口进来，进来之后从哪个口出去取决目的MAC地址，原理和物理交换机差不多。

刚创建一个bridge时，它是一个独立的网络设备，只有一个端口连着协议栈，其他端口什么都没连接，这样的bridge其实没有任何实际功能，如图所示。

Linux bridge在网络虚拟化中的应用

虚拟机

虚拟机通过tun/tap或者其他类似的虚拟网络设备，将虚拟机内的网卡同br0连接起来，这样就达到和真实交换机一样的效果，虚拟机发出去的数据包先到达br0，然后由br0交给eth0发送出去，数据包都不需要经过host机器的协议栈，效率高，如图所示。如果有多个虚拟机，那么这些虚拟机通过tun/tap设备连接到网桥。

容器

容器运行在自己单独的network namespace里，因此都有自己单独的协议栈。Linux bridge在容器场景的组网和上面的虚拟机场景差不多，但也存在一些区别。例如，容器使用的是veth pair设备，而虚拟机使用的是tun/tap设备。在虚拟机场景下，我们给主机物理网卡eth0分配了IP地址；而在容器场景下，我们一般不会对宿主机eth0进行配置。在虚拟机场景下，虚拟器一般会和主机在同一个网段；而在容器场景下，容器和物理网络不在同一个网段内。Linux bridge在容器中的应用如图所示。

在容器中配置其网关地址为br0，在我们的例子中即1.2.3.101（容器网络网段是1.2.3.0/24）。因此，从容器发出去的数据包先到达br0，然后交给host机器的协议栈。由于目的IP是外网IP，且host机器开启了IP forward功能，数据包会通过eth0发送出去。因为容器所分配的网段一般都不在物理网络网段内（在我们的例子中，物理网络网段是10.20.30.0/24），所以一般发出去之前会先做NAT转换（NAT转换需要自己配置，可以使用iptables，）。

网络接口的混杂模式

前文提到过网桥的混杂模式，网络接口的混杂模式在Kubernetes网络也有应用，本节将重点讨论网络接口的混杂模式。

混杂模式，简称Promisc mode，俗称“监听模式”。混杂模式通常被网络管理员用来诊断网络问题，但也会被无认证的、想偷听网络通信的人利用。根据维基百科的定义，混杂模式是指一个网卡会把它接收的所有网络流量都交给CPU，而不是只把它想转交的部分交给CPU。在IEEE 802定的网络规范中，每个网络帧都有一个目的MAC地址。在非混杂模式下，网卡只会接收目的MAC地址是它自己的单播帧，以及多播及广播帧；在混杂模式下，网卡会接收经过它的所有帧！

给用户态一个机会：tun/tap设备

在前文讲解Linux bridge时就介绍过tun/tap设备，并强调tun/tap设备在虚拟机的组网过程中起到作用。tun/tap设备到底是什么？从Linux文件系统的角度看，它是用户可以用文件句柄操作的字符设备；从网络虚拟化角度看，它是虚拟网卡，一端连着网络协议栈，另一端连着用户态程序。如果把veth pair称为设备孪生，那么tun/tap就像是一对表兄弟。虽然很多情况下我们都是连带提到它们，但它们还是有些区别的。tun表示虚拟的是点对点设备，tap表示虚拟的是以太网设备，这两种设备针对网络包实施不同的封装。

tun/tap设备有什么作用呢？tun/tap设备可以将TCP/IP协议栈处理好的网络包发送给任何一个使用tun/tap驱动的进程，由进程重新处理后发到物理链路中。tun/tap设备就像是埋在用户程序空间的一个钩子，我们可以很方便地将对网络包的处理程序挂在这个钩子上，OpenVPN、Vtun、flannel都是基于它实现隧道包封装的。

tun/tap设备的工作原理

先简单介绍物理设备上的数据是如何通过Linux网络栈送达用户态程序的，tun/tap设备的基本原理如图所示。

上图是一个经典的、通过Socket调用实现用户态和内核态数据交互的过程。物理网卡从网线接收数据后送达网络协议栈，而进程通过Socket创建特殊套接字，从网络协议栈读取数据。

从网络协议栈的角度看，tun/tap设备这类虚拟网卡与物理网卡并无区别。只是对tun/tap设备而言，它与物理网卡的不同表现在它的数据源不是物理链路，而是来自用户态！这也是tun/tap设备的最大价值所在。

tun/tap设备其实就是利用Linux的设备文件实现内核态和用户态的数据交互，而访问设备文件则会调用设备驱动相应的例程，要知道设备驱动也是内核态和用户态的一个接口。tun设备的工作模式如图所示。

普通的物理网卡通过网线收发数据包，而tun设备通过一个设备文件（/dev/tunX）收发数据包。所有对这个文件的写操作会通过tun设备转换成一个数据包传送给内核网络协议栈。当内核发送一个包给tun设备时，用户态的进程通过读取这个文件可以拿到包的内容。当然，用户态的程序也可以通过写这个文件向tun设备发送数据。

tap设备与tun设备的工作原理完全相同，区别在于：

  • tun设备的/dev/tunX文件收发的是IP包，因此只能工作在L3，无法与物理网卡做桥接，但可以通过三层交换（例如ip_forward）与物理网卡连通；
  • tap设备的/dev/tapX文件收发的是链路层数据包，可以与物理网卡做桥接。

tun设备的tun是英文隧道（tunnel）的缩写，言下之意，tun设备似乎与隧道网络存在一丝联系。tun/tap设备的用处是将协议栈中的部分数据包转发给用户空间的应用程序，给用户空间的程序一个处理数据包的机会。常见的tun/tap设备使用场景有数据压缩、加密等，最常见的是VPN，包括tunnel及应用层的IPSec等。

iptables

iptables的底层实现是netfilter。netfilter是Linux内核2.4版引入的一个子系统，最初由Linux内核防火墙和网络的维护者Rusty Russell提出。它作为一个通用的、抽象的框架，提供一整套hook函数的管理机制，使得数据包过滤、包处理（设置标志位、修改TTL等）、地址伪装、网络地址转换、透明代理、访问控制、基于协议类型的连接跟踪，甚至带宽限速等功能成为可能。netfilter的架构就是在整个网络流程的若干位置放置一些钩子，并在每个钩子上挂载一些处理函数进行处理。

IP层的5个钩子点的位置，对应iptables就是5条内置链，分别是PREROUTING、POSTROUTING、INPUT、OUTPUT和FORWARD。netfilter原理图如图所示。

当网卡上收到一个包送达协议栈时，最先经过的netfilter钩子是PREROUTING，如果确实有用户埋了这个钩子函数，那么内核将在这里对数据包进行目的地址转换（DNAT）。不管在PREROUTING有没有做过DNAT，内核都会通过查本地路由表决定这个数据包是发送给本地进程还是发送给其他机器。如果是发送给其他机器（或其他network namespace），就相当于把本地当作路由器，就会经过netfilter的FORWARD钩子，用户可以在此处设置包过滤钩子函数，例如iptables的reject函数。所有马上要发到协议栈外的包都会经过POSTROUTING钩子，用户可以在这里埋下源地址转换（SNAT）或源地址伪装（Masquerade，简称Masq）的钩子函数。如果经过上面的路由决策，内核决定把包发给本地进程，就会经过INPUT钩子。本地进程收到数据包后，回程报文会先经过OUTPUT钩子，然后经过一次路由决策（例如，决定从机器的哪块网卡出去，下一跳地址是多少等），最后出协议栈的网络包同样会经过POSTROUTING钩子。

netfilter是Linux内核网络模块的一个经典框架，毫不夸张地说，整个Linux系统的网络安全大厦都构建在netfilter之上，如图所示。

我们可以发现，构建在netfilter钩子之上的网络安全策略和连接跟踪的用户态程序就有ebtables、arptables、（IPv6版本的）ip6tables、iptables、iptables-nftables（iptables的改进版本）、conntrack（连接跟踪）等。Kubernetes网络之间用到的工具就有ebtables、iptables/ip6tables和conntrack，其中iptables是核心。

iptables的三板斧：table、chain和rule

iptables是用户空间的一个程序，通过netlink和内核的netfilter框架打交道，负责往钩子上配置回调函数。一般情况下用于构建Linux内核防火墙，特殊情况下也做服务负载均衡（这是Kubernetes的特色操作，我们将在后面章节专门分析）。iptables的工作原理如图所示。

我们常说的iptables 5X5，即5张表（table）和5条链（chain）。

Table

表名称 说明
filter 表 默认的表，用于网络流量的过滤。包含数据包的接受（ACCEPT）、拒绝（DROP）等基本操作。
nat 表 用于网络地址转换（NAT，Network Address Translation），处理数据包的源地址和目的地址转换，主要用于路由、端口转发等。

这5张表的优先级从高到低是：raw、mangle、nat、filter、security。需要注意的是，iptables不支持用户自定义表。

Chain

链名称 说明
INPUT 链 该链用于处理进入本机的数据包。所有发往本地系统的数据包会首先进入 INPUT 链。
OUTPUT 链 该链用于处理由本机发出的数据包。所有由本机发送的数据包会首先进入 OUTPUT 链。
FORWARD 链 该链用于处理通过本机转发的数据包。如果数据包不是发往本地机器，而是需要转发到其他机器时，会经过此链。
PREROUTING 链 该链用于处理进入本机的数据包，在路由决定之前进行处理。例如，NAT表中的端口转发规则会使用此链。
POSTROUTING 链 该链用于处理从本机发出的数据包，在路由决定之后进行处理。常用于修改出站数据包的源地址（如源地址转换）。

这里产生了一个疑问，iptables的链（chain）的概念还比较好理解，就是对应netfilter的5处钩子，而iptables的表（table）的具体作用是什么呢？而且上文说的“不是每个链上都能挂表”这句话的表述似乎也很奇怪。

任何概念都不是凭空想象出来的，它都是有实际用途的。其实，iptables的表是来分类管理iptables规则（rule）的，系统所有的iptables规则都被划分到不同的表集合中。上文也提到了，filter表中会有过滤数据包的规则，nat表中会有做地址转换的规则。因此，iptables的规则就是挂在netfilter钩子上的函数，用来修改数据包的内容或过滤数据包，iptables的表就是所有规则的5个逻辑集合！

Rule

在 iptables 中，Rule（规则） 是用于定义如何处理进入、离开或转发的数据包的配置项。每个规则（Rule）包含了一组条件和对应的动作。通过这些规则，可以指定特定的数据包流量如何被接受、拒绝或处理。

1. iptables 规则的基本结构

每条 iptables 规则通常由以下几个部分组成：

  • 匹配条件（Match Conditions）：指定规则的适用条件，例如源地址、目标地址、协议类型、端口等。
  • 动作（Target Action）：指定匹配条件满足时，iptables 应该对数据包执行的操作，例如 ACCEPT、DROP、REJECT、SNAT、DNAT 等。

例如，以下是一个简单的规则：

  • -A INPUT：将规则追加到 INPUT 链。
  • -p tcp：匹配协议为 TCP。
  • --dport 80：匹配目标端口为 80（HTTP 服务）。
  • -j ACCEPT：匹配成功时，接受该数据包。

2. iptables 规则的常见目标

iptables 支持多种目标类型，常见的包括：

目标（Target） 说明
ACCEPT 允许数据包通过。
DROP 丢弃数据包，不返回任何响应（常用于防止攻击）。
REJECT 丢弃数据包并返回一个 ICMP 错误消息（例如，目标不可达）。
SNAT 源地址转换（Source NAT），修改数据包的源地址。
DNAT 目的地址转换（Destination NAT），修改数据包的目标地址。
MASQUERADE 动态源地址转换，通常用于共享 Internet 连接（当源地址是本地私有地址时）。
LOG 记录数据包的详细信息，通常用于调试或监控。
RETURN 停止当前链的处理，返回到调用链的下一条规则。
MARK 设置数据包标记，用于其他系统的规则或日志管理。

3. 规则匹配条件

每条规则都有一些匹配条件，这些条件可以组合使用，以确保规则只适用于特定的数据包。常见的匹配条件包括：

条件 说明
-p [协议] 匹配协议类型，如 tcp、udp、icmp 等。
-s [源IP地址] 匹配源IP地址（可以是IP地址范围）。
-d [目标IP地址] 匹配目标IP地址（可以是IP地址范围）。
–sport [源端口] 匹配源端口（通常与协议为 tcp 或 udp 一起使用）。
–dport [目标端口] 匹配目标端口（通常与协议为 tcp 或 udp 一起使用）。
-i [接口] 匹配数据包的进入接口（例如 eth0）。
-o [接口] 匹配数据包的离开接口（例如 eth0）。
-m [模块] 使用额外的匹配模块，如 conntrack、state 等。
-j [目标] 指定规则匹配成功后执行的动作（如 ACCEPT、DROP）。

值得一提的是，用户自定义链中的规则和系统预定义的5条链里的规则没有区别。由于自定义的链没有与netfilter里的钩子进行绑定，所以它不会自动触发，只能从其他链的规则中跳转过来，这也是JUMP动作存在的意义。

容器

容器是镜像的运行时实例。它是在镜像的基础上启动出来的，带有自己的文件系统、进程、网络等资源。容器可以看作是一个活跃的、运行中的应用。容器就像是从蓝图（镜像）上建造出来的一辆车，它会具体化为一个可以行驶的实体。

容器（Container）是一个轻量级、可移植、可执行的软件包，它封装了应用及其所有依赖项（包括操作系统库和配置文件），能够在任何环境中运行。容器的主要特点是隔离性和高效性。容器与虚拟机的区别在于它们共享宿主机的操作系统内核，而虚拟机是通过虚拟化实现完整的操作系统模拟。

容器的核心特点：

  • 隔离性：每个容器都有自己的文件系统、进程空间、网络配置等，但都在同一个宿主操作系统内核上运行。
  • 高效性：容器不需要模拟整个操作系统，资源消耗较低，启动速度较快。
  • 可移植性：容器镜像可以在任何支持Docker的环境中运行，保证了一致性。
  • 易于管理：容器的创建、启动、停止、销毁等操作都非常简便，适合微服务架构的应用部署。

网络模型

前置知识：Linux网络虚拟化 - The Peak Tower

从网络的角度看容器，就是network namespace+容器的组网方案。利用network namespace，可以为Docker容器创建隔离的网络环境。容器具有完全独立的网络栈，与宿主机隔离。用户也可以让Docker容器共享主机或者其他容器的network namespace。network namespace的相关技术点已经在前面的文章中详细地介绍过，本节不再赘述。

容器的网络方案可以分为三大部分：

  • 单机的容器间通信
  • 跨主机的容器间通信
  • 容器与主机间通信。

单机的容器间通信

我们在使用docker run命令创建Docker容器时，可以使用–network选项指定容器的网络模式。Docker有以下4种网络模式：

  • bridge模式，通过–network=bridge指定
  • host模式，通过–network=host指定
  • container模式，通过–network=container:NAME_or_ID指定，即joiner容器
  • none模式，通过–network=none指定

在安装完Docker之后，Docker Daemon会在宿主机上自动创建三个网络，分别是bridge网络、host网络和none网络

bridge模式

Docker在安装时会创建一个名为docker0的Linux网桥。bridge模式是Docker默认的网络模式，在不指定–network的情况下，Docker会为每一个容器分配network namespace、设置IP等，并将Docker容器连接到docker0网桥上。严谨的表述是，创建的容器的veth pair中的一端桥接到docker0上。docker0网桥是普通的Linux网桥，而非OVS网桥。

host模式

连接到host网络的容器共享Docker host的网络栈，容器的网络配置与host完全一样。host模式下容器将不会获得独立的network namespace，而是和宿主机共用一个network namespace。容器将不会虚拟出自己的网卡，配置自己的IP等，而是使用宿主机的IP和端口。

host模式下的容器可以看到宿主机的所有网卡信息，甚至可以直接使用宿主机IP地址和主机名与外界通信，无须额外进行NAT，也无须通过Linux bridge进行转发或者进行数据包的封装。

当然，host模式有利有弊，优点是没有性能损耗且配置方便，缺点也很明显，例如：

  • 容器没有隔离、独立的网络栈：容器因与宿主机共用网络栈而争抢网络资源，并且容器崩溃也可能使主机崩溃，导致网络的隔离性不好；·
  • 端口资源冲突：宿主机上已经使用的端口就不能再用了

container模式

创建容器时使用–network=container:NAME_or_ID模式，在创建新的容器时指定容器的网络和一个已经存在的容器共享一个network namespace，但是并不为Docker容器进行任何网络配置，这个Docker容器没有网卡、IP、路由等信息，需要手动为Docker容器添加网卡、配置IP等。

需要注意的是，container模式指定新创建的容器和已经存在的任意一个容器共享一个network namespace，但不能和宿主机共享。新创建的容器不会创建自己的网卡，配置自己的IP，而是和一个指定的容器共享IP、端口范围等。同样，两个容器除了网络方面，其他的如文件系统、进程列表等还是隔离的。两个容器的进程可以通过lo网卡设备通信。

none模式

none模式下的容器只有lo回环网络，没有其他网卡。none模式网络可以在容器创建时通过–network=none指定。这种类型的网络没有办法联网，属于完全封闭的网络。唯一的用途是客户有充分的自由度做后续的配置。这种模式下的Docker容器拥有自己的network namespace，但是并不为Docker容器进行任何网络配置。也就是说，这个Docker容器没有网卡、IP、路由等信息，需要我们自己为Docker容器添加网卡、配置IP等。

跨主机容器间通信

在容器化架构中，跨主机的容器间通信是非常重要的，因为它使得分布式容器应用能够相互访问。跨主机容器通信一般依赖于网络覆盖技术（Overlay Network）或容器编排平台（如 Docker Swarm 和 Kubernetes）来实现。

跨主机通信的需求：容器部署通常不局限于单台主机，容器可以分布在多台宿主机上，因此需要支持容器之间跨主机通信。主要目的是确保无论容器位于哪台主机上，都能实现相互访问。

跨主机通信的实现方式

Overlay 网络（覆盖网络）

概念：Overlay 网络是一个虚拟网络，将多个主机上的容器连接到一个共享的虚拟网络中，容器通过该网络跨主机进行通信。

技术原理：Overlay 网络通过隧道技术（如 VXLAN、GRE、IPsec 等）将不同主机的网络连接起来，创建一个虚拟的、全局可访问的容器网络。

优点：

  • 透明性：容器之间的通信不受物理主机的限制。
  • 隔离性：提供容器网络的完全隔离，使得容器之间的网络不干扰。
  • 灵活性：适合大规模容器编排，如 Kubernetes 和 Docker Swarm。

缺点：

  • 可能引入一些网络延迟，因为数据包需要通过虚拟隧道进行传输。
  • 配置相对复杂，尤其是在涉及多个物理机时。

Docker Swarm 和 Kubernetes 网络

Docker Swarm：Docker 自带的容器编排工具，使用 Overlay 网络进行跨主机容器间的通信。Docker Swarm 使用 docker network create --driver overlay 来创建跨主机的 Overlay 网络，使得分布在不同主机上的容器能够互相访问。

Swarm Overlay 网络：

  • 使用内部的 Raft 协议来同步集群中的服务状态。
  • 容器通过跨宿主机的 Overlay 网络实现跨主机通信。

Kubernetes：Kubernetes 支持 CNI（Container Network Interface）标准，可以选择不同的网络插件（如 Flannel、Calico、Weave 等）来实现跨主机通信。

  • Flannel：一个简单的 Overlay 网络插件，使用 VXLAN 或其他隧道协议连接跨主机的容器。
  • Calico：提供更高效的网络实现，可以使用路由方式而非 Overlay 网络。
  • Weave：也提供 Overlay 网络，通过 VXLAN 或 IPsec 隧道来实现跨主机通信。

直接连接

容器直接通过宿主机的网络进行跨主机通信，不使用 Overlay 网络。其容器使用主机的路由表和网络接口直接进行通信。通过配置路由，使容器可以跨主机通信。

优点：

  • 高效：没有 Overlay 网络引入的额外开销。
  • 配置灵活：可以直接操作宿主机的网络配置。

缺点：

  • 复杂性：需要手动配置路由和网络接口。
  • 安全性：容器与宿主机之间没有网络隔离，可能会导致安全问题。

容器与主机间通信

容器与宿主机的通信是容器化部署中的重要组成部分。由于容器通常运行在宿主机的网络命名空间内，因此容器与宿主机之间的通信方式需要合理配置，以确保网络功能的正常工作。容器与宿主机的通信可以通过以下几种方式实现。

1. 容器与主机间通信的基本方式

容器与宿主机的通信方式主要有三种：

  1. 端口映射（Port Mapping）
  2. Host 网络模式
  3. Macvlan 网络模式

2. 端口映射

端口映射是最常见的容器与宿主机间通信的方式。容器通常会运行在一个隔离的网络命名空间中，但可以通过将容器的端口映射到宿主机的端口，来实现外部访问容器。

4. Macvlan 网络模式

Macvlan 网络模式 允许容器直接使用宿主机网络的一个独立的 MAC 地址，容器通过宿主机的物理网络接口与外界通信，而不使用 Docker 默认的虚拟网桥（bridge）进行通信。这使得容器在网络上与物理主机一样，可以直接与其他设备或宿主机进行通信。

容器网络的第一个标准(CNM)

容器网络的第一个标准是 CNM（Container Network Model），即容器网络模型。它是 Docker 提出的一个容器网络模型标准，旨在提供一种标准化的方式来描述和管理容器网络。CNM 定义了容器如何通过网络连接起来，以及容器如何与外部世界进行通信。

CNM 主要组件

CNM 由以下几个关键组件组成，来定义容器的网络行为：

  1. Network：
    • 表示容器之间的网络连接。
    • 它是一个抽象层，用于实现网络功能，容器通过网络连接在一起。
    • 可以有不同类型的网络（如：bridge、overlay、macvlan 等）。
    • 网络模型本身支持创建、管理和删除不同类型的网络。
  2. Endpoint：
    • 容器与网络连接的接口，代表一个容器加入到某个网络。
    • 每个容器通过一个或多个 Endpoint 连接到网络。
    • 每个 Endpoint 有一个 IP 地址和网络配置，用于数据包的路由和转发。
  3. Sandbox：
    • 沙箱是一个封装容器网络配置的环境，包含了容器的网络设置、虚拟网络接口（veth）、路由等信息。
    • 沙箱的目的是提供容器的网络隔离，并让容器网络配置不与其他容器网络干扰。
  4. Network Plugin：
    • 网络插件是实现 CNM 的具体实现，可以是自定义的，也可以是现有的网络插件（如 Docker 网络插件）。
    • 网络插件提供了底层的网络实现和接口（如 IP 地址分配、路由设置等）。
  5. Networking API：
    • 网络插件提供的 API 接口，允许用户或者容器编排系统如 Docker 和 Kubernetes 管理容器的网络。
    • 通过这些 API，用户可以创建、删除、配置和管理容器的网络和连接。

CNM 与容器编排的关系

CNM 是为了支持容器编排而设计的，它为容器之间的网络通信提供了标准化的方式。容器编排系统（如 Docker、Kubernetes 等）可以利用 CNM 来管理和配置容器网络，使容器能够跨多个主机和不同的网络互联。

例如，Docker 在其容器网络实现中遵循了 CNM 标准：

  • Docker 使用 CNM 定义了其容器网络模型，并实现了多个网络类型（如 bridge 网络、host 网络、overlay 网络等）。
  • 在 Docker 中，每个容器可以通过不同的网络插件（如 bridge、host 或 overlay）与其他容器或外部网络通信。

CNM 网络类型

CNM 定义了几种常见的网络类型来满足不同场景的需求：

  1. Bridge Network（桥接网络）：
    • 容器通过一个虚拟网桥（通常是 docker0）连接到宿主机上。
    • 所有连接到同一个桥接网络的容器可以通过私有 IP 地址直接相互通信。
  2. Host Network（主机网络）：
    • 容器共享宿主机的网络栈，包括 IP 地址、端口等。容器内的服务可以直接暴露在宿主机上。
    • 容器和宿主机之间没有隔离，适用于需要高性能网络的场景。
  3. Overlay Network（覆盖网络）：
    • 容器跨主机通信时使用的网络类型。通过 VPN 或 VXLAN 技术将多个主机上的容器连接起来，形成一个逻辑上的网络。
    • 适用于分布式容器平台和容器编排平台（如 Kubernetes）。
  4. Macvlan Network（Macvlan 网络）：
    • 允许容器在宿主机网络上拥有独立的 MAC 地址，使得容器在网络上看起来像是独立的物理设备。
    • 常用于需要容器具有与宿主机相同网络身份的场景，例如需要容器直接暴露到外部网络时。

CNM 的优势

  • 标准化：CNM 为容器网络提供了一个统一的标准，确保了不同容器和网络插件之间的一致性。
  • 灵活性：CNM 允许通过网络插件来实现不同类型的网络，用户可以根据需求选择合适的网络模型。
  • 隔离性：通过网络沙箱，CNM 可以有效地实现容器网络之间的隔离。
  • 易于扩展：通过网络插件，CNM 可以方便地扩展新的网络功能，支持新的网络类型和协议。

CNM 与 CNI（Container Network Interface）对比

虽然 CNM 是 Docker 提出的容器网络标准，但随着容器编排技术的成熟，CNI（Container Network Interface） 成为了另一种流行的容器网络标准，特别是在 Kubernetes 中。两者的主要区别：

CNM CNI
由 Docker 提出并用于 Docker 网络 由 Cloud Native Computing Foundation 提出，广泛应用于 Kubernetes
定义了网络类型、端口和沙箱等 更专注于容器网络插件接口，提供通用的网络管理接口
适用于 Docker 和其他容器平台 主要应用于 Kubernetes 和容器编排系统

尽管如此，CNM 和 CNI 的目标是相似的，都是为了提供容器之间的网络连接，并且两者可以互操作。在 Docker 早期版本中，CNM 是默认的网络模型，而 CNI 逐渐成为 Kubernetes 等编排平台的标准容器网络接口。
